# [FIX SPEC] gh-cli card: document `gh pr edit` Projects-classic failure mode and the REST fallback

Resolves `.opencode#2461`.

## 1. Intent and Executive Summary

| # | Field | Description |
|---|-------|-------------|
| 1 | **Problem Statement** | On the current system gh build (2.45.0, Ubuntu `2.45.0-1ubuntu0.3`), `gh pr edit --body-file <file>` fails with exit 1: `GraphQL: Projects (classic) is being deprecated in favor of the new Projects experience … (repository.pullRequests.nodes.0.projectCards)`. The failure is server-side: gh's `pr edit` GraphQL read path includes the deprecated `projectCards` field, so the edit never reaches the API regardless of PR content. The gh-cli skill card (`.opencode/skills/gh-cli/SKILL.md`) has no coverage for this: §4 "Common operations" lists `gh pr create/view/merge` but not `gh pr edit`, and no fallback for PR-body amendment is documented anywhere in the card. An agent following the deck that needs to amend a PR body on an affected gh build hits a silent hard failure with no deck-guided recovery path. Upgrading gh is not a general remedy: the system is package-current (no newer Ubuntu package exists), and the deck runs on machines outside this project's package control. |
| 2 | **Root Cause / Motivation** | Two independent causes. (a) Upstream: gh 2.45.0's `pr edit` mutation query unconditionally reads the deprecated `projectCards` field; GitHub's GraphQL API now rejects any query touching it. (b) Deck: the gh-cli card was authored (.opencode#2490, #2547) covering issue and repo flows plus PR create/view/merge and release create/view, without a `pr edit` operation or a failure-mode fallback — so the deck's own recovery path (§5 "Failures are information") has nothing specific to diagnose against for this case. Motivation observed 2026-10-14: PR #204 of `NewsRx/hermes-ingest-pubmed` could not be body-amended via `gh pr edit` (issue #2461 report), reproduced live on a disposable PR in `michael-conrad/test-submodule-1` the same day. |
| 3 | **Approach Chosen** | Amend `.opencode/skills/gh-cli/SKILL.md` (deck-authored card — hand-editable; vendor-card boundary not involved) in place: (a) extend §4's common-operations list with `gh pr edit` so agents reach for the native command knowingly; (b) extend §5's failure-handling rule with the verified recovery: when `gh pr edit` fails with the Projects-classic deprecation error, amend the PR body via REST — `gh api -X PATCH repos/{owner}/{repo}/pulls/{N} -F body=@<file>` — which bypasses the GraphQL read path entirely and uses the same built-in gh auth. The fallback is phrased as a symptom→remedy mapping (stderr names the deprecation → use the PATCH), version-agnostic: it stays correct on fixed gh builds too, where it simply never triggers. Scope correction from triage is binding on the content: the failure is `gh pr edit` only — `gh issue edit` was tested on the same build and succeeds (exit 0), so nothing in the card may extend the failure mode to issue operations. Card edits go through the skill-creator admission gate; this item is developer-directed (the developer chose the card fix over vendoring a newer gh binary in session, 2026-10-14), so the carve-out applies and the gate's content standards bind. Provenance lines (frontmatter `provenance:` and the SPDX body comment) gain the `.opencode#2461` anchor. |
| 4 | **Alternatives Considered & Why Discarded** | (a) Upgrade gh on affected machines — discarded as the primary fix: the system is package-current, no newer package is available, and the deck's consumers run on machines whose package state this project does not control; it treats one machine, not the deck. (b) Vendor a current gh binary into `<project-root>/.tools/` per project, reusing global auth config — discarded: it cuts against the floor's "gh CLI — built-in" and "never hand-rolled" inventory rule, adds per-project binary/version/bootstrap maintenance the deck would then have to govern, and solves one stale-package symptom where a one-sentence fallback solves it everywhere; it also duplicates what the card's §2 already provides (`gh api` exists for gaps). (c) File the fallback in a new standalone task card (e.g. `gh-pr-edit`) — discarded: bodies stay lean and the gap is two sentences, not a procedure; a new card fails the gate's what-it-replaces/net-zero test. (d) Also document an issue-edit fallback — discarded: triage showed `gh issue edit` succeeds on the affected build; documenting a fallback for a working command would author a false failure mode into the deck. |
| 5 | **Key Design Decisions** | (1) Symptom-mapped, not version-mapped: the card keys the fallback to the stderr text (the deprecation error), never to a gh version range — a version predicate would rot and implies a completeness claim about gh's release history nobody verified. (2) The fallback stays inside the card's own rules: it is `gh api` passthrough using built-in auth — no hand-rolled API code, satisfying §1/§2. (3) The fallback is stated as an amendment path for the PR body (`--body-file`/`--body` case, the verified one); the spec does not claim REST PATCH equivalence for title/metadata edits that were not tested — the card text says what was verified, nothing more. (4) Placement follows the card's existing structure — the operation joins §4's list; the failure mode and recovery join §5's failure rule — no new sections, no restructure of a lean card. (5) Root-agnostic discipline: the fallback text uses `{owner}/{repo}`/`{N}` placeholders, zero repo names or absolute paths. (6) Predicate classification: the fallback's trigger is fact-decidable (stderr names the deprecation) and the remedy is a fixed command — no scripted check on judgment; whether an amendment is worth making at all remains ordinary agent judgment under §5. (7) The failure mode and the recovery are separate criteria (SC-2/SC-3) so neither can pass on the other's presence. |
| 6 | **User Intent / Original Prompt** | `.opencode#2461` (bug report, 2026-09-23 repro; triage comment 2026-10-14 corrected scope). Session: "read .opencode#2461, does this even make sense? since when do projects handle PRs?" → explanation → "the system is up-todate. if no newer packages are available, then no help there. it would be better to fix the skill card I think as we do not have control over the multiple systems this deck is used on, unless it can be agent installed into <project-root>/.tools for agent use but still use the global config?" → (vendoring weighed and discarded) → "you have test repos to run tests on test-submodule-1 and test-submodule-2" → live repro + fallback verification executed → "complete your triage and convert into a fix spec". |

## 2. Not Included

- **A vendored gh binary** under any project `.tools/` path (Alternative (b)) — rejected on deck-governance and maintenance grounds; the floor inventory stays as is.
- **An `gh issue edit` fallback or failure note** — `gh issue edit` works on the affected build; documenting a remedy for a working path would fabricate a failure mode (Design Decision 3's negative case).
- **Claims about REST equivalence for edits other than the body** (title, reviewers, metadata) — untested in triage; the card states the verified case only.
- **Changes to the card's description/frontmatter routing** — the description already routes on "when GitHub operations fail unexpectedly"; only the provenance anchor changes.
- **Changes to any other card, guideline, or floor file** — the gap is local to gh-cli's operations/failure coverage.
- **Deck-wide gh-version auditing** — no sweep of other cards for stale-version claims; nothing in triage surfaced a second occurrence.
