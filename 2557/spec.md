# SPEC — Restore build/run verification practice and the language/build-framework skill-card family

## 1. Intent and Executive Summary

### Problem Statement

Agent behavior regressed in three reported facets, all traced to one root cause (below):

1. **Build-verification practice lost.** The agent no longer verifies build-affecting changes by a shallow checkout into a temp folder, running the canonical build there, and asserting the final outputs (example for Gradle: `./gradlew shadowJar`, `./gradlew build` are not being run). The developer scoped the impact to **all build frameworks and languages**. Provenance that this practice existed and was retired: spec `.opencode#365` ("[SPEC] Release promotion verification gate — pinned-SHA build+test before tag", recovered from issue-store git history) was implemented as `.opencode#2439` — the release-promoter verification gate with behavioral SCs 1–6 (shallow temp-copy checkout, pinned submodule resolution, drift assertion, manifest-discovered build/test commands, build execution with BUILD_FAIL blocking promotion). The `#2490` re-rip moved the gated skill to `attic/` and stage 4e deleted the 2439 behavioral suite. The live `release-promoter` card carries no gate; the live `implement` workflow demands only "an executed check" and lists build inside a conflated "structural | lint/typecheck/build commands" row — a weaker rule that admits both "build never run" and "outputs never inspected."

2. **shadowJar/SPI packaging knowledge absent.** The agent no longer configures shadowJar correctly — INCLUDE semantics and the SPI changes fat jars require (`mergeServiceFiles()` / `META-INF/services` preservation). Grep of the live deck and the attic returns zero hits for `shadowJar`/`mergeServiceFiles`: the live deck never carried this knowledge. The retired default prompt (`attic/prompts/default.txt`) additionally carried the habit "if the correct command is unknown, ask the user and suggest adding it to the parent repo's AGENTS.md or the appropriate submodule's AGENTS.md" — that habit died with the re-rip.

3. **Dependency-injection mandate missing.** `.opencode#2243` mandated a Python DI pin (`dependency-injector`); `.opencode#2249` generalized it to a generic multi-language mandate with a curated three-tier recommended-packages table (Clear standard / Contested / Guidance-only), selection guidance, an HTML/CSS exclusion, and behavioral enforcement tests. `#2429` demoted the content into `082-python-standards.md`, and the `#2490` re-rip retired the guidelines corpus to `attic/`. The live deck has zero DI content.

**Supporting finding (session-store telemetry).** A read-only analysis of the opencode session database (`~/.local/share/opencode/opencode.db`) measured 784 skill loads across all history: pipeline cards fire constantly (`spec` 49, `approval-gate` 45, `implement` 42, `verify` 23), `programming-principles` has **zero loads ever**, and in the three largest product repositories only pipeline cards ever fired — no domain-knowledge card dispatched in real work. The same analysis shows where demand lives: `snea-shoebox-editor` is a Python product (2,498 `.py` writes, 1,087 sessions), `snea-phonetics` Python, `algonquian-library` Python+toml, with active Godot projects (`godot-4-opencode-dev-test`, `ai-hex-game-1`) whose dominant verbs are *run*, *export*, and *scenes*. Domain knowledge that exists only as a description does not dispatch; the demand is real and currently unserved.

### Root Cause / Motivation

The `#2490` deck re-rip ("lean corpus cut per developer direction") retired the pre-rip deck to `attic/` (tag `pre-rip`) and deleted the per-SC behavioral test suite. Retired with it: the release/build verification gate, its enforcement tests, the defunct guidelines corpus (including the DI mandate), and the default prompt's canonical-command habit. The live deck's replacement rules ("run the check; the output itself is the evidence"; "project-local lint/typecheck/build commands | cheap mechanical facts first") do not require a clean-tree build, do not require asserting final outputs, and carry no language-specific or build-framework knowledge. The regression is deck content retirement without equivalent replacement, now reported as live behavior and confirmed by dispatch telemetry.

### Approach Chosen

Restore the retired practice and knowledge as a **skill-card family under progressive disclosure**, per the developer's directives this session: focused skill cards (a multi-concern card's body loads whole at dispatch, defeating progressive disclosure), lean bodies, detail cards one level deep in `references/`, and descriptions as the router — matching agent intent semantically, never by keyword or file-glob matching. Because session telemetry shows domain knowledge never dispatches from descriptions alone, **structural edges from the reliably-loaded pipeline cards carry the family**: `spec`, `plan`, and `implement` gain explicit call outs in their main skill bodies directing the load of the language/tool cards for the languages in scope and of `programming-principles` for the engineering-principles layer.

The change surface is **only skill cards and skill detail cards** (new cards created, existing cards updated); behavioral enforcement scenarios are produced as verification instruments under `tests-v2/AGENTS.md`, not as knowledge implementation.

### Alternatives Considered & Why Discarded

- **One fat Java card carrying build toolchain + packaging + DI + code standards, with detail references.** Discarded per developer direction: the card's body loads whole at dispatch even when the task touches one concern; "multiple skill cards are more reliable with more properly focused content."
- **A separate top-level skill card per tool and topic (`gradle`, `uv`, `pyproject`, `dependency-injection`).** Considered and then superseded by the developer's consolidation directive: `uv` and `pyproject` are Python-exclusive concerns whose intent space is contained by Python-project work, so they fold into the `python` card as detail cards; `gradle` stays top-level because its intent space is not contained by Java work (build configuration touches no Java code, and a future Kotlin/Scala card would need it). The grouping rule: **a concern folds into a language card when its intent space is contained by that language's work; it stays top-level when it can arise without the language.**
- **The DI tier table scattered into per-language detail cards.** Discarded after re-evaluation: the table names fourteen ecosystems, most of which have no language card (cards are evidence-gated), so the knowledge would be homeless. The canonical tier table stays whole in the shared DI detail card under `programming-principles`; language cards carry practice depth that presupposes the recommendation.
- **Restore the defunct guidelines corpus (082 et al.) as guidelines.** Discarded: the guidelines machinery is retired; the developer's directive is that implementation creates/updates only skill cards and skill detail cards.
- **Restore the `#2249` tier table verbatim.** Discarded: live-source verification found the defunct table carries drift (the Java row's "Dagger for GWT-style" does not match the verified Java landscape — Spring / Guice / Dagger 2, with GWT's historical DI story being Gin). A recommendations list that is wrong is worse than one that is absent; the table returns through a currency pass with structure and tier philosophy preserved.
- **A routing.md row for the family.** Discarded: the platform already injects every card description into every session; a second always-injected surface restating the same mapping adds per-session cost and a drift surface without adding dispatch power. Descriptions are the router.
- **Admit maven/npm/cargo/dotnet cards in this change.** Deferred: not in the developer's named set; the taxonomy admits them on the same evidence terms when failures demand them.

### Key Design Decisions

- **Descriptions are the router — and the only injected dispatch surface.** Descriptions match agent intent semantically — never by user utterance, and never by keyword or file-glob matching; a lexical trigger is the same defect class the deck bans for user phrases (gamed by rephrasing, blind to paraphrase). Two framing patterns serve semantic matching: artifact cards describe the *activity* — writing, reviewing, or testing code in the language; building, packaging, or configuring the project through the tool; declaring what the project is — with artifacts named only as the natural objects of those activities; topic/detail content describes the *decision moments* where the concern arises. The set organizes through semantic association: each description carries the vocabulary of the intents it serves (seeded from the session-store demand vocabulary — e.g. the Godot card claims *running and exporting the game* because that is the actual dominant verb), sibling boundary sentences redirect adjacent intents by meaning, and every intent territory is claimed by exactly one description — siblings compose rather than compete. Wide territories with crisp seams: descriptions may be broad, provided the "Owns" clauses stay disjoint.
- **Dispatch edges carry what descriptions cannot.** Session telemetry measured the law: cards whose trigger is a discrete work-cycle event fire constantly; cards whose territory is a domain or a continuous practice (`programming-principles`: zero loads ever) never fire from descriptions alone. Therefore: (a) the `implement` pre-implementation section keeps a row identifying the language/toolchain of the files about to be modified and loading their cards; (b) the `spec`, `plan`, and `implement` main bodies carry explicit call outs directing both loads (language/tool cards for the languages in scope, `programming-principles` for the engineering layer) — language standards shape spec requirements and plan item structure, not just implementation; (c) descriptions are re-anchored to discrete decision moments wherever their concern is continuous. Design principle: **descriptions route discrete intents; structural edges from already-loaded surfaces route continuous concerns.**
- **DI layering.** The shared detail card `programming-principles/references/dependency-injection.md` carries the generic mandate ("use a DI approach," not "use framework X"), the full canonical tier table (currency-passed), selection guidance, the HTML/CSS exclusion, and the infra-tooling carveout in root-agnostic phrasing. Its load is a **mandatory read** carried in the `programming-principles` body — one directive covering every language, including cardless ones. Per-language DI practice stays as each language card's detail card (Java: Spring/Dagger/Guice wiring; Python: the `dependency-injector` pin), presupposing the mandate rather than restating the table.
- **Load discipline for practices.** The `programming-principles` body carries one-line summaries of the key expectations (versioning discipline, compatibility) with a load directive to `references/practices.md` for depth — the expectation is visible at level one, the detail is one hop away, and nothing fattens the mandatory path.
- **Build-verification placement.** The universal practice (shallow temp-copy checkout, canonical build from the repository's build manifest, final-outputs assertion) lives in the `implement` workflow reference, is demanded by the `verify` evidence bar, and is fully gated once per release in `release-promoter`. Throughout this spec, **build manifest** means the file the repository itself declares as the source of its canonical build and test commands (AGENTS.md or an equivalent the repository names). Tool cards specialize the practice for their ecosystem; they never restate it.
- **Root-agnostic.** No repo names or absolute paths in any new card; canonical build/test commands are always sourced from the repo's declared build manifest; the infra carveout is phrased generically ("agent-deck infrastructure tooling is exempt"), replacing the defunct carveout's hardcoded paths.
- **Rulings adopted in session discussion, restated here as design decisions:** (a) the cards-only scoping governs the *knowledge implementation*; behavioral SCs still get `tests-v2` harness verification instruments because deck standards classify these rules as behavioral and grep/string evidence is an evidence-type mismatch (`#2249` precedent); (b) the defunct 082 corpus splits at the deck boundary — typing, pathlib, f-strings, print discipline, and the DI pin are deck-level; the pipeline-rerun constraint and DB enum-mapping rule are project-local and stay in project AGENTS.md files, not the deck; (c) the currency pass over the restored packages list, including the `dependency-injector` maintenance-status check.

## 2. Not Included

- **maven, npm, cargo, dotnet cards** — the taxonomy admits them on the same evidence terms; not in the developer's named set.
- **Separate top-level cards for `uv`, `pyproject`, or `dependency-injection`** — they are detail cards under `python` and `programming-principles` respectively, per the containment rule and the consolidation directive.
- **GDScript conventions as a separate card** — `godot` carries engine + build/run; a language split awaits observed failure.
- **routing.md or floor.md edits** — new cards register through their descriptions; the floor is untouched.
- **Revival of the defunct guidelines corpus** — the cards-only approach replaces it; retired guidelines stay in `attic/`.
- **Project-local rules** — the defunct 082 pipeline-rerun constraint and DB enum-mapping rule belong in project AGENTS.md files, not the deck.
- **A speculative industry-practices corpus** — `references/practices.md` starts with the stated expectation (semver discipline) and the defunct-provenance backward-compatibility/deprecation rules (`087-no-backward-compat`); further practices grow evidence-gated.
- **Per-change shallow checkout for changes that do not affect build configuration or packaging** — the practice triggers on build-affecting changes; the full pristine-tree gate remains once-per-release in `release-promoter`.
- **Changes to `tests-v2` harness mechanics** — scenarios are added under the existing contract; the harness *scripts* are not modified. (R-15's §14 edit is agent-facing mandate text in the harness spec — documentation, not mechanics.)
