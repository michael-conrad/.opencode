# SPEC — Restore build/run verification practice and the language/build-framework skill-card family

## 1. Intent and Executive Summary

### Problem Statement

Agent behavior regressed in three reported facets, all traced to one root cause (below):

1. **Build-verification practice lost.** The agent no longer verifies build-affecting changes by a shallow checkout into a temp folder, running the canonical build there, and asserting the final outputs (example for Gradle: `./gradlew shadowJar`, `./gradlew build` are not being run). The developer scoped the impact to **all build frameworks and languages**. Provenance that this practice existed and was retired: spec `.opencode#365` ("[SPEC] Release promotion verification gate — pinned-SHA build+test before tag", recovered from issue-store git history) was implemented as `.opencode#2439` — the release-promoter verification gate with behavioral SCs 1–6 (shallow temp-copy checkout, pinned submodule resolution, drift assertion, manifest-discovered build/test commands, build execution with BUILD_FAIL blocking promotion). The `#2490` re-rip moved the gated skill to `attic/` and stage 4e deleted the 2439 behavioral suite. The live `release-promoter` card (tag + GitHub Release + live-API verify) carries no gate; the live `implement` workflow demands only "an executed check" and lists build inside a conflated "structural | lint/typecheck/build commands" row — a weaker rule that admits both "build never run" and "outputs never inspected."

2. **shadowJar/SPI packaging knowledge absent.** The agent no longer configures shadowJar correctly — INCLUDE semantics and the SPI changes fat jars require (`mergeServiceFiles()` / `META-INF/services` preservation). Grep of the live deck and the attic returns zero hits for `shadowJar`/`mergeServiceFiles`: the live deck never carried this knowledge. The retired default prompt (`attic/prompts/default.txt`) additionally carried the habit "if the correct command is unknown, ask the user and suggest adding it to the parent repo's AGENTS.md or the appropriate submodule's AGENTS.md" — that habit died with the re-rip.

3. **Dependency-injection mandate missing.** `.opencode#2243` mandated a Python DI pin (`dependency-injector`); `.opencode#2249` generalized it to a generic multi-language mandate with a curated three-tier recommended-packages table (Clear standard / Contested / Guidance-only), selection guidance, an HTML/CSS exclusion, and behavioral enforcement tests. `#2429` demoted the content into `082-python-standards.md`, and the `#2490` re-rip retired the guidelines corpus to `attic/`. The live deck has zero DI content (grep: no hits in live skills).

### Root Cause / Motivation

The `#2490` deck re-rip ("lean corpus cut per developer direction") retired the pre-rip deck to `attic/` (tag `pre-rip`) and deleted the per-SC behavioral test suite. Retired with it: the release/build verification gate, its enforcement tests, the defunct guidelines corpus (including the DI mandate), and the default prompt's canonical-command habit. The live deck's replacement rules ("run the check; the output itself is the evidence"; "project-local lint/typecheck/build commands | cheap mechanical facts first") do not require a clean-tree build, do not require asserting final outputs, and carry no language-specific or build-framework knowledge. The regression is therefore not model drift — it is deck content retirement without equivalent replacement, now reported as live behavior.

### Approach Chosen

Restore the retired practice and knowledge as a **skill-card family under progressive disclosure**, per the developer's directives this session: multiple focused skill cards (a multi-concern card's body loads whole at dispatch, defeating progressive disclosure), lean bodies, detail cards one level deep in `references/`, and descriptions as the router. The change surface is **only skill cards and skill detail cards** (new cards created, existing cards updated); behavioral enforcement scenarios are produced as verification instruments under `tests-v2/AGENTS.md`, not as knowledge implementation.

New cards:

| Card | Type | Content source |
|---|---|---|
| `dependency-injection` | topic | restored from `#2249` (mandate + tier table) through a live currency pass |
| `java` | language | new (DI practice from `#2249` tier table; shadowJar-adjacent JVM knowledge) |
| `python` | language | restored from defunct `082-python-standards.md`, deck-level items only |
| `gradle` | build/run tool | new (shadowJar INCLUDE/SPI is the demonstrated failure) |
| `uv` | build/run tool | new (defunct deck held only scattered command fragments) |
| `pyproject` | config surface | new |
| `godot` | build/run tool | new (zero defunct-deck mentions) |

Updated cards: `implement` (workflow reference gains the build-verification row), `verify` (evidence bar extended), `release-promoter` (verification gate restored to the live card, gate detail card restored from `attic/skills/release-promoter/tasks/operating-protocol.md` and re-homed under `references/` per current card standards).

### Alternatives Considered & Why Discarded

- **One fat Java card carrying build toolchain + packaging + DI + code standards, with detail references.** Discarded per developer direction: the card's body loads whole at dispatch even when the task touches one concern; "multiple skill cards are more reliable with more properly focused content."
- **Java card plus separate Gradle card, with DI recommendations scattered into per-language detail cards.** Partially adopted (Gradle *is* a separate card), then corrected after re-evaluation: moving each language's recommended-packages row into its language card breaks cross-language coverage — the tier table names fourteen ecosystems, most of which have no language card (cards are evidence-gated), so the knowledge would be homeless. The canonical tier table stays whole in the `dependency-injection` card; language cards carry practice depth that presupposes the recommendation.
- **Restore the defunct guidelines corpus (082 et al.) as guidelines.** Discarded: the guidelines machinery is retired; the developer's directive is that implementation creates/updates only skill cards and skill detail cards.
- **Restore the `#2249` tier table verbatim.** Discarded: live-source verification found the defunct table carries drift (the Java row's "Dagger for GWT-style" does not match the verified Java landscape — Spring / Guice / Dagger 2, with GWT's historical DI story being Gin). A recommendations list that is wrong is worse than one that is absent; the table returns through a currency pass with structure and tier philosophy preserved.
- **Admit maven/npm/cargo/dotnet cards in this change.** Deferred: not in the developer's named set; the taxonomy admits them on the same evidence terms when failures demand them.

### Key Design Decisions

- **Card taxonomy:** language / build-run tool / config surface / topic. Grouping rule: a config format consumed by multiple tools earns its own card (`pyproject`); a single-tool config lives inside its tool's card (`build.gradle` inside `gradle`; `project.godot` inside `godot` — single-tool and overwhelmingly editor-generated).
- **Descriptions are the router.** Each description states domain framing and implementation framing (e.g. `gradle` catches "shadowJar", "fat jar", "build.gradle", "JVM build/packaging") and carries pairing pointers at description level only (`java` ↔ `gradle`; `python` ↔ `uv` ↔ `pyproject`). No routing.md edits; no cross-reference webs inside bodies.
- **DI layering:** the generic mandate ("use a DI approach," not "use framework X"), the canonical tier table, selection guidance, the HTML/CSS exclusion, and the infra-tooling carveout live in the `dependency-injection` card; `java` and `python` DI detail cards defer to it and carry practice depth only.
- **Build-verification placement:** the universal practice (shallow temp-copy checkout, canonical build from the repo's build manifest, final-outputs assertion) lives in the `implement` workflow reference, is demanded by the `verify` evidence bar, and is fully gated once per release in `release-promoter`. Tool cards specialize the practice for their ecosystem; they never restate it.
- **Root-agnostic:** no repo names or absolute paths in any new card; canonical build/test commands are always sourced from the repo's declared build manifest; the infra carveout is phrased generically ("agent-deck infrastructure tooling is exempt"), replacing the defunct carveout's hardcoded `.opencode/` paths.
- **Flagged for approval at the spec gate (adopted as stated leans, revise here if wrong):** (a) the developer's cards-only scoping is interpreted as governing the *knowledge implementation*; behavioral SCs still get `tests-v2` harness verification instruments because deck standards classify these rules as behavioral and grep/string evidence is an evidence-type mismatch (`#2249` precedent); (b) the defunct 082 corpus splits at the deck boundary — typing, pathlib, f-strings, print discipline, and the DI pin are deck-level; the pipeline-rerun constraint and DB enum-mapping rule are project-local and stay in project AGENTS.md files, not the deck; (c) the currency pass over the restored packages list, including the `dependency-injector` maintenance-status check.

### User Intent / Original Prompt

## 2. Not Included

- **maven, npm, cargo, dotnet cards** — the taxonomy admits them on the same evidence terms; not in the developer's named set.
- **GDScript conventions as a separate card** — `godot` carries engine + build/run; a language split awaits observed failure.
- **routing.md or floor.md edits** — new cards register through their descriptions; the floor is untouched.
- **Revival of the defunct guidelines corpus** — the cards-only approach replaces it; retired guidelines stay in `attic/`.
- **Project-local rules** — the defunct 082 pipeline-rerun constraint and DB enum-mapping rule belong in project AGENTS.md files, not the deck.
- **Per-change shallow checkout for changes that do not affect build configuration or packaging** — the practice triggers on build-affecting changes; the full pristine-tree gate remains once-per-release in `release-promoter`.
- **Changes to `tests-v2` harness mechanics** — scenarios are added under the existing contract; the harness itself is not modified.

## 4. Requirements

- **R-1. `dependency-injection` card.** Body states the generic mandate — approach problem solving and unit tests from the point of view of having an available DI approach of some worth, and use it rather than hand-rolling manual wiring where such an approach exists; the enforceable rule is "use a DI approach," not "use framework X." Body carries the full three-tier recommended-packages table (Clear standard / Contested / Guidance-only) restored from `#2249` and currency-passed per SC-14; selection guidance (choice driven by code analysis and spec requirements, never a fixed pin; combinations allowed where the table documents multiple idiomatic options); the HTML/CSS exclusion; the infra-tooling carveout phrased root-agnostically.
- **R-2. `java` card.** Lean body; detail card `references/dependency-injection.md` carries Java DI practice (Spring as clear standard, Dagger and Guice practice, constructor-injection patterns) deferring the mandate and tier classification to the canonical card; description pairs with `gradle`.
- **R-3. `python` card.** Lean body; `references/conventions.md` restores the deck-level defunct-082 items (typing with Pydantic/Dataclasses and 3.12+ built-in generics, pathlib exclusivity, f-strings, print-statement discipline); `references/dependency-injection.md` carries the `dependency-injector` pin (container-first pattern, no hand-rolled containers or module-level singletons) deferring to the canonical card; project-local defunct items excluded.
- **R-4. `gradle` card.** Body carries wrapper discipline (`./gradlew` over bare `gradle`) and canonical-command sourcing from the repo's build manifest; `references/packaging-spi.md` carries shadowJar INCLUDE semantics, `mergeServiceFiles()`/SPI preservation, and the fat-jar outputs verification (`META-INF/services` assertions); description catches "shadowJar", "fat jar", "build.gradle", "JVM build/packaging" and pairs with `java`.
- **R-5. `uv` card.** Body carries runner discipline (`uv run` over bare `python`/`pip`, project venv), `uv sync`/`uv add`/lockfile handling, canonical-command sourcing, and the Python-ecosystem specialization of the build-verification practice (sync → build → assert `dist/` outputs); description pairs with `python` and `pyproject`.
- **R-6. `pyproject` card.** Body carries pyproject.toml authoring: PEP 621 metadata, dependency declaration, build-backend selection, tool sections, entry points/scripts; does not teach uv operations (defer to `uv`).
- **R-7. `godot` card.** Body carries project structure (`project.godot`, scenes/resources), headless run/import (`godot --headless`), export presets, canonical-command sourcing; carries GDScript conventions only insofar as they are build/run-relevant until a separate card earns admission.
- **R-8. `implement` update.** The workflow reference's post-implementation section gains a build-verification row satisfying SC-1's mechanism, distinct from the conflated structural row it replaces (that row's build mention is retired into the new row — the net-zero disposition for this admission).
- **R-9. `verify` update.** The evidence demands for build-affecting changes include the build run output and the outputs assertion; the reviewer consumes them as executed evidence.
- **R-10. `release-promoter` update.** Description regains the verification-gate mention; the gate detail card is restored from `attic/skills/release-promoter/tasks/operating-protocol.md`, re-homed as `references/operating-protocol.md` under current card standards, preserving the SC-6 mechanism (shallow checkout at the release commit, pinned submodules, drift assertion, manifest-discovered build/test, once-per-release, promotion block).
- **R-11. Governance.** Every new/updated card passes the skill-creator admission gate: observed failure (this regression, three facets), consumer and trigger (descriptions), predicate classification (DI mandate: intent-decidable — judgment decides, no scripts; build-verification execution: fact-decidable at its boundary checks — the build ran, the outputs exist), domain match (the demonstrated failures), root-agnostic content, and the net-zero/what-it-replaces disposition (R-8 for the implement row; provenance-based restoration for the rest).
- **R-12. Implementation surface.** Only skill cards and skill detail cards are created or updated; behavioral enforcement scenarios are verification instruments produced under `tests-v2/AGENTS.md` (Two-SC artifact + clean-room pattern where applicable), not knowledge implementation; `floor.md`, `routing.md`, and the guidelines corpus are untouched.
- **R-13. Progressive-disclosure discipline.** Lean bodies; details one level deep in `references/`; no detail-card chains deeper than one level; pairing pointers at description level only.
- **R-14. Root-agnostic content.** No repository names or absolute paths in card content; canonical commands always sourced from the repo's declared build manifest; per-project specifics stay in project AGENTS.md files.
