# [SPEC] unify the review-audit loop: repeat-until-zero with semantic spin detection and diagnosis-driven escalation; retire the fixed one-re-review bound

## 1. Intent and Executive Summary

| # | Field | Description |
|---|-------|-------------|
| 1 | **Problem Statement** | The deck carries two conflicting loop-termination rules for review/audit cycles, discovered 2026-10-14 during the on-demand spec audit of `.opencode#2544` (the audit's dispatch path loads both surfaces). The `verify` card §4 FAIL path — *"Remediate → one re-review. Still failing → halt to the developer with the specific failing SCs, the root cause, and what is needed"* — plus its frontmatter description (*"FAIL → remediate → one re-review → still FAIL → halt to the developer… One verdict record; no artifact chains, no re-audit loops"*) and `routing.md`'s verify entry (*"single fresh-context reviewer, churn rule, bounded loop"*) bound the loop at exactly one re-review. The `validation-standards.md` Loop section (the #2601 restoration) — *"The revise → re-validate cycle repeats until a verdict with zero findings… Escalation to the developer fires only when the audit cannot reach a zero-finding verdict by revision"* — echoed by `spec` card §6 (*"the loop repeats until a verdict with zero findings, per the standards reference's loop section"*), repeats the cycle autonomously until zero findings. Same artifact type (a spec under audit — routing sends on-demand spec audits through `verify` while criteria invariance pins their criteria to validation-standards), two termination bars, neither text subordinates the other. The verify card is internally torn as well: §4 and the description deny a loop exists while §8's criteria-invariance machinery (*"Every audit and re-audit runs on the same declared criteria set… re-audit prompts restate it verbatim"*, *"Post-verdict notes and directives feed the loop's revision step"*) presumes one. An agent running a FAILing audit faces an undefined choice between halting after one failed re-review and looping autonomously until clean. |
| 2 | **Root Cause / Motivation** | The two rules entered the deck at different moments and were never reconciled. The one-re-review bound predates the #2490 re-rip restorations; the repeat-until-zero Loop semantics were (re)authored by the #2601 criteria-depth restoration (2026-10-13). #2597 explicitly deferred the dispatch-topology question (*"the single-fresh-context-reviewer model is the #2550 restoration's deliberate shape; this item restores the artifact-presence gate, not the dispatch topology"*), leaving the loop-count conflict standing. The conflict surfaced as a live problem on 2026-10-14 when the developer, observing the #2544 audit flow, named it directly and directed the resolution: the loop must exist and must perform semantic checking for "spinning." |
| 3 | **Approach Chosen** | One loop rule governs every review/audit cycle — spec validation, on-demand spec audit, deliverable verification: FAIL → genuine remediation of every named finding → fresh re-review → repeat until a zero-finding verdict. The fixed one-re-review bound is retired, subsumed by a **semantic spin condition**: each cycle, the agent running the loop judges — never a script — whether the loop is spinning: findings recurring or reshuffling without genuine resolution relative to the remediation performed. On spin, the loop halts to the developer carrying the specific findings, the suspected cause class(es), the root cause, and what is needed. The developer's enumerated cause classes — a spec conflict; a composite SC that needs breaking up; a spec too fat and needing splitting into multiple specs; atomic work unit violations; needed re-evaluation — are recorded in the validation-standards Loop section as judgment examples of what spinning usually indicates: exemplary and open ("and so forth"), never a closed checklist. Surfaces amended: `verify` card §4 (FAIL path restated to the unified loop + spin halt), `verify` frontmatter description (re-worded to the spin-bounded shape), `routing.md` verify entry ("bounded loop" wording updated), `validation-standards.md` Loop section (spin semantic + example classes + escalation content), deck-debt ledger #2534 (governance-decision entry recording the retirement). The `spec` card §6 already defers to the standards' loop section and inherits the amendment unchanged. All edits go through the skill-creator admission gate; this item is developer-directed (carve-out applies; the gate's content standards bind). |
| 4 | **Alternatives Considered & Why Discarded** | (a) Keep the one-re-review bound and subordinate the standards' loop to it — discarded: it defeats the convergence guarantee the #2601 restoration deliberately authored; an audit whose remediation is genuinely converging would halt prematurely and shift loop-resolution work onto the developer that the loop can resolve itself. (b) Keep the repeat-until-zero loop with no halt — discarded: unbounded autonomous looping is precisely the runaway the verify bound exists to prevent; the developer loses control over non-converging cycles. (c) Mechanical spin detection (re-review counters, finding-overlap thresholds, keyword checks) — discarded: intent-decidable rules are never scripted (floor safety); a counter cannot judge whether findings persist because remediation was fake or because the artifact carries a deeper defect the loop cannot fix. (d) Per-context loop rules (separate termination rules for spec validation vs deliverable verification) — discarded: two rules re-create the conflict one level down; the spin condition is artifact-agnostic and one rule governs all review cycles. |
| 5 | **Key Design Decisions** | (1) The fixed count retires; the spin condition subsumes its protective intent — a spinning loop halts early, a progressing loop continues; no runaway, no premature halt. (2) Spin detection is intent-decidable — never mechanical; the deck's founding defect is scripted checks on judgment. (3) The spin judgment belongs to the agent running the loop (orchestrator side), which compares verdicts across cycles; each cycle's fresh-context reviewer judges only the artifact in front of it and has no cross-cycle visibility by design — the reviewer role is unchanged. (4) The enumerated cause classes are exemplary and open-class; the developer's "and so forth" is normative — a closed checklist would be a scripted check on judgment. (5) One mechanism, two statements (the #2597 pattern): the verify card states the loop and the spin halt in dispatch voice; the validation-standards Loop section states the full semantic with the example classes in criteria voice; no duplicated procedure text. (6) The spin-halt escalation reuses the existing escalation content shape (specific findings, root cause, what is needed — already in verify §4 and the standards' Loop) and extends it with the suspected cause class(es). (7) Re-wording is in scope per the #2597 doctrine: the SCs bind the semantic elements each surface must state, not literal wording; any sentence whose meaning changes beyond this item's scope stays untouched. (8) The cause-class enumeration lives only in the validation-standards Loop (the spec-validation/audit context the developer's enumeration addresses); the verify card's spin halt stays generic — no code-audit cause classes were enumerated, and inventing them is scope creep. |
| 6 | **User Intent / Original Prompt** | "spec audit .opencode#2544" → audit prep loads both surfaces → developer: "the one re-review vs repeat are in conflict, this needs to be addressed as an additional SC in this spec. discuss." → resolution discussion → developer: "this can be filed as an additional spec per your recommendation. what is the resolution for the conflict? the revise/re-audit loop needs to exist, but it also needs to do semantic checking to determine if the revise/re-audit is 'spinning' in place, when this happens, that is usually caused by a spec conflict, composite SC that needs breaking up, the spec being too fat and needing splitting up into multiple specs, atomic work unit violations or neede re-evaluation, and so forth." |

## 2. Not Included

- **Changes to the criteria content itself** (defect classes, analysis families in validation-standards.md) — the bar's content is not the defect; the loop semantics are.
- **Mechanical or scripted spin detection** — counters, thresholds, keyword lists; intent-decidable by design (Alternative (c)).
- **Changes to the single-fresh-context-reviewer model** — each cycle's reviewer stays fresh-context; the spin judgment is orchestrator-side (Design Decision 3).
- **The attic DiMo dispatch topology** — stays retired (#2597 Alternative (a)).
- **Code-audit cause-class enumeration in the verify card** — none was given for the deliverable-verification context; inventing classes is scope creep (Design Decision 8).
- **Changes to the approval gate or the churn rule** — not the defect.
- **Edits to the `spec` card** — §6 already defers to the standards' loop section and inherits the amendment unchanged.
- **Edits to `floor.md`** — the floor's `remediate [and re-audit]` vocabulary entry already presumes the loop; no fixed count appears there.
