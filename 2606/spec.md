# [SPEC] unify the review-audit loop: repeat-until-zero with semantic spin detection and diagnosis-driven escalation; retire the fixed one-re-review bound

## 1. Intent and Executive Summary

| # | Field | Description |
|---|-------|-------------|
| 1 | **Problem Statement** | The deck carries conflicting loop-termination rules for review/audit cycles, discovered 2026-10-14 during the on-demand spec audit of `.opencode#2544` (the audit's dispatch path loads both surfaces). The `verify` card §4 FAIL path — *"Remediate → one re-review. Still failing → halt to the developer with the specific failing SCs, the root cause, and what is needed"* — plus its frontmatter description (*"FAIL → remediate → one re-review → still FAIL → halt to the developer… One verdict record; no artifact chains, no re-audit loops"*) and `routing.md`'s verify entry (*"single fresh-context reviewer, churn rule, bounded loop"*) bound the loop at exactly one re-review. The `validation-standards.md` Loop section (the #2601 restoration) — *"The revise → re-validate cycle repeats until a verdict with zero findings… Escalation to the developer fires only when the audit cannot reach a zero-finding verdict by revision"* — echoed by `spec` card §6 (*"the loop repeats until a verdict with zero findings, per the standards reference's loop section"*), repeats the cycle autonomously until zero findings. Same artifact type (a spec under audit — routing sends on-demand spec audits through `verify` while criteria invariance pins their criteria to validation-standards), two termination bars, neither text subordinates the other. The verify card is internally torn as well: §4 and the description deny a loop exists while §8's criteria-invariance machinery (*"Every audit and re-audit runs on the same declared criteria set… re-audit prompts restate it verbatim"*, *"Post-verdict notes and directives feed the loop's revision step"*) presumes one. An agent running a FAILing audit faces an undefined choice between halting after one failed re-review and looping autonomously until clean. The plan-validation path carries the same unreconciled semantics one level down: the `plan` card §7 defers to `plan-validation-standards.md`'s Loop section, whose escalation fires on a persistent finding with no spin judgment — so the unification must cover both validation-criteria references, or the conflict re-creates itself between spec-side and plan-side loops. |
| 2 | **Root Cause / Motivation** | The rules entered the deck at different moments and were never reconciled. The one-re-review bound predates the #2490 re-rip restorations; the repeat-until-zero Loop semantics were (re)authored by the #2601 criteria-depth restoration (2026-10-13) for the spec side, with the plan side's `plan-validation-standards.md` Loop section carrying the same pre-amendment escalation shape. #2597 explicitly deferred the dispatch-topology question (*"the single-fresh-context-reviewer model is the #2550 restoration's deliberate shape; this item restores the artifact-presence gate, not the dispatch topology"*), leaving the loop-count conflict standing. The conflict surfaced as a live problem on 2026-10-14 when the developer, observing the #2544 audit flow, named it directly and directed the resolution: the loop must exist, must perform semantic checking for "spinning," and on spin must attempt higher-level fixing of the cause before escalating. |
| 3 | **Approach Chosen** | One loop rule governs every review/audit cycle — spec validation, on-demand spec audit, plan validation and audit, deliverable verification: FAIL → genuine remediation of every named finding → fresh re-review → repeat until a zero-finding verdict. The fixed one-re-review bound is retired, subsumed by a **semantic spin condition**: each cycle, the agent running the loop judges — never a script — whether the loop is spinning: findings recurring or reshuffling without genuine resolution relative to the remediation performed. On spin, the revision step moves up a level: the agent diagnoses the cause by judgment and attempts **higher-level fixing of the diagnosed cause** — artifact-level structural revision such as breaking up a composite SC, splitting an over-fat spec into multiple specs, resolving a spec conflict, restructuring into atomic work units, or re-evaluating the approach — using AI agent intelligence, never a scripted procedure; the loop then continues on the revised artifact. Escalation to the developer fires when spin persists after genuine higher-level fixing attempts, carrying the specific findings, the suspected cause class(es), the root cause, what was tried, and what is needed. The developer's enumerated cause classes — a spec conflict; a composite SC that needs breaking up; a spec too fat and needing splitting into multiple specs; atomic work unit violations; needed re-evaluation — are recorded in both validation-criteria Loop sections as judgment examples of what spinning usually indicates and of where the higher-level fixing aims: exemplary and open ("and so forth"), never a closed checklist. Surfaces amended: `verify` card §4 (FAIL path restated to the unified loop + two-stage spin response), `verify` frontmatter description (re-worded to the spin-bounded shape), `routing.md` verify entry ("bounded loop" wording updated), `validation-standards.md` Loop section (spin semantic + example classes + attempt-before-escalate escalation, spec voice), `plan-validation-standards.md` Loop section (the same spin semantic, plan voice), deck-debt ledger #2534 (governance-decision entry recording the retirement). The `spec` card §6 and the `plan` card §7 already defer to their references' loop sections and inherit the amendment unchanged. All edits go through the skill-creator admission gate; this item is developer-directed (carve-out applies; the gate's content standards bind). |
| 4 | **Alternatives Considered & Why Discarded** | (a) Keep the one-re-review bound and subordinate the standards' loop to it — discarded: it defeats the convergence guarantee the #2601 restoration deliberately authored; an audit whose remediation is genuinely converging would halt prematurely and shift loop-resolution work onto the developer that the loop can resolve itself. (b) Keep the repeat-until-zero loop with no halt — discarded: unbounded autonomous looping is precisely the runaway the verify bound exists to prevent; the developer loses control over non-converging cycles. (c) Mechanical spin detection (re-review counters, finding-overlap thresholds, keyword checks) — discarded: intent-decidable rules are never scripted (floor safety); a counter cannot judge whether findings persist because remediation was fake or because the artifact carries a deeper defect the loop cannot fix. (d) Per-context loop rules (separate termination rules for spec validation vs deliverable verification) — discarded: two rules re-create the conflict one level down; the spin condition is artifact-agnostic and one rule governs all review cycles. (e) Halt to the developer immediately on first spin detection — discarded: the developer directed that the agent first attempt higher-level fixing of the diagnosed cause using its intelligence; immediate escalation would delegate work the agent can perform itself and would surface every structural defect as a developer interrupt. (f) Amend only the spec-side reference and leave the plan-side `plan-validation-standards.md` Loop as-is — discarded: post-implementation the plan path would escalate immediately on a persistent finding while every other review cycle attempts higher-level fixing first — two escalation bars, the conflict re-created one level down in precisely the shape Alternative (d) discards. |
| 5 | **Key Design Decisions** | (1) The fixed count retires; the spin condition subsumes its protective intent — the two-stage response keeps the loop always terminating: it converges, or it escalates after genuine cause-level attempts; no runaway, no premature halt. (2) The spin response is two-stage — attempt before escalate: on spin, the agent first attempts higher-level fixing of the diagnosed cause (artifact-level structural revision guided by the cause classes), and escalation is reserved for spin persisting after genuine attempts. AI agent intelligence performs the diagnosis, the fixing, and the persistence judgment — no scripted procedure at any stage (developer direction, 2026-10-14). (3) Spin detection is intent-decidable — never mechanical; the deck's founding defect is scripted checks on judgment. (4) The spin judgment belongs to the agent running the loop (orchestrator side), comparing verdicts across cycles; each cycle's fresh-context reviewer judges only the artifact in front of it — the reviewer role is unchanged. The higher-level fixing is performed by the side that owns artifact revision in that loop (author for spec and plan artifacts, implementor for deliverables). (5) The enumerated cause classes are exemplary and open-class; the developer's "and so forth" is normative — they ground both the diagnosis and where the fixing aims; a closed checklist would be a scripted check on judgment. (6) One mechanism, statements per surface (the #2597 pattern): the verify card states the loop and the spin response in dispatch voice; each validation-criteria reference — the spec card's `validation-standards.md` and the plan card's `plan-validation-standards.md` — states the full semantic with the example classes in its own criteria voice; the `spec` and `plan` cards defer to their references; no duplicated procedure text. (7) The spin escalation reuses the existing escalation content shape (specific findings, root cause, what is needed) and extends it with the suspected cause class(es) and what was tried — the same five elements in every surface that states the escalation. (8) Re-wording is in scope per the #2597 doctrine: the SCs bind the semantic elements each surface must state, not literal wording; any sentence whose meaning changes beyond this item's scope stays untouched. (9) The cause-class enumeration lives in the validation-criteria references (the spec-validation/audit context the developer's enumeration addresses); the verify card's spin response stays generic — no code-audit cause classes were enumerated, and inventing them is scope creep. |

## 2. Not Included

- **Changes to the criteria content itself** (defect classes, analysis families in both validation-criteria references) — the bar's content is not the defect; the loop semantics are.
- **Mechanical or scripted spin detection** — counters, thresholds, keyword lists; intent-decidable by design (Alternative (c)).
- **A scripted upper bound on higher-level fixing attempts** (e.g., a fixed number of cause-fix iterations before escalation) — the persistence judgment is the bound; scripting it is a mechanical check on judgment.
- **Changes to the single-fresh-context-reviewer model** — each cycle's reviewer stays fresh-context; the spin judgment is orchestrator-side (Design Decision 4).
- **The attic DiMo dispatch topology** — stays retired (#2597 Alternative (a)).
- **Code-audit cause-class enumeration in the verify card** — none was given for the deliverable-verification context; inventing classes is scope creep (Design Decision 9).
- **Changes to the approval gate or the churn rule** — not the defect.
- **Edits to the `spec` card** — §6 already defers to its reference's loop section and inherits the amendment unchanged.
- **Edits to the `plan` card** — §7 already defers to its reference's loop section and inherits the amendment unchanged (same pattern as `spec` §6).
- **Edits to `floor.md`** — the floor's `remediate [and re-audit]` vocabulary entry already presumes the loop; no fixed count appears there.
