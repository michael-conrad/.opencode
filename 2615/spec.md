# [SPEC] PR body contract — closing-keyword mechanics, lean section format, submodule-bump description

Resolves `.opencode#2615`.

## 1. Intent and Executive Summary

| # | Field | Description |
|---|-------|-------------|
| 1 | **Problem Statement** | PR bodies across the repository family are inconsistent and defect-prone in three observed ways. (a) Malformed closing keywords: PR #2614's body used `Resolves .opencode#2461` — the deck's qualified `repo#N` form is not a GitHub closing keyword, so issue #2461 did not auto-close at merge and had to be closed manually in cleanup; a bare `#N` without a keyword no-ops identically. No card states the keyword mechanics, so every PR body improvises them. (b) Unbounded content quality: excellent bodies (.opencode#2608, #2611 — per-change what/why, real evidence) coexist with ritual-bloated bodies (opencode-config#370 — Verification Attestation / VbC table / DiMo Chain Attestation boilerplate marginalizing the actual content) and thin ones (opencode-config#368). The owning card's entire body guidance is one sentence. (c) Submodule bumps described worst: parent-repo PRs carrying pointer bumps say "pointer to 9a9d9cde" or "the corresponding commit" (opencode-config#370, release PR #362) — never what the bump delivers (which submodule PRs/issues) or its effect on the project. The owning card governs bump mechanics (pointer inclusion, no pointer-only PRs, ordering gate) but has no bump-description requirement. |
| 2 | **Root Cause / Motivation** | (a) The #2490 deck rip retired the pre-rip PR-body machinery (a closing-keywords reference and a body template) together with its ritual defects, and the replacement left the card with a single "Body" sentence — the mechanics were lost with the bloat, and form is now improvised per PR. (b) No section contract exists, so body quality is whatever the agent assembles; the variance spans excellent (#2608) to ritual-bloated (#370, written in the old template's ghost format) to thin (#368). (c) A bump-description requirement never existed in any era: the pre-rip card verified bump SHAs in release mode but no card ever required the parent PR body to describe the bump's content or effect — this is a new requirement, not a restoration. Motivation observed 2026-10-14: the developer reviewed recent PRs and named all three defects ("they don't properly close tickets… don't properly describe the PR's contents… don't properly describe what is in a submodule bump and how it effects the project"). |
| 3 | **Approach Chosen** | A binding PR-body contract owned by `git-workflow-pr`, plus closure-role and release-body alignment in three sibling cards — all in the `.opencode` submodule. **(1) `git-workflow-pr` §4 (Body)** becomes the contract. The format: `Closes #N` lines at body top (cross-repo: `Closes owner/repo#N`), then `## Summary` (2–4 sentences, executive voice, sourced from the authorizing spec/issue intent), optional `## Changes` (short bullets, omitted for single-purpose PRs), `## Evidence` (what actually ran and produced: test results with real numbers, fresh-context verify verdict, structural gates), `## Submodule bump` (only when the PR carries pointer bumps: per bump, old→new SHA, the submodule PRs/issues it delivers one line each, and the effect on the project), `## Provenance` (spec path, verify record), byline footer. Binding rules: uniform keyword `Closes` — no Fixes/Resolves roulette; `Refs #N` for references that must not auto-close; two prohibited forms — bare `#N` without a keyword, and the deck-qualified `repo#N` form in a keyword position; closing keywords auto-close the remote issue at default-branch merge (empirically confirmed on this family — see §4), and cleanup verifies and syncs from that state; anti-bloat rule — no attestation boilerplate, evidence-taxonomy tables, or artifact-chain output; ~30-line size guard (release PRs exempt as changelog-bearing). **(2) `git-workflow-cleanup` §2** redefines post-merge closure as verify-and-sync: verify the remote closure state the keywords produced, then close/sync the local `.issues/` records; an issue already auto-closed is not closed again. **(3) `release-promoter`** states the release PR body composition (changelog + bump section; closes only when a release issue exists) and that the GitHub Release body stays changelog-only. **(4) `changelog-generator`** gains at most a one-line note aligning it with the release-PR body composition. All card edits are developer-directed (session 2026-10-14: design brainstormed and approved, "no cargo culting" ruling recorded); the skill-creator content standards bind — lean bodies, root-agnostic text, no always-loaded surface growth. |
| 4 | **Alternatives Considered & Why Discarded** | (a) Restore the pre-rip `pr-body-template.md` wholesale — discarded: it mandates the Verification Attestation / VbC / DiMo ritual that produced opencode-config#370, and the developer ruled "no cargo culting"; the new format is designed from the observed failures, not excavated. (b) Keep closure cleanup-owned only, keywords informational (the pre-rip architecture's actual choice) — discarded: GitHub auto-close is empirically confirmed working on this family's default-branch merges (§4), so it closes remote issues at merge time for free; cleanup-only closure leaves remote issues open whenever cleanup is deferred, which is the exact defect the developer named. (c) A per-keyword semantics table (`Fixes` vs `Closes` vs `Resolves` by issue type, as the pre-rip reference had) — discarded: the distinction is stylistic, not semantic; choice overhead is where malformed forms crept in; one uniform keyword is deterministic and grep-able. (d) A dedicated body-conformance audit sub-agent before submission (the pre-rip `pr-body-audit` task) — discarded: with a fixed section contract and the anti-bloat rule, body conformance is a full-card-read fact during the existing fresh-context verify; a second sub-agent is ceremony the change does not need. |
| 5 | **Key Design Decisions** | (1) Uniform `Closes` keyword everywhere — deterministic, mechanically checkable, no per-type selection. (2) `Refs #N` is the only sanctioned form for references the PR does not resolve — prevents accidental auto-close of linked-but-not-resolved issues. (3) GitHub closing keywords are the primary remote-closure mechanism; cleanup's role shifts from performing to verifying-and-syncing — the two mechanisms compose instead of duplicating. (4) The Submodule-bump section is conditional: required exactly when the PR carries pointer bumps, omitted otherwise — no padding in bump-free PRs. (5) Release PR body = changelog + bump section; the GitHub Release body stays changelog-only — two different artifacts with different readers. (6) Size guard ~30 lines with the release exemption — a tripwire against both improvisation drift and ritual bloat. (7) GitBucket closing-keyword support is unknown at spec time; it is confirmed empirically during implementation with a defined disposition (§4) — the card text states the per-platform mechanism as found, never assumed. (8) Predicate classification: keyword forms, prohibitions, section presence, and bump-section triggers are fact-decidable (mechanical checks on body text); summary sourcing quality (executive voice vs implementation narration) is intent-decidable — agent judgment decides, no script enforces prose quality. |
| 6 | **User Intent / Original Prompt** | Session 2026-10-14: "review the skill cards for creating PRs and Release PRs; the PR messages are not very good. They don't properly close tickets. They don't properly describe the PR's contents. They don't properly describe what is in a submodule bump and how it effects the project. brainstorm." → evidence gathered from live PR bodies; attic reviewed for the pre-rip format on request; "no cargo culting, what is the new recommended formatting and which skill cards need to be updated?" → format and four-card update set presented → "this is good. create the spec." |

## 2. Not Included

- **Any restoration of pre-rip template sections** (Verification Attestation, VbC table, DiMo Chain Attestation, Spec-Card-Mapped Commits) — the anti-bloat rule bans them by name; `attic/` stays unloaded reference.
- **Changes to the `gh-cli` or `gb-cli` cards** — they own command mechanics, not body composition; the gap is local to `git-workflow-pr` and its closure/release siblings.
- **Changes to GitBucket tooling** — if GitBucket lacks closing-keyword auto-close, the difference is stated in card text (§4 disposition); no code changes.
- **An automated PR-body linter** — the contract is enforced by the authoring agent under the card; a lint tool is ceremony for a mechanical surface the author controls.
- **Retroactive edits to already-merged PR bodies** — the contract binds future PRs; history stays as recorded.
- **The `.counter` store-file drift** (file present, referenced by no tool or card mechanism; repaired to store-max as hygiene during this spec's filing) — recorded here so it is not silently re-litigated; a spec-card cleanup is a separate item if the developer wants it.
