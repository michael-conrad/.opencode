# [SPEC] Harden the ragsync retrieval service launch path — client-death reaping, resource ceilings, host-memory admission, same-host serialization

## 1. Intent and Executive Summary

1. **Problem Statement** — The deck's default retrieval service, the `ragsync` MCP server (`jsbroks/ragsync-mcp`) launched per deployment via `uvx --with mcp<2 ragsync --config .opencode/ragsync-config.yaml`, has no lifecycle or resource governance in its launch path. On 2026-10-15 (≈09:13–12:18 EDT) this produced a host-endangering failure on the shared 62 GiB family build host: two clientless ragsync instances (for host repos `CrossrefAbstracts` and `SEC-Filings-Scraper`) survived their MCP clients' death for ~3 hours, ballooned to **39.4 GB and 21.7 GB RSS** (combined demanded footprint ≈ **117 GB** against 62 GiB physical and 127 Gi swap), drove **63 Gi of swap consumption (~57 Gi attributable)** with `kswapd0` continuously in `D` state and load average 47–53, and read a cumulative **≈2.7 TiB** over the window while orphaned, unwatched, and unbounded. Diagnosis took manual intervention; remediation required developer-ordered `SIGTERM` to all four processes (2× `uvx` wrappers, 2× `python ragsync`), which then exited cleanly within ~5 s. No observable data loss occurred (sub-GB writes; Chroma stores regenerable from source).
2. **Root Cause / Motivation** — Three interacting gaps, per the incident record's analysis: (1) **client-death survival** — stdio MCP servers have no parent-death detection; a clientless server that is busy (writes nothing to stdout) never hits EPIPE, the `uvx` wrapper layer enforces no lifecycle contract, and nothing reaps it; (2) **unbounded memory workload** — ragsync's chroma backend loads the full collection (`chroma.sqlite3` + HNSW `data_level0.bin`/`link_lists.bin`) into RAM with fastembed (`Qwen3-Embedding-0.6B-Q`), with no memory cap, no thread-pool cap (151/154 parallel threads observed), and no host-aware admission; (3) **no cross-repo concurrency guard on one host** — configs are per-repo and nothing serializes ragsync instances sharing a machine. Motivation to act now: the launch path that produced the incident is unchanged as of authoring (verified 2026-11-25: the registration in `.opencode/opencode.jsonc` is byte-for-byte the pre-incident pattern and no ragsync-related commit landed on trunk in the interim), and an unhardened instance of exactly this launch shape is in live use on the same host at authoring time (`/home/muksihs/git/snea-phonetics`, verified 2026-11-26 02:39 UTC: PPID-linked `uvx`→`python ragsync`, ~3.15 GB RSS, 90 threads after ~5 minutes) — a client death while that instance works reproduces the incident's first leg without any code change.
3. **Approach Chosen** — Fix the ragsync setup in place, entirely inside the deck-owned layer — four concrete changes to the setup surfaces, in implementation order: (1) **watchdog wrapper on the registered launch command** — `.opencode/opencode.jsonc`'s `mcp.ragsync.command` changes from the raw `uvx --with "mcp<2" ragsync --config .opencode/ragsync-config.yaml` line to a wrapper invocation that starts that exact command as its supervised child and reaps the whole tree on client death: a parent-death signal (Linux PR_SET_PDEATHSIG-class prctl) set on the server process plus a PPID-poll side loop carrying the documented reap deadline — belt-and-suspenders by design, since PDEATHSIG alone misses the parent-dies-before-prctl-sets-it window and PPID polling alone can lag — so a dead client terminates the wrapper and server with zero dependence on stdout/EPIPE (R-1); the registered command still ends at `--config .opencode/ragsync-config.yaml` (CON-5 co-location, R-8). (2) **resource ceilings in the co-located setup** — the wrapper/config pair carries a configured peak-memory-demand ceiling and a thread-pool cap applied to the supervised child; upstream ragsync/chroma/fastembed knobs where plan-time live verification confirms them, wrapper-level limit application otherwise and by default (R-2, R-3). (3) **host-memory admission gate in the wrapper** — below a configured free-memory threshold the tree refuses to start heavyweight work, in an observably-distinguishable state (R-4). (4) **same-host serialization** — a runtime lock in a user-owned runtime directory holds exactly one heavyweight reindex slot per host user (R-5). The same wrapper optionally carries the clientless idle/heartbeat self-reaper (R-6, SHOULD). Default-on (`enabled: true`) registration and the retrieval function itself are preserved — the fix governs the setup's workload, it does not retire the service. Consumers and surfaces the change reaches: every deck deployment's `ragsync` registration and config (edited in place), the family build host's co-tenants (protected by the admission gate and ceilings), retrieval users (function preserved per R-7), the upstream service (complementary, not gated), and deck docs referencing the service (updated to the hardened launch path).
4. **Alternatives Considered & Why Discarded** — (i) **Discard ragsync (retire the plugin)** — rejected: the service is the deck's adopted, documented default retrieval (`#2315` CON-1; floor-listed), load-bearing in live deployments (a consuming deployment ran an instance throughout this triage), and its only prior neighbor `srclight` is banned from re-registration (`#2315` CON-9) and cannot cover the multi-language corpora. The observed failure is operational governance (lifecycle + resource shape), not a correctness defect: retrieval results were correct, no data was lost, and every store in the incident was regenerable. Discard removes a working capability to avoid a defect the deck owns the layer to fix. (ii) **Globally disable ragsync pending hardening** — rejected: the admission gate plus serialization deliver the protection the disable would approximate; blanket disable trades away default retrieval. A per-deployment disable before hardening lands remains an operator choice on data-heavy deployments, outside this spec. (iii) **Bespoke replacement retrieval implementation** — rejected on standing adoption constraint (`#2315` CON-1: adopt-as-is; no bespoke RAG) and the minimal-change principle. (iv) **Upstream-only fix (patch `jsbroks/ragsync-mcp` and wait)** — rejected: the exposure is live between any upstream patch and its adoption; deck-owned wrapper/config controls take effect immediately and remain complementary to upstream work. (v) **Generalize lifecycle hardening to every registered stdio MCP service** (editor, the-notebook-mcp, ollama-web-search) — rejected for this spec: the observed failure is the ragsync heavy-reindex memory/workload shape; generalization is a possible future follow-on ticket, not this problem's fix.
5. **Key Design Decisions** — (a) Hardening lives in the deck-owned launch/configuration layer, never in ragsync's own code — no fork, no vendored server (`#2315` CON-1 alignment; owning that layer is what makes the fix immediate); tradeoff: accepted at decision (b) — wrapper-level bounding over native in-server tuning. (b) The fix commits to concrete deck-owned mechanisms — the watchdog wrapper, the admission gate, the host lock, and wrapper/config-applied ceilings; upstream knobs where plan-time confirmation finds them refine the implementation but are never a dependency — tradeoff: wrapper-level bounding is coarser than native in-server tuning would be, in exchange for a fix that cannot stall on upstream availability. (c) Serialization scope is **one heavyweight slot per host user** (user-runtime-directory lock shared across repos), matching the incident's cross-repo multiplication; tradeoff: two simultaneously-launched small-corpus instances serialize too, though their workloads would have been individually bounded by (b). (d) Clientless idle/heartbeat self-reap is SHOULD-level — the report marks it optional, and R-1's watchdog already reaps busy clientless servers, which is the expensive shape; tradeoff: idle-but-clientless servers may persist between watchdog deadline and idle timeout. (e) Registration stays default-on with the admission gate as the safe-start control; tradeoff: on a memory-saturated host a session starts degraded/no-RAG, which is exactly the honest best-effort continuation the standing adoption already defines (`#2315` CON-7 semantics).
6. **User Intent / Original Prompt** — Developer, 2026-11-25 (this session, verbatim): "triage .opencode#2624; this is a serious problem. do we need to discard attempting to use this plugin?" Operative remediation intent from the filed record itself (remote issue `michael-conrad/.opencode#2624`, filed from the 2026-10-15 incident, "Fix directions (triage input — not yet a spec)"): a parent-death watchdog in the MCP launch path; ragsync resource ceilings in deck config defaults (chroma collection memory cap or mmap-bounded index load, thread-pool cap, host-memory admission refusing to start or deferring indexing below a free-memory threshold); an instance serialization guard for same-host concurrency; optionally an idle/heartbeat timeout for clientless stdio MCP servers. The incident record also records developer-ordered `SIGTERM` remediation (2026-10-15) and marks the downstream Xvfb/`awaitConsoleIdle` defects as tracked in the doaj/NewsRxUI trackers (cross-ref only). Developer revision directive, 2026-11-25 (this session, verbatim): "revise the spec to fix the ragsync setup" — the concretization grounds for this artifact's §1.3 fix-target approach and the setup-surface-pinned R-1..R-6 wording.

## 2. Not Included

- **Retiring or replacing the adopted ragsync service** — the approach keeps ragsync (`Alternative (i)`); re-registering `srclight` stays prohibited under `#2315` CON-9 regardless.
- **Xvfb startup-budget resilience and the `awaitConsoleIdle` premature-idle race** — tracked in the doaj/NewsRxUI trackers (incident context cross-ref only, per the record's own boundary marking); they are not this deck's deliverables.
- **Changes to the other registered MCP services** (`editor`, `the-notebook-mcp`, `ollama-web-search`) — the observed failure is the ragsync workload shape; genericizing lifecycle hardening to all stdio services is a possible follow-on, not this change (`Alternative (v)`).
- **Modifying ragsync's own source, forking, or vendoring it into the deck** — hardening stays in the deck-owned launch/config layer (`#2315` CON-1).
- **Changing the corpus designation or include/exclude policy** — `#2315` §3.1/CON-8 designation authority is untouched; this spec adds lifecycle/resource governance only.
- **New model pinning (revisions, checksums) or offline/cache-path machinery** — `#2315` CON-7's name-only pin and caching-≠-pinning ruling stand untouched.
- **Filing the upstream issues or requiring upstream adoption** — upstream patches are complementary; this spec does not gate on them (`Alternative (iv)`).
- **Per-deployment disable policy for data-heavy consuming repos** — an operator choice outside this deck change (`Alternative (ii)`'s scope note).

## 3. Requirements

- **R-1 (SHALL)** — The deck's registered ragsync launch command SHALL route server startup through a configured wrapper that detects the death of its MCP client and terminates the entire server tree (wrapper and server processes), without requiring client-related stdout activity (no EPIPE dependence), within the wrapper's bounded reap deadline (documented parameter; default recorded at implementation time).
- **R-2 (SHALL)** — The ragsync service setup (co-located config + launch wrapper) SHALL bound the supervised instance's peak memory demand to a configured ceiling (deck default chosen and recorded with rationale at implementation time, sized above the embedding-model resident baseline), enforced through upstream configuration where plan-time live verification confirms a knob, and through wrapper-level limit application otherwise — the deck-owned path is the fix's default and does not depend on upstream.
- **R-3 (SHALL)** — The ragsync service setup SHALL cap the supervised instance's thread/worker count at a configured maximum (deck default recorded with rationale at implementation time), enforced through the same knob-or-wrapper contract as R-2.
- **R-4 (SHALL)** — The launch wrapper SHALL apply host-memory admission: when free host memory is below a configured threshold (deck default recorded with rationale at implementation time), it SHALL NOT admit heavyweight work — the reindex/HNSW index-construction workload class observed in the incident — whether by refusing startup or by entering without performing it, in an observably-distinguishable state.
- **R-5 (SHALL)** — The launch wrapper SHALL serialize heavyweight reindex work across ragsync instances on the same host: at most one instance performs heavyweight reindex/HNSW work at any instant, coordinated via a runtime lock in a user-owned runtime directory (XDG_RUNTIME_DIR-class), held only while the heavyweight work runs.
- **R-6 (SHOULD)** — The launch wrapper SHOULD provide a clientless idle/heartbeat reaper: a stdio server whose client is gone and which performs no work for a configured idle duration self-terminates.
- **R-7 (SHALL)** — Post-hardening the retrieval function SHALL be preserved: the registered service starts under the hardened launch path and answers retrieval queries against its designated corpora, within the service's documented startup envelope (`#2315` CON-7's honest best-effort semantics apply to unavailability).
- **R-8 (SHALL)** — The hardening SHALL preserve the standing co-location contract (`#2315` CON-5): the registered launch command continues to name `--config .opencode/ragsync-config.yaml` (any wrapper referencing the same co-located config path), with registration and the co-located configs (`ragsync-config.yaml`, and the wrapper's hardening config) edited in the same change's diff. The hardening defaults live in the wrapper's co-located hardening config, never in `ragsync-config.yaml` — upstream's schema validates that file with `extra="forbid"` and an added key crashes the server (verified 2026-11-26; SC-9 carries the check).

## 8. Cost Frame

- **SC-1 (client-death reaping)** — acting: one lifecycle fixture run (minutes, model cache warm); skipping: the incident's first leg — the clientless busy server — ships unverifiable, and the unbounded 3-hour orphan shape is a wrapper edge away from repeating on the shared build host.
- **SC-2 (memory ceiling)** — acting: one uncapped baseline sample plus one capped rerun of the fixture reindex; skipping: the peak-demand bound is asserted, not observed — the 117 GB-demand shape returns unmeasured.
- **SC-3 (thread-pool cap)** — acting: thread sampling during the SC-2 capped run (co-executed, near-zero marginal cost); skipping: unbounded thread growth (151/154 observed in the incident) recurs unnoticed under load.
- **SC-4 (admission fixture)** — acting: one launch with an inflated threshold (seconds, no indexing performed); skipping: the safe-start control is trust rather than evidence — the one gate that stops the overload shape.
- **SC-5 (serialization)** — acting: a two-instance fixture with overlap sampling; skipping: concurrent heavy work in different repos (the incident's exact multiplication) would re-thrash CPU/IO even with per-instance memory bounded.
- **SC-6/SC-7 (idle reaping pair)** — acting: two short fixture windows around the idle timeout; skipping: the SHOULD-level reaper ships either dead or false-positive-prone, and a false positive would reap live sessions — worse than not shipping it.
- **SC-8 (function preserved)** — acting: one MCP invocation of the hardened tree (seconds); skipping: a hardening regression that kills retrieval ships silently — the silent-regression shape the gap-analysis family names.
- **SC-9 (structural parse)** — acting: one parse + grep (seconds); skipping: the registration and the hardened defaults could drift apart silently — the exact co-location defect `#2315` CON-5 exists to prevent.

## 9. Edge Cases

| Category | Condition | Expected behavior / Resolution |
|----------|-----------|-------------------------------|
| Failure & recovery | Client dies before/during the MCP connect window (tree killed or client exits cold-start — the documented cold-load/connect-window race) | Reaping covers the wrapper phase, not only the warmed server; fixture for SC-1 exercises a client kill during startup at least once in the plan's verification set. |
| Failure & recovery | Client dies while watch-mode (inotify) is active and the server is stdout-idle | Reaping does not depend on stdout activity (R-1's no-EPIPE-dependence); the stdout-quiet busy fixture for SC-1 covers the class; watch-idle coverage recorded in the plan's fixture matrix. |
| Input boundaries | Memory ceiling configured below the embedding-model resident baseline (~3.15 GB RSS observed warm) | Admission refuses rather than entering an unrunnable bounded state; the recorded default sits above the baseline; the SC-2 fixture's ceiling placement encodes the bound. |
| Failure & recovery | Admission threshold crossed by external host pressure (kswapd0 from non-ragsync workloads, as observed in the incident window) | Admission re-evaluates live free memory per launch/defer-cycle — it never latches a permanent refusal; the state is observable per SC-4's distinguishability ground. |
| Concurrency (deliverable-owned) | Two instances launched simultaneously on one host by different repos (the incident's exact shape; observed live at authoring) | One heavyweight slot: serialized per R-5; lock acquisition must respect the client's connect window — a waiter that would exceed it surfaces the documented honest-unavailable state rather than wedging startup. |
| State transitions | SIGTERM/SIGKILL mid-reindex (interrupted run) | Chroma stores are regenerable (incident evidence); an interrupted run must leave the next start able to re-sync; lock must not outlive its holder's death (stale-lock takeover rule recorded at implementation). |
| Failure & recovery | Model cache cleared (cold load exceeds connect window — documented known constraint) | Post-hardening behavior preserves `#2315` CON-7 honest best-effort: failure surfaced, session continues without RAG; hardening must not add silent retry/restart machinery that masks it. |
