# Bound per-turn generation in behavioral runs — output-token cap and resume-on-cap-hit in the tests-v2 harness

## Summary

Six tier-2 behavioral runs for `.opencode#2639` SC-7 documented a recurring run-fatal shape: a single generation turn intermittently produces an unbounded reasoning block — 4,140–6,030 tokens over 8.5–19 minutes with no tool-call flush — and the run dies there, at a different position every run (turn 1, mid-pipeline turns, implementation dispatches). Two deck fixes shipped on the #2639 branch (bounded trunk-freshness verification; short-path inline default) each verified effective at their target surfaces, and the stall relocated rather than disappeared: the only invariant across all six stalls is the model generating unbounded output within one turn against the deck-heavy context. The fix is at the harness layer — bound per-turn output for behavioral runs via opencode's `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` runtime flag, which feeds `maxOutputTokens` of every assistant generation, composed with a resume-on-cap-hit step (`behavior_run()`) that continues a capped session via the §10.7 machinery. The model is unchanged; the runtime config bounds each turn the same way the bash-tool timeout bounds execution, and the resume keeps the run alive across the bound.

## Root cause

1. **Unbounded per-turn generation.** The seeded test environment sets no per-turn output bound; opencode's own session-level default ceiling is far above the turn sizes the harness's monitoring cadence assumes (~2,500-token completed turns are the observed norm per the attempt-4 diagnosis; healthy turns of 1,000–4,100 tokens were observed across the attempts), so a degenerate reasoning block can run for many minutes before anything observes it. Verified against both runtime binaries: `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` is parsed (positive-integer, optional) and flows into `maxOutputTokens` per generation (binary strings evidence, 2026-10-19).
2. **Relocating stall, constant mechanism.** The six #2639 attempts show the degenerate turn is not tied to any one deck surface (freshness verification, implementation dispatch, turn-1 opener all hosted it at least once). Deck-side fixes reduced the surfaces; the per-turn bound addresses the mechanism at its only invariant surface — the unbounded generation itself.
3. **A cap hit ends the session.** Attempt 7 of the SC-7 run (2026-10-19, under the cap): the capped turn ended with `finish: length` after truncated reasoning that issued no tool call, and opencode's agentic loop exited — the session ended cleanly (exit 0) with the scenario's goal unreached. Bounding the turn without resuming replaces the runaway death with an early clean exit; the cap alone does not keep the run alive, which is why the bound requires the R-4 resume composition.

- Degenerate turns observed (no tool-call flush, run killed): 22k flushed reasoning chars/0 tools/8.5 min (attempt 2); ~5,200 tokens/12 min (attempt 3 turn 1); ~6,030 tokens/19 min (attempt 4 turn 5); ~4,140 tokens/17 min dispatch (attempt 5); ~4,360 tokens/15 min (attempt 6 turn 3). Healthy completed turns for contrast: ~1,000 and ~1,900 tokens (attempt 6) and ~4,100 tokens (attempt 4 turn 1, which flushed 58 tool calls).
- Binary verification (2026-10-19), both runtime binaries: the host-tier binary (`.tools/opencode/opencode`, `--version` 1.18.3) shows `outputTokenMax:G("OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX")` and `maxOutputTokens:be.maxOutputTokens(e.model,e.flags.outputTokenMax)`; the Docker-tier binary the six failure runs actually executed (`tests-v2-test-agent` image, opencode 1.19.0 at `/usr/local/bin/opencode`, version pinned by `Dockerfile.test-agent` `ARG OPENCODE_VERSION=1.19.0`) carries the identical wiring (`grep -oa` on the image binary, 2026-10-19).
- Attempt-7 record: the capped turn's final message carried `finish: length`, `output: 4000`, and the loop exited one second after the request returned — session end, not continuation.

## Approach

Set `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` (default 4000) for behavioral runs at every env surface the harness controls: the `with-test-home` `env -i` allowlist and its `set-env.sh` debug export (two surfaces, one file, as `${...:-4000}` — the harness's constant default with a parent-env override for probe runs), the Docker-tier `docker_env` passthrough in `docker-harness.sh` (literal 4000), and the §14 classifier-home seeder in `behaviors/helpers.sh` (literal 4000). Document the cap in `tests-v2/AGENTS.md` (§5 infrastructure details and the §14/§17 monitoring context): a turn that hits the cap ends with a length finish and terminates cleanly — verified empirically on the host-tier 1.18.3 binary (2026-10-19): a harness smoke run under `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX=60` recorded `finish: "length"`, `output: 60`, and the CLI exited cleanly, without error or hang (test home DB, since removed). Attempt 7 (2026-10-19, Docker tier) then established what termination means in an agentic run: the truncated reasoning issues no tool call, opencode's loop treats the turn as the agent's final answer, and the session ends cleanly — so the cap composes with R-4's resume-on-cap-hit step, which is what continues the work; the Docker-tier 1.19.0 binary carries the identical plumbing (see Evidence), and this spec's SC-4/SC-5 verify the composed behavior on the tier the scenarios execute.

Compose the cap with a fact-decidable resume-on-cap-hit step in `behavior_run()` for monitored runs: after a monitored model run exits, if the session's last assistant message carries `finish: length` (the cap fired), the harness resumes that session via the §10.7 machinery (`with-test-home --resume-home <home> opencode run --continue`, same test home), bounded by a resume ceiling so capped-turn → resume cycles cannot loop forever. The resume is placed after the determination record (and, on the halt-class path, the orchestrator decision) exists, because the §10.7 SC-8 determination gate refuses a resume whose home has no non-undetermined determination (observed: all three attempt-7-probe-era resumes FATAL'd "determination.yaml not found" when the resume ran before the record was written). Unmonitored runs are out of the resume path: their capped session ends and the evidence is exported (the §14 mandate requires orchestrated SC-verification runs to launch monitored). Each resumed run's events land in the same session store, and the exported `session.yaml` covers the full exchange. A dedicated probe scenario exercises the resume path deterministically (cap overridden small for that probe only), giving SC-5 its runtime instrument without waiting for an ordinary run to hit the cap.

4,000 tokens sits at the boundary of the observed healthy-turn range (1,000–4,100) and below the smallest degenerate turn (4,140): a legitimate 4,100-token turn is split into two turns rather than lost, and every degenerate shape observed is hard-bounded. No isolation contract change: the env allowlist gains one entry, not a credential.

Predicate classification (skill-creator admission gate #4): fact-decidable — the cap's presence and value are file/env facts; the resume trigger (last assistant `finish: length`) is a store fact a script may read; a script may assert them. The cap's adequacy for a given scenario remains judgment (§17), never scripted. Cadence compliance (R-5) is judged from recorded timestamps — fact-decidable on the record.

Governance posture (admission gate): observed failure = the six #2639 run records plus attempt 7's cap-hit session-end (D1's fix directive + D2's stacking directive + D3's cadence direction); consumer = every behavioral run through `behavior_run`/`with-test-home`; mechanism/trigger = existing harness load paths, unchanged; domain match = the failure is from this harness's own runs; root-agnostic = the amendment names no repo or absolute paths beyond the harness's own; what-it-replaces = the cap replaces opencode's implicit session-level default ceiling with an explicit harness-chosen bound — a bounded default displacing an effectively unbounded one.

## Requirements

- R-1. The behavioral-run environment SHALL set `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` to a default of 4000 at every surface the harness controls — five surfaces across three files: the `with-test-home` `env -i` allowlist and its `set-env.sh` debug export (both in `with-test-home`, as `${OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX:-4000}` — the harness's constant default with a parent-env override for probe runs), the Docker-tier `docker_env` passthroughs in `docker-harness.sh` (literal 4000 — two surfaces: the initial-run launch and the R-4 resume launch, each a distinct container run carrying its own env), and the §14 classifier-home seeder in `behaviors/helpers.sh` (literal 4000). Every ordinary behavioral run executes with 4000; only a deliberate probe overrides it.
- R-2. `tests-v2/AGENTS.md` SHALL document the cap in the infrastructure-details section: what it bounds (per-generation output, fed to `maxOutputTokens`), the value, the cap-hit behavior (clean length finish; in an agentic run the session ends there — truncation mid-reasoning issues no tool call) and the resume-on-cap-hit composition (R-4) that continues the work, and its relationship to the §14 supervision mandates (a cap hit is observed as normal turn cadence, not an abort signal).
- R-3. The change SHALL NOT alter the isolation contract (no credential passthrough, no new mount, no model substitution — `DEFAULT_TEST_MODEL` remains the single source of truth) and SHALL NOT alter the env allowlist beyond this one entry.
- R-4. `behavior_run()` SHALL resume a capped session when the run was monitored (`BEHAVIOR_SEMANTIC_MONITOR=1` — the orchestrated SC-verification norm): when a monitored model run exits and the session's last assistant message carries `finish: length`, the harness resumes that session via the §10.7 machinery (`--resume-home` + `opencode run --continue`, same test home) so the truncated turn continues. The §10.7 SC-8 determination gate governs permissibility — a monitored run writes its determination record on natural completion, and a non-undetermined record permits the resume; the §10.7 persistent undetermined-ceiling block composes with (is not replaced by) R-4's own ceiling. Resumption is bounded by that ceiling (default 3 resumed runs per attempt) beyond which the attempt ends and the evidence is exported for evaluation. Unmonitored runs are out of the resume path: their capped session ends and the evidence is exported (the §14 mandate requires orchestrated SC-verification runs to launch monitored). Each resumed run's events land in the same session store, and the exported `session.yaml` covers the full exchange. A dedicated probe scenario exercises the resume path deterministically (cap overridden small for that probe only), giving SC-5 its runtime instrument without waiting for an ordinary run to hit the cap.
- R-5. The behavioral evidence this spec produces SHALL include supervised-run cadence compliance: the supervisor's per-poll timestamps are recorded for every supervised run in this spec's verification, and the derived inter-poll intervals SHALL NOT exceed the 60-second ceiling of the Agent-Supervisor Mandate while a run is pending. A violation is a finding against SC-6 — recorded honestly, never rationalized.

## Impact

- **Consumers**: every behavioral run (tier-2 and tier-3) through `with-test-home`/`behavior_run`; the §14 monitor and supervisor observe bounded turn cadence.
- **Blast radius**: three harness files plus the harness spec documentation; no isolation change; no model change; no scenario script change (beyond the added probe).
- **Risk**: truncation — a turn that legitimately needs more than 4,000 output tokens is ended by the cap and the session resumes per R-4, so the work continues rather than dying; a resumed run re-enters with the full session context. The resume ceiling bounds worst-case cycles; ceiling exhaustion ends the attempt with evidence preserved for evaluation.
