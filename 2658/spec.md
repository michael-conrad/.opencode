# [SPEC] Closing-keyword mechanics — GitBucket platform fact, cross-repo form rule, merge-vs-close verification

Resolves `.opencode#2658`.

## 1. Intent and Executive Summary

| # | Field | Description |
|---|-------|-------------|
| 1 | **Problem Statement** | Two defects in the deck's closing-keyword contract, both live. (a) **False platform claim.** `git-workflow-pr` §4 states: *"Closing keywords auto-close the remote issue at default-branch merge on platforms that support it: GitHub confirmed for both forms; **GitBucket has no closing-keyword auto-close** — cleanup performs closure there."* That is false. Measured against GitBucket 4.48.0 (release WAR, in the tests-v2 self-contained container): the same-repo form **does** close the issue when the PR is merged into the repository's default branch — confirmed for `Closes`, `Fixes`, `Resolves`, `Close`, `CLOSES`, and comma-separated lists, and for a keyword carried in the PR title, the PR body, the merged commits' messages, or the merge message. The upstream parser is `extractCloseId` in `gitbucket/core/util/StringUtil.scala`; the merge path is `mergePullRequest` in `gitbucket/core/service/MergeService.scala` ("close issue by content of pull request"), reached both from the web UI and from the GitHub-compatible `PUT /api/v3/repos/{owner}/{repo}/pulls/{id}/merge`. Two boundaries hold on GitBucket: the cross-repo form `Closes owner/repo#N` closes **nothing** (the keyword parser requires whitespace immediately before `#`, so a qualified reference yields no issue id at all and the close lookup is never reached — §6.1), and a merge into a non-default base branch closes nothing — on GitBucket and on GitHub alike. (b) **Wrong form produced.** The card's prohibition names *"the deck-qualified `repo#N` form"* and says it *"closes nothing"* — but the form that closes a cross-repo reference on GitHub is `owner/repo#N`, which **contains** that banned substring (on GitBucket no cross-repo form closes — §6.1). The card never states the rule that decides the form (whether the referenced issue lives in the PR's own repository). Agents therefore write bodies whose closing markers do not close their targets: across nine observed instances, none shows the auto-close signature, and in five the target was already closed before the merge — so the merge closed nothing, and the delivered change is no longer tied to the ticket it resolves. **The dating of that evidence is stated in §6.3 and is load-bearing for what this spec claims: all nine instances predate the current card text, so they evidence what the absence of keyword guidance produces, not what the current wording produces.** The current wording's defects are established by reading the card, not by these instances. |
| 2 | **Root Cause / Motivation** | (a) The false claim was recorded by the #2615 implementation and generalized into card prose. The #2615 work record (`.issues/2615/plan.md:11-14`) states: *"disposable container (image `gitbucket/gitbucket:latest`), disposable repo/issue/PR — PR body carried `Closes #1`; **merge via API returned 200; issue stayed `state: open`.** Outcome: GitBucket has no closing-keyword auto-close → cleanup class."* **The record does not establish the operation it performed.** It says only *"merge via API returned 200; issue stayed `state: open`"*; no command, request, or response is recorded anywhere in the `#2615` folder or the issue store. The outcome it reports — HTTP 200 with the issue still open — is produced both by a close (`PATCH .../pulls/{n}` with `{"state":"closed"}`, GitHub's *close-PR* semantic, which on GitHub likewise produces no auto-close) and by a merge into a non-default branch, so the recorded outcome does not discriminate between them. A close on GitBucket 4.48.0 was reproduced and gives exactly the recorded outcome: HTTP 200, PR `state: closed`, issue `state: open` — the reproduction identifies an operation *consistent with* the record, not the operation the record performed. The probe also used `gitbucket/gitbucket:latest`, the image `tests-v2/AGENTS.md:929` records as a *"stale JDK8-base build"* that is *"never used or run"*. The consequence is not that the record is shown to be wrong but that it is **insufficient to establish a platform fact** — and a finding recorded on that basis did not deserve the status of a platform fact. (b) **The form-selection rule was never stated, and the prohibition collides with the correct form.** #2615 installed the *forms* (`Closes #N`, `Closes owner/repo#N`, `Refs #N`) and the *prohibitions* (bare `#N`, the deck-qualified `repo#N` form) but never the *decision rule* that maps a referenced issue to a form. The prohibition names the deck-qualified form — and the deck's own qualified form is `.opencode#N`, a substring of the correct `owner/.opencode#N` — so the wording meant to keep the qualified form out also reads as keeping the only cross-repo form that closes out. **The evidence for this root cause is the card's own text, not the historical instances**: before #2615 the card stated no keyword mechanics at all (§6.3 dates that), and every instance in §6.3 predates the current text, so the instances show what the *absence* of guidance produces, not what the current wording produces. Stating the rule is therefore a requirement to close a readable gap in the current card, and rewording the prohibition is a requirement to remove a readable collision — neither is a claim that the current wording has been observed producing a wrong form. (c) **The finding was known and unapplied.** A prior session's research card — `.issues/research-cards/gitbucket-closing-keyword-auto-close.md`, written 2026-10-23 09:52 and left uncommitted in the issues worktree — reached the same conclusion (GitBucket does auto-close; the cross-repo form and the non-default base branch are the two exceptions) from a 12-case matrix with source corroboration, and it was never committed, never carried into a card edit, and never turned into a requirement. The finding existed; the deck did not carry it. |
| 3 | **Approach Chosen** | Correct the text in the three cards that own the mechanic, and correct the record that carries the false finding. No new gate, no new workflow, no new test, no change to GitBucket. (1) `git-workflow-pr` §4: replace the false class claim with the per-platform/per-form statement; add the form-selection rule; reword the prohibition so it bans the owner-less qualified form while preserving the owner-qualified form; state that the developer's merge is what fires the close. (2) `git-workflow-cleanup` item 1: distinguish a closed PR from a merged one. Item 3: name the cases the keywords leave open (a cross-repo reference on GitBucket; a merge into a non-default base branch) and which of them the workflow closes, and replace the item's vestigial binary-class wording with a pointer to the per-(platform × form) statement in `git-workflow-pr` §4. (3) `gb-cli` §4: state the human merge gate, that `PATCH .../pulls/{n}` with `state: closed` closes without merging and produces no closing-keyword closure, and that GitBucket's issue API reports `state` but not `closed_at`. The two cross-card pointers the change introduces use the deck's canonical `Read [Text](path)` form, and each edited card carries the `.opencode#2658` anchor in both provenance surfaces. (4) `.issues/2615/plan.md`: state what the probe did and did not establish — that it recorded an outcome without recording the operation that produced it, that the recorded outcome does not discriminate between a close and a merge into a non-default branch, and therefore that it does not establish a platform fact — together with the corrected platform finding. (5) `.issues/research-cards/gitbucket-closing-keyword-auto-close.md`: correct two statements in it — the GitBucket API v3 *does* expose pull-request create and merge endpoints (both verified), and the harness test repository's default branch is `main`, not `master`. Its finding, matrix, and source corroboration are retained unchanged. |
| 4 | **Alternatives Considered & Why Discarded** | (a) **Add a "discriminating probe" discipline clause to the operational cards** — discarded by the developer: the rule is process content and belongs in the process layer; the operational cards are loaded on every PR and every GitBucket contact, and the added paragraph is actionable by none of them there. The rule already exists in the process layer (`verify` §11 instrument capability; `plan-validation-standards` #5 and #12; `spec/references/validation-standards` #5), and adding a prose rule would not have caught the #2615 failure — the work record's recorded *outcome* was non-discriminating, so a reviewer reading the record could not have told what operation produced it, and no rule about how to phrase a record can repair that. (b) **Add a post-implementation gate to `implement`** — same objection, and it is inert at that hook: the false statement was written into the *plan* artifact, so by the time a post-implementation gate runs the sentence is already baked in. (c) **Add a `tests-v2` behavioral scenario that merges for real** — discarded by the developer as a new workflow, not a correction. (d) **State GitBucket's behaviour as a generic "depends on the platform" hedge** — discarded: the platform fact is knowable and now measured; a hedge reproduces the vagueness that produced the defect, and the two boundaries (cross-repo form, non-default base branch) are the specific facts an agent needs. (e) **Leave `gb-cli` untouched** — rejected because the card documents two ways to *close* a PR and never mentions that the merge is a human gate, nor that a close is not a merge. The consequence of that omission is that a closed pull request and a merged one are not distinguished, which is the confusion the #2615 record's non-discriminating outcome is an instance of — the record's outcome is what a close and a merge into a non-default branch have in common. (f) **Restore the pre-rip `attic/skills/git-workflow-pr/reference/closing-keywords.md`** — discarded: it is retired, GitHub-centric, and introduces the `Implements` keyword the uniform-`Closes` contract rejected. |
| 5 | **Key Design Decisions** | (1) **Correct the text; do not add a mechanism.** The change is a set of sentence replacements, plus the two provenance surfaces each edited card carries by the deck's uniform practice — net-zero in deck surface apart from a few lines in the `git-workflow-pr` §4 bullet, three sentences in `gb-cli` §4, one sentence in `git-workflow-cleanup` item 1, and the rewritten item 3 sentences. (2) **The class is per (platform × form), not per platform.** GitBucket is in the keyword-closure class for the same-repo form and outside it for the cross-repo form; the deck's previous binary platform class cannot express that. (3) **State the decision rule, not just the forms.** "The form follows whether the referenced issue lives in the PR's own repository" is the missing sentence; without it the prohibitions leave the choice underdetermined. (4) **Prohibition wording must distinguish owner-less from owner-qualified.** `repo#N` and `owner/repo#N` share a suffix, and the deck's own qualified form is a suffix of the correct cross-repo form. (5) **The merge is the developer's.** The floor's human-merge gate and `git-workflow-pr` §6 make the merge a human action; the card states this so the agent knows the close is not its act at that moment, and its duty at cleanup is to verify and sync. (6) **Closed is not merged.** A PR can carry `state: closed` without ever having merged — GitBucket's `PATCH .../pulls/{n}` with `state: closed` does exactly that, returning HTTP 200. `git-workflow-cleanup` item 1 must read the merge state, not the open/closed flag. (7) **No merge command enters the deck.** `gh pr merge` is listed in `gh-cli` §4's capability list; no card instructs the agent to use it, and none may. (8) **Predicate classification.** Every SC is fact-decidable: a full-card read of card text, a grep across `skills/`, or a read of the work record. Nothing in this change is intent-decidable. (9) **Root-agnostic.** The corrected text names forms (`#N`, `owner/repo#N`, `repo#N`) and platforms (GitHub, GitBucket) only — no repository name, no absolute path, no root-repo-specific string. |
| 6 | **User Intent / Original Prompt** | Session 2026-10-23: the developer reported that *the deck misleads the agent into concluding that GitBucket does not accept standard GitHub close markers in PRs*, that *this is erroneous*, and asked for a fix spec. Subsequent developer directives in the same session: the change is *correcting the false premise and any incorrect wording in any of the skill cards and deck docs*; *not implementing a new workflow*; *the agent is not allowed to merge PRs*; and — after a scoping question that the evidence already answered — *why are you asking me for answers about what you are analyzing*. The developer's stated operational symptom: *the agent is not formatting the PR bodies correctly to autoclose the issue tickets that need closing because it thinks the keyword closing won't work*. |

### 2.2 Surfaces deliberately untouched

- **Reference documents** — none. `git-workflow-pr`, `git-workflow-cleanup`, and `gb-cli` are single-`SKILL.md` cards with no `references/` directory; there is no level two to push detail into, and creating one for a paragraph would be net-negative (new file, new load). `skill-creator`'s "bodies stay lean; details go one level deep in `references/`" does not bite here because the additions are a few lines in existing bullets.
- **`skills/issues/`** — its closure content (§5 Closure, §6 ticket-state hygiene) governs *when* closure is authorized and local↔remote reconciliation, not platform closing-keyword mechanics. Those mechanics live where this change puts them: `git-workflow-pr` §4 (the forms, the platform classes, the closing lines) and `git-workflow-cleanup` item 3 (the workflow's closure and verification duty). `gb-cli` §5 carries only the non-interactive issue-state-change route (`?action=close`), not the closing-keyword semantics. `issues/references/sync-mirroring.md` governs store↔tracker status drift and carries no closing-keyword content.
- **`skills/release-promoter/`, `skills/changelog-generator/`** — no platform-class claims; `release-promoter` only composes the release PR body and mentions `Closes` lines.
- **`skills/gh-cli/`** — its `gh pr create/edit/view/merge` line is a capability listing, not an instruction; no card instructs the agent to merge.
- **`floor.md`, `guidelines/`, `AGENTS.md`, `README.md`, `CHANGELOG.md`** — swept; none asserts a GitBucket closing-keyword fact. The CHANGELOG never recorded #2615, so it carries no false premise.

### 2.3 Impact

Consumers: every agent that opens a pull request (the `git-workflow-pr` card loads on the PR boundary) and every agent that runs post-merge cleanup (the `git-workflow-cleanup` card).

The observed instances are the product of an era in which the deck stated **no closing-keyword mechanics at all** — before commit `7df0f45c` (2026-10-15T03:29:47Z) — and every one of them predates the current card text (§6.3). What they show is the cost of that absence. In **five** of the nine (#358, #341, #276, #133, #286) a target was already closed before the merge: the merge closed nothing, and the delivered change carries no closure linkage to the ticket it resolves. The pull requests do name their tickets — in the title and in the body's closing line — but the ticket's closure came from somewhere other than the merge, so the merge leaves no record of having resolved it. In **five** of the nine (#286, #142, #712, #104, #2614) a target was closed *after* the merge with no 1–2 second auto-close signature — 1 m 18 s, 19 m 11 s, 25 m 33 s, 5 h 32 m 58 s and 21 m 38 s after the merge, the closing account being the one that files and merges in the repository. Those are compensating closes: the ticket was closed by hand because the merge did not close it. #286 appears in both groups because it names two targets that closed on either side of its merge; #133's remaining targets closed fifteen days later, which is later work rather than a compensating close.

**These instances are not the cost of the current text, and this spec does not attribute them to it.** The live, prospective cost of the current text is a different thing, established by measurement rather than by history: the false platform claim (§6.1) tells an agent that the keyword does not close, so an agent working on a GitBucket-hosted repository issues a redundant close against a ticket the merge already closed — and `gb issue close` falls back to the web UI and **hard-fails** in any non-interactive context (exit 1, "not a terminal"), so the agent spends a failing action on a closed ticket and may read that failure as a closure problem rather than as the redundant action it is. The claim postdates all nine instances, and all nine are GitHub pull requests, so it cannot be their cause; it is the reason the same behaviour is expected to recur on GitBucket.

Blast radius: three cards, two issue-store records, no code, no test surface, no behavior change to any tool.

## 3. Requirements

- **R-1** — `git-workflow-pr` §4 SHALL state that closing keywords close the referenced issue when the PR is merged into the repository's default branch, and SHALL name which platform/form combinations close: GitHub for the same-repo and the cross-repo form, GitBucket for the same-repo form only.
- **R-2** — `git-workflow-pr` §4 SHALL state the form-selection rule: the form follows whether the referenced issue lives in the PR's own repository — same repository `Closes #N`, a different repository `Closes owner/repo#N`, always owner-qualified.
- **R-3** — `git-workflow-pr` §4 SHALL prohibit a `#N` reference carrying no closing keyword and the owner-less qualified form `repo#N`, and SHALL state that the owner-qualified form `owner/repo#N` is a distinct form that closes on GitHub, while pointing at the cases a cross-repo reference cannot close by keyword. That pointer SHALL use the deck's canonical agent-facing cross-reference form, `Read [Text](path)` with a deck-relative path, and SHALL be written so that `.opencode/tools/reference-integrity` resolves it — `Read [the git-workflow-cleanup card](../git-workflow-cleanup/SKILL.md)` — and not as a bare `§N` or a bare file name. The bare-`§N` exclusion is enforced by the tool, which matches a link's text against the target file's headings and reports a link whose text names no heading in the target as broken; the bare-file-name exclusion is the `skill-creator` card's normative cross-reference rule, which the tool does not enforce (a file-level link passes the tool vacuously), so the criterion asserts the form directly.
- **R-4** — `git-workflow-pr` §4 SHALL state that the developer's merge is what fires the close, consistent with the human merge gate.
- **R-5** — `git-workflow-cleanup` item 1 SHALL distinguish a closed pull request from a merged one, requiring the merge state to be read rather than the PR's open/closed flag.
- **R-6** — `git-workflow-cleanup` item 3 SHALL name the two cases the closing keywords leave open, using terms that do not overlap — the cross-repo **form** `owner/repo#N` on GitBucket, where no cross-repo form closes, and a merge into a **non-default base branch**, where the keyword cannot fire at all — and SHALL state the precedence: the base-branch condition governs first, so when the merge did not land on the default branch the ticket's closure is outside the workflow's remit because the work has not landed there, and the cross-repo form on GitBucket is closed by the workflow when the merge did land on the default branch. The remit statement SHALL be scoped to **closure only** and SHALL NOT narrow the workflow's other duties (merge verification, branch deletion, trunk sync, work-state removal), which remain unqualified by branch. Item 3 SHALL **retain in substance the general fallback it currently carries** — that where the closing keywords do not close the issue, closure happens in the cleanup workflow or on explicit developer instruction — with the two named cases as its confirmed instances, so that the pre-change duty is preserved and not narrowed to an enumeration. It SHALL retain the rule that an issue the keywords already closed is not closed again.
- **R-7** — `gb-cli` §4 SHALL state that the merge is a human gate, that `PATCH .../pulls/{n}` with `state: closed` closes without merging and produces no closing-keyword closure, and that GitBucket's issue API reports `state` but not `closed_at`.
- **R-8** — The change SHALL introduce no instruction to merge a pull request, and the deck's existing human-merge-gate statements — `git-workflow-pr` §6 and `floor.md`'s `## Pipeline` section — SHALL remain in force and unmodified.
- **R-9** — The `.issues/2615/` work record SHALL state what its probe did and did not establish: that it recorded an outcome (HTTP 200, issue still open) without recording the operation that produced it, that the recorded outcome does not discriminate between a close and a merge into a non-default branch, and therefore that it does not establish a platform fact — together with the corrected platform finding measured in §6.1.
- **R-10** — The `.issues/research-cards/gitbucket-closing-keyword-auto-close.md` research card SHALL retain its **finding** and its **empirical matrix**, both of which are correct, and SHALL be corrected in four respects: the statement that the GitBucket API v3 has no pull-request create or merge endpoint (it has both); the harness test repository's default branch, named `master` where it is `main`; the directive that the merge must go through the GitBucket web form, replaced with the API v3 path the card then acknowledges exists; and the source-corroboration row's **mechanism** for the cross-repo form, which attributes it to the repository-scoping lookup — the lookup governs the bare form, while a qualified reference is rejected earlier, by the parser, because the pattern requires whitespace immediately before `#`.
- **R-11** — `git-workflow-cleanup` item 3 SHALL replace its whole vestigial binary-class wording — all three per-platform class phrases it currently carries: "on platforms that support it", "on platforms without closing-keyword support", and the parenthetical naming which platforms fall in which class — with a pointer to the per-(platform × form) statement in `git-workflow-pr` §4, since the change removes the binary class that wording describes. The replacement of the general fallback clause is governed by R-6, which requires it to be retained in substance. That pointer SHALL use the deck's canonical agent-facing cross-reference form, `Read [Text](path)` with a deck-relative path, and SHALL be written so that `.opencode/tools/reference-integrity` resolves it — `Read [the git-workflow-pr card](../git-workflow-pr/SKILL.md)` — and not as a bare `§N` or a bare file name.
- **R-12** — Each edited card SHALL carry the `.opencode#2658` anchor in its frontmatter `provenance:` line and in its `<!-- Provenance: … -->` comment, matching the deck's uniform practice on card edits.

Mechanism, read from upstream `gitbucket/gitbucket`: `src/main/scala/gitbucket/core/util/StringUtil.scala` `extractCloseId` matches `(?i)(?<!\w)(?:fix(?:e[sd])?|resolve[sd]?|close[sd]?)\s+#(\d+)(,\s?#(\d+))*(?!\w)` — a pure pattern over the message text, carrying no repository scoping of its own, and tolerating no colon. The repository scoping lives in `src/main/scala/gitbucket/core/service/IssuesService.scala` `closeIssuesFromMessage`, which runs `extractCloseId(message).flatMap { issueId => for (issue <- getIssue(owner, repository, issueId) if !issue.closed) yield … }` — the issue is looked up in the owner and repository it is handed, and `MergeService.mergePullRequest` hands it the pull request's own owner and repository, so a **bare** `#N` resolves only in the pull request's own repository. A **qualified** reference (`owner/repo#N`) never reaches that lookup at all: the pattern requires whitespace immediately before `#`, so a keyword followed by `owner/repo#N` yields no id — confirmed on GitBucket 4.48.0 by a pull request whose body carried `Closes <other-repo>#N` naming an issue that also existed in the pull request's own repository: that same-repository issue stayed open, so the qualified form is rejected by the parser, not by the lookup. `src/main/scala/gitbucket/core/service/MergeService.scala` `mergePullRequest` closes issues from the PR's title and body, the merged commits' messages, and the merge message, guarded by `if (pullRequest.branch == defaultBranch)`. `src/main/scala/gitbucket/core/controller/api/ApiPullRequestControllerBase.scala` routes `PUT /api/v3/repos/:owner/:repository/pulls/:id/merge` to the same service method as the web UI.

**The API v3 merge path is confirmed, not inferred.** Driven end-to-end with raw `curl` against the GitHub-compatible API and no CLI: `POST /api/v3/repos/root/t3/pulls` → HTTP 200, PR #2 created; `PUT /api/v3/repos/root/t3/pulls/2/merge` → HTTP 200, `{"merged":true}`, "Pull Request successfully merged"; the referenced issue then read `state: open` — the marker in that body was the colon form, which GitBucket does not accept. The `gb pr create` / `gb pr merge` CLI path was separately confirmed to reach the same endpoint and to fire the close (issue #1 closed at merge). This contradicts the research card's statement that the API v3 has no PR create or merge endpoint — see §6.7.

### 6.3 Observed instances of the failure

**The method.** Nine merged pull requests were examined in detail: for each, the body's closing-keyword lines were read, each referenced issue number was resolved against the pull request's own repository, and the target issue's `closed_at` was compared with the pull request's `merged_at`. A pull request is an *instance* when the marker in its body does not close its target — because the referenced number does not exist in the pull request's own repository, because the marker is the owner-less qualified form, or because the pull request merged into a branch other than the repository's default branch. **This is a sample, not a sweep**: no exhaustive enumeration of the family repositories' merged pull requests was performed, the table is what the examination of these nine found, and this spec makes no claim about how many further instances exist. The load-bearing claim is the mechanism below, which does not depend on the count.

**The auto-close signature.** GitHub closes an issue at the instant the merge lands. Four pull requests give the signature — each merged into `main`, the repository's default branch, each carrying the uniform `Closes #N` form, each with its target closing in one to two seconds:

| PR | merged | target closed | gap |
|---|---|---|---|
| `.opencode` #2621 | 2026-10-15T15:03:23Z | `#2617` at 15:03:25Z | 2 s |
| `.opencode` #2634 | 2026-10-17T13:38:32Z | `#1925` at 13:38:33Z | 1 s |
| `.opencode` #2638 | 2026-10-18T00:03:26Z | `#2635` at 00:03:27Z | 1 s |
| `.opencode` #2651 | 2026-10-21T04:39:27Z | `#2639` at 04:39:29Z | 2 s |

**What does not discriminate.** The `closed` timeline event's `source.issue` does **not** distinguish an auto-close from any other close: `.opencode#2617` — a known auto-close by the signature above — carries `source: null`, exactly as the instances below do. No inference about *who* or *how* an issue was closed may be drawn from that field. The causal test used instead is ordering, which needs no discriminator: a close that precedes its merge cannot have been caused by that merge.

**The mechanism.** A bare `#N` in a pull-request body resolves against the **pull request's own repository**. Parent-repository pull-request bodies carry bare markers naming two kinds of issue: those that exist in `michael-conrad/opencode-config` — which close correctly, because a bare marker is right when the issue is in the pull request's own repository — and those that name submodule issues, which do not exist in the parent repository and therefore resolve to nothing there. Every number named in the table below was queried against the parent repository and returned no such issue. The defect is therefore not that a bare marker is wrong in itself — it is that a bare marker is wrong **when the referenced issue lives in another repository**, which is the case the card never states.

### 6.7 GitBucket issue-API field surface

`GET /api/v3/repos/{owner}/{repo}/issues/{n}` returns `state: closed` with `closed_at` **absent** and `state_reason` **absent** — confirmed on every closed issue the probe produced. Closure verification therefore reads `state`; a reader expecting `closed_at` would see null on a closed issue.
