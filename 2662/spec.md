# [SPEC] Stakeholder-channel rule — the tracker-comment gate, the internal default, and the channel map

## 1. Intent and Executive Summary

| # | Field | Description |
|---|-------|-------------|
| 1 | **Problem Statement** | The live deck has no rule that keeps the agent's own working content off the remote issue tracker, and no card that names the route for an escalation, a clarification request, or a state update. The deck's only instruction on *when* to post a comment is `skills/issues/SKILL.md` §3: a remote comment is posted "only for a major substantive change that needs special attention — findings or decisions a stakeholder must see," with three exclusions (progress narration, internal reasoning, routine status) that "stay in chat or the local store." One further live instruction appends content to a tracker — `guidelines/deprecation-encounter-protocol.md` R-4: "Found → append the encounter evidence as a comment." The developer's observed failures are the agent's escalation reports, clarification requests, reasoning, chat and session-transcript excerpts, and pipeline-state updates. The gate's **predicate has no falsifier**: "needs special attention" and "must see" are satisfied by anything the agent finds interesting, so an escalation report and a clarification request each read as "a finding a stakeholder must see" and pass the gate. The exclusions reach one of the five classes (internal reasoning) and miss the other four; and none of the five has a stated route, so where the exclusion is not recognized the agent has nowhere else to put the content. The channel vacuum compounds it: the implementation-workflow reference says to "report the state, the blocker, and what is needed," the `verify` card says escalation "fires" to the developer, the `git-workflow-pr` card says "Notify and stop," the floor's standing formula says to halt with an open-ended clarification request — none names where the report goes, and the tracker is the surface that persists, is developer-visible, and already carries pipeline state. The deck already holds the governing principle and never applies it to the tracker: `skills/correspondence/SKILL.md` §1 states that internal findings, audit output, and raw progress "go to chat — never to stakeholder channels," and the card's description claims the decision surface — "when deciding whether content belongs in a stakeholder channel at all" — but no card ever names an issue comment as a stakeholder channel. |
| 2 | **Root Cause / Motivation** | Three causes, each traceable in the deck's own history. **(1) The rewrite replaced a procedure with a rewritten summary.** Pre-rewrite, `attic/skills/issue-operations-comments/tasks/comment.md` carried a caller-side gate — "This substantiveness gate MUST be evaluated by callers BEFORE the caller commits to posting… Callers must not assume posting is the default outcome" — a content-classification table ("HOW it was figured out → internal"; "Audit findings, verdicts → internal"; "Discussion responses → internal"; "Decision log entries → internal"), and a default under uncertainty: "Default to `internal` (conservative) when classification is uncertain… Internal content posted publicly cannot be retracted." The live `skills/issues/SKILL.md` §3 shares no sentence with that card: its positive clause is a rewritten summary ("a major substantive change that needs special attention"), its exclusions are three rewritten examples with a different destination ("chat or the local store"), and its third sentence is a rewritten routing rule. What the rewrite dropped is the procedure's substance — the classification, the default under uncertainty, the explicit route table, and the caller-side discipline. The live gate is a weak predicate plus three examples; the retired card was a decision procedure. **(2) The deck's channel vocabulary never covered the tracker.** The retired pre-rip surfaces carried the missing pieces: `attic/skills/issue-operations-comments/` (the classification), `attic/guidelines/045-open-questions.md` (the interview format), `attic/guidelines/141-planning-status-tracking.md` (the rule that specs and plans are not tracking documents and that progress lives in state files). What remains in the live deck names the tracker as a place to *file* an issue and as a place to *read* context, and nowhere as a place the agent publishes its own working content. **(3) The working content has no stated route per class.** `skills/work/SKILL.md` §4 makes the work record scratch — it lives in the repository's git directory and the cleanup card removes it. The live gate does name two destinations for content it will not post ("chat or the local store"), and the local store is durable: the `issues` card's operating contract states that the mutation commands auto-commit and auto-push to the `issues-data` branch, and the developer has confirmed the local store as an acceptable record. What is missing is not a durable surface but a **route per class** — the gate's destinations are informal, no card says that an escalation goes to chat, and the deck writes pipeline state to the tracker by a different route as well (remote labels, `skills/issues/SKILL.md` §2; recorded as out of scope in §2.2). For a class the gate does not name, the agent has no route, and the tracker is the route it finds. The deck's own store records the developer's ruling on this pattern in the other direction: `.opencode#2610` — "a ledger is a tracking tool, not tracked work; it does not belong in the issues system." |
| 3 | **Approach Chosen** | One rule, one home, no mechanism. The `correspondence` card is widened to own the **channel decision** — which surface a piece of agent-generated content belongs on, and in what form — and its description is widened to name every surface on which the agent publishes generated content, so the card is loaded at the moment the agent decides where content goes. The card's body gains the channel set (stakeholder surfaces against working surfaces), a **falsifiable** remote class (a stakeholder notice: content whose reader must take a specific action before the work can continue), the **named** internal class (the five observed failure classes, plus progress narration and audit and verification verdicts), the **default under uncertainty** (the working surface, with the asymmetry that decides the tie), the **route** for each class (chat for the live exchange; the local issue store for the record; the artifacts for the durable trace; the artifact edited in place for a correction), and the no-read-back rule (a tracker comment is never an answer, an authorization, or a record the agent reads back). `skills/issues/SKILL.md` §3 keeps a pointer to that rule and states the caller-side discipline the retired card carried — the gate is evaluated before the agent commits to posting, and posting is not the default outcome. Every escalation and clarification producer in the live deck states its route and its recipient (§2.1 and §2.2 hold the single inventory; R-8 binds the producers that carry a route), so the vacuum is closed at each producer and not only at the gate. The change adds **no script, no wrapper, no tool command, no classifier, and no threshold**: the rule is judgment. The pre-rip deck's scripted instruction surfaces are preserved in `attic/` after the #2490 rewrite, and the developer's ruling in this session is explicit — scripting produces decks that have to be trashed and replaced. |
| 4 | **Alternatives Considered & Why Discarded** | (a) **Widen `skills/issues/SKILL.md` §3 in place.** — Discarded: the `issues` card's description is the router for issue lifecycle operations, and a comment-posting decision is not an issue-lifecycle operation; a widened `issues` description becomes a routing magnet for every issue-adjacent task. The channel set the rule must name (issue comment, PR body, PR comment, wiki page, release note, correspondence) is not an issues concern. (b) **A new dedicated `issue-comment` card.** — Discarded: the deck then carries a card for one decision while `correspondence` already holds both the principle and the vocabulary, and the skill-creator admission gate's net-zero requirement prefers the reuse. (c) **A mechanical gate — a wrapper command that writes the local record and then posts.** — Discarded by developer directive, and on the merits: the agent in the reported situation is already rogue and would work around a wrapper, and the pre-rip deck's scripted surfaces are the decks that had to be trashed and replaced. (d) **A session hook that blocks the tracker-comment command.** — Discarded for the same reason, and because it adds a script to the deck to defend a surface the rogue agent would route around; the deck's answer to an agent that ignores its rules is a rule that is true, findable, and correct on its default path, not an interlock. (e) **A size or structure threshold on comment bodies.** — Discarded: size metrics are the deck's retired discipline, and a threshold is gameable by a threshold-shaped body. (f) **Ban remote issue comments entirely.** — Discarded: the developer accepted a tight positive class; a legitimate notice (a decision whose reader must take a specific action, such as a scope change that voids an authorization) needs a durable surface, and `.opencode#2661`'s R-5 notice is exactly that case. (g) **Name the five observed failure classes and stop there — a bare ban list.** — Discarded: a ban list leaves the predicate unbounded, and the live gate already fails that way — its positive clause admits the observed classes and its three exclusions miss four of the five. A rule that names the five inside a falsifiable predicate and a stated default answers both halves of the failure; a bare list answers only the half that was not the failure. (h) **State the route centrally in the channel rule and leave every producer untouched.** — Discarded: the escalation rule appears in three places — the two criteria-set files carry the same escalation paragraph, and the `verify` card's copy differs slightly — and a route stated in one copy and not the others leaves the deck stating one rule two ways: routed in one place, unrouted in two, with the spec-audit and plan-audit escalation paths exactly as exposed as before. The route is stated centrally *and* at each producer; the central statement keeps the rule one rule, the per-producer clauses keep it one way. |
| 5 | **Key Design Decisions** | (1) **The channel decision lives in `correspondence`, not in `issues`**: the deck's audience-separation principle already exists, and widening that card's reach is net-zero against the admission gate's replacement requirement, while `issues` keeps the operations it owns. (2) **The card owns the decision; the owning card owns the mechanics**: the channel rule decides *whether* content belongs on a surface; a surface's own card (`git-workflow-pr` for a PR body, `release-promoter` for a release note, `wiki-operations` for a wiki page) keeps the mechanics. The description says so, so a widened router does not create competing jurisdictions. (3) **The remote class is positive and falsifiable, not negative**: a tracker comment is a stakeholder notice — content whose reader must take a specific action before the work can continue — and the rule names the qualifying kinds. The pre-rip deck's falsifier ("needs to act on") is restored; the rewrite's weakening to "must see" is the defect. (4) **The default under uncertainty is the working surface, and the asymmetry decides the tie**: a notice can be added later; published narration cannot be withdrawn. This is the retired card's "default to internal" with its cost rationale, restored. (5) **The five observed classes are named inside the rule**, so the rule's coverage of the reported failures is legible on the card rather than inferred. (6) **Every producer states its route** — the rule alone leaves the vacuum open at the moment of escalation, which is where the reported failures occur. (7) **One rule, one home**: `skills/issues/SKILL.md` §3 becomes a pointer, not a second gate, so the two surfaces cannot drift. (8) **`floor.md` is untouched**: a substantive write to the floor triggers the ainglish discipline's whole-card-on-touch conversion of the entire floor's normative prose (`guidelines/ainglish-writing-discipline.md`, "Adoption rules"), and the channel decision is card-level content under the skill-creator card's always-loaded-surface discipline. (9) **PR comments follow the issue-comment gate; PR bodies do not**: the pre-rip deck exempted the PR body (a merge artifact) and held PR comments to the same rule as issue comments, and the live deck states neither. (10) **The amendment is larger than the ten targeted deltas**: the ainglish whole-card-on-touch rule brings each amended card's entire normative prose into scope, and the change's blast radius is stated accordingly in §2.3. (11) **The rule governs comments, not the tracker's other surfaces**: the `issues` card's label clause and ticket-state hygiene remain the `issues` card's business, and the rule says so, so the two surfaces do not classify the same content differently. (12) **One inventory, referenced everywhere**: §2.1 and §2.2 hold the single list of touched and covered surfaces, and the requirements, criteria, and evidence reference it rather than restating it, so the plan of record cannot drift from the scope. |
| 6 | **User Intent / Original Prompt** | The developer's directives, this session: review the deck — the agent has started posting useless comments to remote issue tickets ("escalations", "interview attempts", "chat dialog", "reasonings", "state tracking," and other commentary) which the developer deletes as nothing more than trash and noise; comments added to the local spec record are fine, while remote API issue tickets are considered wasteful, polluting, and confusing. Find the probable wording issues or rewrite loss in the skill cards, using the ainglish reference materials to identify problematic wording. Widen the `correspondence` description as much as seems allowable. No scripting: "scripting always results in trash decks that have to be trashed and replaced with new decks." On the residual risk of an agent that disregards the deck's rules: the reported agent is already rogue and will work tirelessly to bypass any scripting, so the fix is the rule text and the routing, not enforcement. Spec per the recommendations. |

- **`skills/plan/SKILL.md`** — the card carries no escalation or clarification producer; its loop's criteria-set copy is surface 6.
- **`skills/research/SKILL.md`** — §5 already routes findings to a local research card; the rule cites it as the pattern rather than restating it.
- **`skills/skill-creator/SKILL.md`** — its one open-ended question is a **producer** asked in the session (chat by construction); it produces no tracker-bound content.
- **`skills/explore/SKILL.md`** — its questions are a **producer** asked one per message in the session (chat by construction).
- **`skills/behavioral-testing/SKILL.md`** — its "ceremony escalation" is a verdict sense of the word, not a developer escalation; its supervision update is already bound to chat.
- **`skills/gh-cli/SKILL.md` and `skills/gb-cli/SKILL.md`** — the CLI cards carry mechanics, not judgment; naming the tracker-comment command there would widen the affordance the rule narrows.
- **`skills/git-workflow-pr/SKILL.md` §4** — the PR *body* contract's rule is unchanged; §6 is the only change to this card.
- **The criteria sets' content** — the defect classes, verdict contracts, analysis families, and loop mechanics of both validation-standards files are unchanged; only the escalation paragraph of each is amended (surfaces 5 and 6). The `skill-creator` admission gate and every other deck-governance rule are untouched.
- **`skills/issues/SKILL.md` §2's label clause and §6's ticket-state hygiene** — the live deck writes pipeline state to remote labels ("Title states the work; labels describe pipeline state," `skills/issues/SKILL.md` §2) and treats the remote tracker's state as the anchor for out-of-band changes. That is state tracking on the tracker by a different route, adjacent to the developer's reported "state tracking" class, and it is a separate question from the comment gate; the deck's recorded position on labels is `.opencode#1312` principle 2 (remote labels are advisory for stakeholders; local state is authoritative), and this spec does not re-litigate it. The channel rule states that these are the `issues` card's surfaces, outside its own scope, so the two rules classify the same content consistently. Recorded here so the adjacency is visible rather than silently ignored.
- **The `local-issues` tool** — no command added, changed, or deprecated. The rule names the existing `comment --type internal` and `update --status`/`--phase` commands as routes; the tool itself is not touched.
- **`tests-v2/`** — no new scenario script and no harness change, per the developer's no-scripting directive. The change's runtime effect is observed in the developer's review of the tracker, not asserted by a new script.
- **`.opencode#2661`'s spec** — its R-5 recomposition notice is a legitimate stakeholder notice under the new rule, and the rule's classification leaves it permitted. The change does not edit that spec.

### 2.3 Impact

- **Consumers.** Every agent session that touches a tracked issue — the deck's own issue pipeline, the repositories whose issues it works, and the developers who read those trackers. The change replaces the deck's only instruction on remote comments with a falsifiable predicate, a named internal class, a default, and routes.
- **Risk — over-suppression.** A legitimate stakeholder notice withheld. Bounded by the positive class (R-3), which names the qualifying kinds, and by the developer's own review of the tracker, which is where the notice would otherwise have been noise.
- **Risk — no enforcement.** A determined agent that disregards every card remains outside the deck's reach, by the developer's explicit direction. The change's effect rests on the rule being encountered, on the routes being stated at each producer, and on the default being the working surface.
- **Risk — a wider diff than the ten deltas.** The ainglish whole-card-on-touch rule brings each amended card's entire normative prose into scope: the `issues` card's eight items and its operating contract, the `work` card's seven items, the `verify` card's twelve items, the `implement` card's thirteen items, the `git-workflow-pr` card's six items, and the `correspondence` card's five. The conversion resolves ambiguity without changing substance (R-14); content defects the conversion surfaces are recorded rather than fixed (§5).
- **Blast radius.** The six amended cards' full normative prose, the three card-owned reference files, and the one guideline. No tool, harness, hook, or script surface changes; no data migration; nothing outside the deck is affected.

## 3. Requirements

- **R-1** — The `correspondence` card SHALL name the channel set: the stakeholder channels (an issue comment, a pull-request body, a pull-request comment, a wiki page, a release note, correspondence) and the working surfaces (chat, the local issue store, the artifacts under an issue's folder); SHALL state that the card owns the channel decision while the card owning a surface owns that surface's mechanics; and SHALL state that the issue tracker's labels and closure state are the `issues` card's surfaces, outside this rule's scope.
- **R-2** — The `correspondence` skill description SHALL name each of the six stakeholder channels enumerated in R-1 and chat, and SHALL state the decision the card owns; so that the card is loaded at the moment the agent chooses between a working surface and a stakeholder surface.
- **R-3** — The rule SHALL state the positive remote class with a falsifier: a remote issue comment is a stakeholder notice — content whose reader must take a specific action before the work can continue; and SHALL name the qualifying kinds (a decision, a scope change, a finding, a status the reader must act on) — those kinds being the ones outside the internal class named in R-4, so that no content is qualified by R-3 and forbidden by R-4.
- **R-4** — The rule SHALL name the content that never reaches a remote issue comment or a pull-request comment, and the named set SHALL include every observed failure class: escalation reports, clarification requests, the agent's reasoning, chat and session-transcript excerpts, and pipeline state — together with progress narration and audit and verification verdicts.
- **R-5** — The rule SHALL state that the default under uncertainty is the working surface, and SHALL state the asymmetry that decides the tie: a stakeholder notice can be added later, and published narration cannot be withdrawn.
- **R-6** — The rule SHALL name the route for each class: chat for a live exchange (an escalation, a clarification request), the local issue store for the record — naming both the `local-issues comment --number repo#N --type internal` command and the `local-issues update --number repo#N --status`/`--phase` state fields — the artifacts for the durable trace, and the artifact edited in place for a correction.
- **R-7** — The rule SHALL state that a tracker comment is never an answer, an authorization, or a record the agent reads back.
- **R-8** — Each producer listed in §2.1 as carrying a route SHALL state its route and its recipient — the developer, in chat. The producers are the `verify` card's escalation rule, the spec card's validation standards' escalation rule, the plan card's validation standards' escalation rule, the implementation-workflow reference's escalation rule, the `implement` card's narration-to-deliverable halt, the `work` card's closing halt clause, the `git-workflow-pr` card's terminal instruction, and the deprecation protocol's R-3 escalation. Each producer listed in §2.2 as covered already states its route — in the session, or by deferring to a surface this change amends.
- **R-9** — The `work` card's work-record rule SHALL state that the work record's contents never become a tracker comment, and SHALL name the local issue store and the artifacts as the durable destinations for the state it holds.
- **R-10** — The `issues` card's comment gate SHALL defer to the channel rule through the deck's canonical link form, SHALL state that the gate is evaluated before the agent commits to posting and that posting is not the default outcome, and the card's description SHALL no longer summarize the gate as a bar on progress narration only.
- **R-11** — The rule SHALL state that a pull-request comment follows the same gate as an issue comment; the `git-workflow-pr` card's PR-body rule continues to stand.
- **R-12** — The change SHALL add no script, no wrapper, no tool command, no classifier, and no size or count threshold.
- **R-13** — The change SHALL touch no file outside the surfaces listed in §2.1.
- **R-14** — Each amended card's full normative prose SHALL be returned under the ainglish writing discipline (`guidelines/ainglish-writing-discipline.md`), per that discipline's whole-card-on-touch rule — the card's entire normative prose written so the reader cannot misbind it, with the misbindings the conversion surfaces resolved — and each amended reference file's and the guideline's normative prose SHALL be returned under the discipline on touch. The conversion SHALL preserve the prose's substance, changing nothing beyond this spec's rules.
- **R-15** — The deprecation protocol's encounter-evidence append SHALL be routed to the ticket's store record rather than to a tracker comment, so that the protocol's evidence log does not create a second channel for working content.
- **R-16** — Each non-canonical cross-reference in an amended card SHALL convert to the canonical `Read [Text](path)` form, per the skill-creator card's forwards-only rule ("existing content converts when touched"): the `issues` card's remote-body-format reference, the `verify` card's two validation-standards references, the `implement` card's change-gate and deprecation-protocol references, and the `work` card's deprecation-protocol reference.

### 6.1 The live gate and the retired procedure

**The live gate.** `skills/issues/SKILL.md` §3, as of 2026-10-23, in full: *"A remote comment is posted only for a major substantive change that needs special attention — findings or decisions a stakeholder must see. Progress narration ("working on it", "halfway done"), internal reasoning, and routine status stay in chat or the local store. The `gb-cli` card shows the `gb issue comment` command once, as a command example, with no rule attached.

**The retired procedure.** `attic/skills/issue-operations-comments/tasks/comment.md` (preserved, tag `pre-rip`) carried the caller-side gate ("Callers must not assume posting is the default outcome"), the classification table ("HOW it was figured out → internal"; "Audit findings, verdicts → internal"; "Discussion responses → internal"; "Decision log entries → internal"), and the default ("Default to `internal` (conservative) when classification is uncertain… Internal content posted publicly cannot be retracted"). The live gate shares no sentence with that file.

`skills/spec/references/validation-standards.md` and `skills/plan/references/plan-validation-standards.md` carry the same escalation paragraph, byte for byte: *"Escalation to the developer fires when spin persists after genuine higher-level fixing attempts, or when the validation cannot reach a zero-finding verdict by revision. ### 6.4 The ainglish reading of the live gate

Against `guidelines/ainglish-writing-discipline.md`: the gate is passive with no named decision-maker (family 1, actor binding); "needs special attention" and "must see" are neither facts nor an assigned decision, and the deck never owns them (family 3, missing evidence vs unmade decision); the predicate carries no falsifier, and the pre-rip wording "needs to **act on**" was weakened to "must see," which a curiosity satisfies (family 4, claim confidence and falsifier anchoring); "chat or the local store" names two channels with no default, and "the local store" binds to neither of the deck's two stores (family 5, referent binding). The skill description compounds it by summarizing the gate as "non-substantive progress updates," so an agent that never loads the card believes the rule bans progress narration only.

### 6.5 The cross-references the touch converts

Six non-canonical cross-references sit in the amended cards as of 2026-10-23: `skills/issues/SKILL.md` (the remote-body-format reference), `skills/verify/SKILL.md` (the validation-standards and plan-validation-standards references), `skills/implement/SKILL.md` (the change-gate and deprecation-protocol references), and `skills/work/SKILL.md` (the deprecation-protocol reference). The skill-creator card's "Agent-facing cross-references" section requires the canonical `Read [Text](path)` form and states "Forwards-only: existing content converts when touched." The `reference-integrity` tool matches `Read\s+\[([^\]]+)\]\(([^)]+)\)` — it validates that canonical links resolve and cannot see a non-canonical form, so the conversion is checked by reading (SC-16).

### 6.6 The developer's own store records the same principle

`.opencode#2610`, filed from the deck-debt ledger the agent had created in the stakeholder-facing tracker: *"A ledger is a tracking tool, not tracked work; it does not belong in the issues system; the mechanism was never asked for."* `.opencode#1312`'s spec, "Eliminate GitHub Issue comment spam from pipeline skills," states the principles this deck's live cards no longer carry: comments are for stakeholder communication only; remote labels are advisory for stakeholders and state tracking is local; comments are never an authorization source; status, progress, phase-complete, and verification results go to the state file and chat.

### 6.7 The rogue-agent limit, stated

The developer reports that the agent in question is already rogue and would work tirelessly to bypass any scripting. This spec therefore assumes no enforcement: there is no interlock, no wrapper, and no classifier, and the deliverable is the rule text and the routing that makes the correct channel the path of least resistance. A determined agent that disregards every card is outside the deck's reach, and the developer's directive in this session is explicit: no scripting.
