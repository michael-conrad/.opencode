# [SPEC] Stakeholder-channel rule — the tracker-comment gate, the internal default, and the channel map

## 1. Intent and Executive Summary

| # | Field | Description |
|---|-------|-------------|
| 1 | **Problem Statement** | The live deck has no rule that keeps the agent's own working content off the remote issue tracker, and no card that names the route for an escalation, a clarification request, or a state update. The deck's only instruction on the matter is `skills/issues/SKILL.md` §3: a remote comment is posted "only for a major substantive change that needs special attention — findings or decisions a stakeholder must see," with three exclusions (progress narration, internal reasoning, routine status) that "stay in chat or the local store." The developer's observed failures are the agent's escalation reports, clarification requests, reasoning, chat and session-transcript excerpts, and pipeline-state updates. The gate's **predicate has no falsifier**: "needs special attention" and "must see" are satisfied by anything the agent finds interesting, so an escalation report and a clarification request each read as "a finding a stakeholder must see" and pass the gate. The exclusions reach one of the five classes (internal reasoning) and miss the other four; and none of the five has a stated route, so where the exclusion is not recognized the agent has nowhere else to put the content. The channel vacuum compounds it: `skills/implement/references/implementation-workflow.md` says to "report the state, the blocker, and what is needed"; `skills/verify/SKILL.md` §4 says escalation "fires" to the developer; `floor.md`'s standing formula says to halt with an open-ended clarification request — none names where the report goes, and the tracker is the surface that persists, is developer-visible, and already carries pipeline state. The deck already holds the governing principle and never applies it to the tracker: `skills/correspondence/SKILL.md` §1 states that internal findings, audit output, and raw progress "go to chat — never to stakeholder channels," and the card's description claims the decision surface — "when deciding whether content belongs in a stakeholder channel at all" — but no card ever names the issue tracker as a stakeholder channel. |
| 2 | **Root Cause / Motivation** | Three causes, each traceable in the deck's own history. **(1) The rewrite replaced a procedure with a rewritten summary.** Pre-rewrite, `attic/skills/issue-operations-comments/tasks/comment.md` carried a caller-side gate — "This substantiveness gate MUST be evaluated by callers BEFORE the caller commits to posting… Callers must not assume posting is the default outcome" — a content-classification table ("HOW it was figured out → internal"; "Audit findings, verdicts → internal"; "Discussion responses → internal"; "Decision log entries → internal"), and a default under uncertainty: "Default to `internal` (conservative) when classification is uncertain… Internal content posted publicly cannot be retracted." The live `skills/issues/SKILL.md` §3 shares no sentence with that card: its positive clause is a rewritten summary ("a major substantive change that needs special attention"), its exclusions are three rewritten examples with a different destination ("chat or the local store"), and its third sentence is a rewritten routing rule. What the rewrite dropped is the procedure's substance — the classification, the default under uncertainty, the explicit route table, and the caller-side discipline. The live gate is a weak predicate plus three examples; the retired card was a decision procedure. **(2) The deck's channel vocabulary never covered the tracker.** The retired pre-rip surfaces carried the missing pieces: `attic/skills/issue-operations-comments/` (the classification), `attic/guidelines/045-open-questions.md` (the interview format), `attic/guidelines/141-planning-status-tracking.md` (the rule that specs and plans are not tracking documents and that progress lives in state files). What remains in the live deck names the tracker as a place to *file* an issue and as a place to *read* context, and nowhere as a place the agent publishes its own working content. **(3) The working content has no stated route per class.** `skills/work/SKILL.md` §4 makes the work record scratch — it lives in the repository's git directory and the cleanup card removes it. The live gate does name two destinations for content it will not post ("chat or the local store"), and the local store is durable: the `issues` card's operating contract states that the mutation commands auto-commit and auto-push to the `issues-data` branch, and the developer has confirmed the local store as an acceptable record. What is missing is not a durable surface but a **route per class** — the gate's destinations are informal, no card says that an escalation goes to chat, and the deck writes pipeline state to the tracker by a different route as well (remote labels, `skills/issues/SKILL.md` §2; recorded as out of scope in §2.2). For a class the gate does not name, the agent has no route, and the tracker is the route it finds. The deck's own store records the developer's ruling on this pattern in the other direction: `.opencode#2610` — "a ledger is a tracking tool, not tracked work; it does not belong in the issues system." |
| 3 | **Approach Chosen** | One rule, one home, no mechanism. The `correspondence` card is widened to own the **channel decision** — which surface a piece of agent-generated content belongs on, and in what form — and its description is widened to name every surface on which the agent publishes generated content, so the card is loaded at the moment the agent decides where content goes. The card's body gains the channel set (stakeholder surfaces against working surfaces), a **falsifiable** remote class (a stakeholder notice: content whose reader must take a specific action before the work can continue), the **named** internal class (the five observed failure classes, plus progress narration and audit and verification verdicts), the **default under uncertainty** (the working surface, with the asymmetry that decides the tie), the **route** for each class (chat for the live exchange; the local issue store for the record; the artifacts for the durable trace; the artifact edited in place for a correction), and the no-read-back rule (a tracker comment is never an answer, an authorization, or a record the agent reads back). `skills/issues/SKILL.md` §3 keeps a pointer to that rule and states the caller-side discipline the retired card carried — the gate is evaluated before the agent commits to posting, and posting is not the default outcome. The escalation and notification producers — the implementation-workflow reference, the `verify` card, the `git-workflow-pr` card, and the `work` card — each state their route, so the vacuum is closed at each producer and not only at the gate. The change adds **no script, no wrapper, no tool command, no classifier, and no threshold**: the rule is judgment. The pre-rip deck's scripted instruction surfaces are preserved in `attic/` after the #2490 rewrite, and the developer's ruling in this session is explicit — scripting produces decks that have to be trashed and replaced. |
| 4 | **Alternatives Considered & Why Discarded** | (a) **Widen `skills/issues/SKILL.md` §3 in place.** — Discarded: the `issues` card's description is the router for issue lifecycle operations, and a comment-posting decision is not an issue-lifecycle operation; a widened `issues` description becomes a routing magnet for every issue-adjacent task. The channel set the rule must name (tracker, PR body, PR comment, wiki page, release note, correspondence) is not an issues concern. (b) **A new dedicated `issue-comment` card.** — Discarded: the deck then carries a card for one decision while `correspondence` already holds both the principle and the vocabulary, and the skill-creator admission gate's net-zero requirement prefers the reuse. (c) **A mechanical gate — a wrapper command that writes the local record and then posts.** — Discarded by developer directive, and on the merits: the agent in the reported situation is already rogue and would work around a wrapper, and the pre-rip deck's scripted surfaces are the decks that had to be trashed and replaced. (d) **A session hook that blocks the tracker-comment command.** — Discarded for the same reason, and because it adds a script to the deck to defend a surface the rogue agent would route around; the deck's answer to an agent that ignores its rules is a rule that is true, findable, and correct on its default path, not an interlock. (e) **A size or structure threshold on comment bodies.** — Discarded: size metrics are the deck's retired discipline, and a threshold is gameable by a threshold-shaped body. (f) **Ban remote issue comments entirely.** — Discarded: the developer accepted a tight positive class; a legitimate notice (a decision whose reader must take a specific action, such as a scope change that voids an authorization) needs a durable surface, and `.opencode#2661`'s R-5 notice is exactly that case. (g) **Name the five observed failure classes and stop there — a bare ban list.** — Discarded: a ban list leaves the predicate unbounded, and the live gate already fails that way — its positive clause admits the observed classes and its three exclusions miss four of the five. A rule that names the five inside a falsifiable predicate and a stated default answers both halves of the failure; a bare list answers only the half that was not the failure. |
| 5 | **Key Design Decisions** | (1) **The channel decision lives in `correspondence`, not in `issues`**: the deck's audience-separation principle already exists, and widening that card's reach is net-zero against the admission gate's replacement requirement, while `issues` keeps the operations it owns. (2) **The card owns the decision; the owning card owns the mechanics**: the channel rule decides *whether* content belongs on a surface; a surface's own card (`git-workflow-pr` for a PR body, `release-promoter` for a release note, `wiki-operations` for a wiki page) keeps the mechanics. The description says so, so a widened router does not create competing jurisdictions. (3) **The remote class is positive and falsifiable, not negative**: a tracker comment is a stakeholder notice — content whose reader must take a specific action before the work can continue — and the rule names the qualifying kinds. The pre-rip deck's falsifier ("needs to act on") is restored; the rewrite's weakening to "must see" is the defect. (4) **The default under uncertainty is the working surface, and the asymmetry decides the tie**: a notice can be added later; published narration cannot be withdrawn. This is the retired card's "default to internal" with its cost rationale, restored. (5) **The five observed classes are named inside the rule**, so the rule's coverage of the reported failures is legible on the card rather than inferred. (6) **Every producer states its route** — the rule alone leaves the vacuum open at the moment of escalation, which is where the reported failures occur. (7) **One rule, one home**: `skills/issues/SKILL.md` §3 becomes a pointer, not a second gate, so the two surfaces cannot drift. (8) **`floor.md` is untouched**: a substantive write to the floor triggers the ainglish discipline's whole-card-on-touch conversion of the entire floor's normative prose (`guidelines/ainglish-writing-discipline.md`, "Adoption rules"), and the channel decision is card-level content under the skill-creator card's always-loaded-surface discipline. (9) **PR comments follow the issue-comment gate; PR bodies do not**: the pre-rip deck exempted the PR body (a merge artifact) and held PR comments to the same rule as issue comments, and the live deck states neither. (10) **The amendment is larger than the six targeted deltas**: the ainglish whole-card-on-touch rule brings each amended card's entire normative prose into scope, and the change's blast radius is stated accordingly in §2.3. |
| 6 | **User Intent / Original Prompt** | The developer's directives, this session: review the deck — the agent has started posting useless comments to remote issue tickets ("escalations", "interview attempts", "chat dialog", "reasonings", "state tracking," and other commentary) which the developer deletes as nothing more than trash and noise; comments added to the local spec record are fine, while remote API issue tickets are considered wasteful, polluting, and confusing. Find the probable wording issues or rewrite loss in the skill cards, using the ainglish reference materials to identify problematic wording. Widen the `correspondence` description as much as seems allowable. No scripting: "scripting always results in trash decks that have to be trashed and replaced with new decks." On the residual risk of an agent that disregards the deck's rules: the reported agent is already rogue and will work tirelessly to bypass any scripting, so the fix is the rule text and the routing, not enforcement. Spec per the recommendations. |

## 2. Scope

### 2.1 Affected surfaces

| Surface | Change |
|---|---|
| `skills/correspondence/SKILL.md` — frontmatter description | The router, widened to name the surfaces on which the agent publishes generated content and the decision the card owns |
| `skills/correspondence/SKILL.md` — body | The channel set; the stakeholder-notice class; the internal class naming the observed failure classes; the default under uncertainty and its asymmetry; the route per class; the no-read-back rule; PR-comment parity. The card's existing format rules (§2 executive-summary format, §5 identity byline) are unchanged and continue to govern a tracker comment; the retired card's per-comment-type templates are not restored |
| `skills/issues/SKILL.md` §3 and description | §3 defers to the channel rule and states the caller-side discipline (gate evaluated before committing to post; posting is not the default); the description's summary of the gate is corrected |
| `skills/implement/references/implementation-workflow.md` — escalation rule | Names the route: the report to the developer goes to chat, not to the tracker |
| `skills/verify/SKILL.md` §4 — escalation rule | Names the route: escalation reaches the developer in chat |
| `skills/git-workflow-pr/SKILL.md` §6 — terminal instruction | "Notify and stop" names the medium: the developer is reported to in chat |
| `skills/work/SKILL.md` §4 — the work record | States that the work record's contents never become a tracker comment, and that durable state lives in the local issue store and the artifacts |

Six files, all in the `.opencode` submodule. The `local-issues` tool, the harness, and every script surface are untouched. The **extent** of the edit to each card is larger than the deltas above: under the ainglish discipline's whole-card-on-touch rule, each amended card's entire normative prose is returned under the discipline (R-14).

### 2.2 Surfaces deliberately untouched

- **`floor.md`** — a substantive write triggers the ainglish whole-card-on-touch conversion of the whole floor; the channel decision is card-level content under the skill-creator card's always-loaded-surface discipline.
- **`skills/spec/SKILL.md`** — §5 already states that spec content never lives in comments and that corrections edit the artifact in place.
- **`skills/research/SKILL.md`** — §5 already routes findings to a local research card; the rule cites it as the pattern rather than restating it.
- **`skills/gh-cli/SKILL.md` and `skills/gb-cli/SKILL.md`** — the CLI cards carry mechanics, not judgment; naming the tracker-comment command there would widen the affordance the rule narrows.
- **`skills/behavioral-testing/SKILL.md`** — its supervision update is already bound to chat.
- **`skills/git-workflow-pr/SKILL.md` §4** — the PR *body* contract is unchanged; §6's terminal instruction is the only change to this card.
- **`skills/issues/SKILL.md` §2's label clause and §6's ticket-state hygiene** — the live deck writes pipeline state to remote labels ("Title states the work; labels describe pipeline state," `skills/issues/SKILL.md` §2) and treats the remote tracker's state as the anchor for out-of-band changes. That is state tracking on the tracker by a different route, adjacent to the developer's reported "state tracking" class, and it is a separate question from the comment gate; the deck's recorded position on labels is `.opencode#1312` principle 2 (remote labels are advisory for stakeholders; local state is authoritative), and this spec does not re-litigate it. Recorded here so the adjacency is visible rather than silently ignored.
- **The `local-issues` tool** — no command added, changed, or deprecated. The rule names the existing `comment --type internal` and `update --status`/`--phase` commands as routes; the tool itself is not touched.
- **`tests-v2/`** — no new scenario script and no harness change, per the developer's no-scripting directive. The change's runtime effect is observed in the developer's review of the tracker, not asserted by a new script.
- **The criteria sets and the `skill-creator` admission gate.**
- **`.opencode#2661`'s spec** — its R-5 recomposition notice is a legitimate stakeholder notice under the new rule, and the rule's classification leaves it permitted. The change does not edit that spec.

### 2.3 Impact

- **Consumers.** Every agent session that touches a tracked issue — the deck's own issue pipeline, the repositories whose issues it works, and the developers who read those trackers. The change replaces the deck's only instruction on remote comments with a falsifiable predicate, a named internal class, a default, and routes.
- **Risk — over-suppression.** A legitimate stakeholder notice withheld. Bounded by the positive class (R-3), which names the qualifying kinds, and by the developer's own review of the tracker, which is where the notice would otherwise have been noise.
- **Risk — no enforcement.** A determined agent that disregards every card remains outside the deck's reach, by the developer's explicit direction. The change's effect rests on the rule being encountered, on the routes being stated at each producer, and on the default being the working surface.
- **Risk — a wider diff than the six deltas.** The ainglish whole-card-on-touch rule brings each amended card's entire normative prose into scope: the `issues` card's eight items and its operating contract, the `work` card's seven items, the `verify` card's twelve items, the `git-workflow-pr` card's six items, and the `correspondence` card. The conversion is a disambiguation pass and preserves the meaning of the prose it touches (R-14); it may surface further defects, which are recorded rather than fixed (§5).
- **Blast radius.** The five amended cards' full normative prose, plus the one reference file's escalation rule. No tool, harness, hook, or script surface changes; no data migration; nothing outside the deck is affected.

## 3. Requirements

- **R-1** — The `correspondence` card SHALL name the channel set: the stakeholder channels (the issue tracker, a pull-request body, a pull-request comment, a wiki page, a release note, correspondence) and the working surfaces (chat, the local issue store, the artifacts under an issue's folder); and SHALL state that the card owns the channel decision while the card owning a surface owns that surface's mechanics.
- **R-2** — The `correspondence` skill description SHALL name each of the six stakeholder channels enumerated in R-1 and chat, and SHALL state the decision the card owns; so that the card is loaded at the moment the agent chooses between a working surface and a stakeholder surface.
- **R-3** — The rule SHALL state the positive remote class with a falsifier: a remote issue comment is a stakeholder notice — content whose reader must take a specific action before the work can continue; and SHALL name the qualifying kinds (a decision, a scope change, a finding, a status the reader must act on).
- **R-4** — The rule SHALL name the content that never reaches the tracker, and the named set SHALL include every observed failure class: escalation reports, clarification requests, the agent's reasoning, chat and session-transcript excerpts, and pipeline state — together with progress narration and audit and verification verdicts.
- **R-5** — The rule SHALL state that the default under uncertainty is the working surface, and SHALL state the asymmetry that decides the tie: a stakeholder notice can be added later, and published narration cannot be withdrawn.
- **R-6** — The rule SHALL name the route for each class: chat for a live exchange (an escalation, a clarification request), the local issue store for the record (the `local-issues comment --number repo#N --type internal` command), the artifacts for the durable trace, and the artifact edited in place for a correction.
- **R-7** — The rule SHALL state that a tracker comment is never an answer, an authorization, or a record the agent reads back.
- **R-8** — Each of the three escalation and notification producers SHALL state its route and its recipient: the implementation-workflow reference's escalation rule, the `verify` card's escalation rule, and the `git-workflow-pr` card's terminal instruction. Each names the developer, in chat, as the recipient.
- **R-9** — The `work` card's work-record rule SHALL state that the work record's contents never become a tracker comment, and SHALL name the local issue store and the artifacts as the durable destinations for the state it holds.
- **R-10** — The `issues` card's comment gate SHALL defer to the channel rule through the deck's canonical link form, and SHALL state that the gate is evaluated before the agent commits to posting and that posting is not the default outcome.
- **R-11** — The rule SHALL state that a pull-request comment follows the same gate as an issue comment; a pull-request body continues to follow the `git-workflow-pr` contract.
- **R-12** — The change SHALL add no script, no wrapper, no tool command, no classifier, and no size or count threshold.
- **R-13** — The change SHALL touch no file outside the surfaces named in §2.1.
- **R-14** — Each amended card's full normative prose SHALL be returned under the ainglish writing discipline (`guidelines/ainglish-writing-discipline.md`), per that discipline's whole-card-on-touch rule, and the reference file's normative prose shall be returned under it on touch; the conversion SHALL preserve the meaning of the prose it touches, changing nothing beyond the rules this spec states.

## 6. Evidence

Progress narration ("working on it", "halfway done"), internal reasoning, and routine status stay in chat or the local store. Spec and plan corrections always edit the artifact in place — never route to comments."* A grep of the live deck's `skills/`, `guidelines/`, `floor.md`, and `docs/` returns no other card that instructs the agent *when* to post a comment; the `gb-cli` card shows the `gb issue comment` command once, as a command example, with no rule attached.

**The retired procedure.** `attic/skills/issue-operations-comments/tasks/comment.md` (preserved, tag `pre-rip`) carried the caller-side gate ("Callers must not assume posting is the default outcome"), the classification table ("HOW it was figured out → internal"; "Audit findings, verdicts → internal"; "Discussion responses → internal"; "Decision log entries → internal"), and the default ("Default to `internal` (conservative) when classification is uncertain… Internal content posted publicly cannot be retracted"). The live gate shares no sentence with that file.

**The vocabulary that survived without its application.** `skills/correspondence/SKILL.md` §1: *"Internal findings, audit output, and raw progress go to chat — never to stakeholder channels."* Its description already claims the decision: *"and when deciding whether content belongs in a stakeholder channel at all."* A grep for "stakeholder" across the live deck returns three files, none of which names the issue tracker as a stakeholder channel.

**The vacuum, quoted.** `skills/implement/references/implementation-workflow.md`: *"Escalation: any step that cannot complete honestly stops the cycle — report the state, the blocker, and what is needed; never fabricate a pass."* `skills/verify/SKILL.md` §4: *"Escalation to the developer fires when spin persists after genuine higher-level fixing attempts…"* `skills/git-workflow-pr/SKILL.md` §6: *"HALT after creation.
