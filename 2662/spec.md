# [SPEC] Stakeholder-channel rule — the tracker-comment gate, the internal default, and the channel map

## 1. Intent and Executive Summary

| # | Field | Description |
|---|-------|-------------|
| 1 | **Problem Statement** | The live deck has no rule that keeps the agent's own working content off the remote issue tracker, and no card that names the route for an escalation, a clarification request, a report to the developer, or a state update. The deck's only instruction on *when* to post a comment is `skills/issues/SKILL.md` §3: a remote comment is posted "only for a major substantive change that needs special attention — findings or decisions a stakeholder must see," with three exclusions (progress narration, internal reasoning, routine status) that "stay in chat or the local store." One further live instruction appends content to a tracker — `guidelines/deprecation-encounter-protocol.md` R-4: "Found → append the encounter evidence as a comment." The developer's observed failures are the agent's escalation reports, clarification requests, reasoning, chat and session-transcript excerpts, and pipeline-state updates. The gate's **predicate has no falsifier**: "needs special attention" and "must see" are satisfied by anything the agent finds interesting, so an escalation report and a clarification request each read as "a finding a stakeholder must see" and pass the gate. The exclusions reach one of the five classes (internal reasoning) and miss the other four; and none of the five has a stated route, so where the exclusion is not recognized the agent has nowhere else to put the content. The channel vacuum compounds it: the implementation-workflow reference says to "report the state, the blocker, and what is needed," the `verify` card says escalation "fires" to the developer, the `git-workflow-pr` card says "Any failure → halt and report the gap," the floor's standing formula says to halt with an open-ended clarification request — none names where the report goes, and the tracker is the surface that persists, is developer-visible, and already carries pipeline state. The deck already holds the governing principle and never applies it to the tracker: `skills/correspondence/SKILL.md` §1 states that internal findings, audit output, and raw progress "go to chat — never to stakeholder channels," and the card's description claims the decision surface — "when deciding whether content belongs in a stakeholder channel at all" — but no card ever names an issue comment as a stakeholder channel. |
| 2 | **Root Cause / Motivation** | Three causes, each traceable in the deck's own history. **(1) The rewrite replaced a procedure with a rewritten summary.** Pre-rewrite, `attic/skills/issue-operations-comments/tasks/comment.md` carried a caller-side gate — "This substantiveness gate MUST be evaluated by callers BEFORE the caller commits to posting… Callers must not assume posting is the default outcome" — a content-classification table ("HOW it was figured out → internal"; "Audit findings, verdicts → internal"; "Discussion responses → internal"; "Decision log entries → internal"), and a default under uncertainty: "Default to `internal` (conservative) when classification is uncertain… Internal content posted publicly cannot be retracted." The live `skills/issues/SKILL.md` §3 shares no sentence with that card: its positive clause is a rewritten summary ("a major substantive change that needs special attention"), its exclusions are three rewritten examples with a different destination ("chat or the local store"), and its third sentence is a rewritten routing rule. What the rewrite dropped is the procedure's substance — the classification, the default under uncertainty, the explicit route table, and the caller-side discipline. The live gate is a weak predicate plus three examples; the retired card was a decision procedure. **(2) The deck's channel vocabulary never covered the tracker.** The retired pre-rip surfaces carried the missing pieces: `attic/skills/issue-operations-comments/` (the classification), `attic/guidelines/045-open-questions.md` (the interview format), `attic/guidelines/141-planning-status-tracking.md` (the rule that specs and plans are not tracking documents and that progress lives in state files). What remains in the live deck names the tracker as a place to *file* an issue and as a place to *read* context, and nowhere as a place the agent publishes its own working content. **(3) The working content has no stated route per class.** `skills/work/SKILL.md` §4 makes the work record scratch — it lives in the repository's git directory and the cleanup card removes it. The live gate does name two destinations for content it will not post ("chat or the local store"), and the local store is durable: the `issues` card's operating contract states that the mutation commands auto-commit and auto-push to the `issues-data` branch, and the developer has confirmed the local store as an acceptable record. What is missing is not a durable surface but a **route per class** — the gate's destinations are informal, no card says that an escalation goes to chat, and the deck writes pipeline state to the tracker by a different route as well (remote labels, `skills/issues/SKILL.md` §2; recorded as out of scope in §2.2). For a class the gate does not name, the agent has no route, and the tracker is the route it finds. The deck's own store records the developer's ruling on this pattern in the other direction: `.opencode#2610` — "a ledger is a tracking tool, not tracked work; it does not belong in the issues system." |
| 3 | **Approach Chosen** | One rule, one home, no mechanism. The `correspondence` card is widened to own the **channel decision** — which surface a piece of agent-generated content belongs on, and in what form — and its description is widened to name every surface on which the agent publishes generated content, so the card is loaded at the moment the agent decides where content goes. The card's body gains the channel set (stakeholder surfaces against working surfaces), a **falsifiable** remote class (a stakeholder notice: content whose reader must take a specific action before the work can continue), the **named** internal class (the five observed failure classes, plus progress narration and audit and verification verdicts), the **default under uncertainty** (the working surface, with the asymmetry that decides the tie), the **route** for each class (chat for the live exchange; the local issue store for the record; the artifacts for the durable trace; the artifact edited in place for a correction), the **class-coverage statement** (developer-directed content — an escalation, a clarification request, a report, a consultation — reaches the developer in chat, whichever card produces it), and the no-read-back rule (a tracker comment is never an answer, an authorization, or a record the agent reads back). `skills/issues/SKILL.md` §3 keeps a pointer to that rule and states the caller-side discipline the retired card carried — the gate is evaluated before the agent commits to posting, and posting is not the default outcome. The deprecation protocol's two encounter-evidence appends are rerouted to the ticket's store record, because they are live instructions to publish working content on the tracker — the one surface the rule would otherwise contradict. The change adds **no script, no wrapper, no tool command, no classifier, and no threshold**: the rule is judgment. The pre-rip deck's scripted instruction surfaces are preserved in `attic/` after the #2490 rewrite, and the developer's ruling in this session is explicit — scripting produces decks that have to be trashed and replaced. |
| 4 | **Alternatives Considered & Why Discarded** | (a) **Widen `skills/issues/SKILL.md` §3 in place.** — Discarded: the `issues` card's description is the router for issue lifecycle operations, and a comment-posting decision is not an issue-lifecycle operation; a widened `issues` description becomes a routing magnet for every issue-adjacent task. The channel set the rule must name (issue comment, PR body, PR comment, wiki page, release note, correspondence) is not an issues concern. (b) **A new dedicated `issue-comment` card.** — Discarded: the deck then carries a card for one decision while `correspondence` already holds both the principle and the vocabulary, and the skill-creator admission gate's net-zero requirement prefers the reuse. (c) **A mechanical gate — a wrapper command that writes the local record and then posts.** — Discarded by developer directive, and on the merits: the agent in the reported situation is already rogue and would work around a wrapper, and the pre-rip deck's scripted surfaces are the decks that had to be trashed and replaced. (d) **A session hook that blocks the tracker-comment command.** — Discarded for the same reason, and because it adds a script to the deck to defend a surface the rogue agent would route around; the deck's answer to an agent that ignores its rules is a rule that is true, findable, and correct on its default path, not an interlock. (e) **A size or structure threshold on comment bodies.** — Discarded: size metrics are the deck's retired discipline, and a threshold is gameable by a threshold-shaped body. (f) **Ban remote issue comments entirely.** — Discarded: the developer accepted a tight positive class; a legitimate notice (a decision whose reader must take a specific action, such as a scope change that voids an authorization) needs a durable surface, and `.opencode#2661`'s R-5 notice is exactly that case. (g) **Name the five observed failure classes and stop there — a bare ban list.** — Discarded: a ban list leaves the predicate unbounded, and the live gate already fails that way — its positive clause admits the observed classes and its three exclusions miss four of the five. A rule that names the five inside a falsifiable predicate and a stated default answers both halves of the failure; a bare list answers only the half that was not the failure. (h) **Amend every escalation, clarification, report, and consultation producer in the deck so each states its route at its own site.** — Discarded as this artifact's deliverable, and recorded as a follow-on: the coverage obligation's scope is "every producer in a live deck," an unbounded and moving target, and an artifact that asserts a complete inventory of it cannot be completed — successive review rounds kept falsifying the inventory. The route reaches those producers through the rule's class-coverage statement and the widened router instead. |
| 5 | **Key Design Decisions** | (1) **The channel decision lives in `correspondence`, not in `issues`**: the deck's audience-separation principle already exists, and widening that card's reach is net-zero against the admission gate's replacement requirement, while `issues` keeps the operations it owns. (2) **The card owns the decision; the owning card owns the mechanics**: the channel rule decides *whether* content belongs on a surface; a surface's own card (`git-workflow-pr` for a PR body, `release-promoter` for a release note, `wiki-operations` for a wiki page) keeps the mechanics. The description says so, so a widened router does not create competing jurisdictions. (3) **The remote class is positive and falsifiable, not negative**: a tracker comment is a stakeholder notice — content whose reader must take a specific action before the work can continue — and the rule names the qualifying kinds. The pre-rip deck's falsifier ("needs to act on") is restored; the rewrite's weakening to "must see" is the defect. (4) **The default under uncertainty is the working surface, and the asymmetry decides the tie**: a notice can be added later; published narration cannot be withdrawn. This is the retired card's "default to internal" with its cost rationale, restored. (5) **The five observed classes are named inside the rule**, so the rule's coverage of the reported failures is legible on the card rather than inferred. (6) **The route reaches the deck's producers by class, not by enumeration**: the rule states once that developer-directed content goes to the developer in chat whichever card produces it, so no producer is left unrouted and no inventory needs asserting. (7) **One rule, one home**: `skills/issues/SKILL.md` §3 becomes a pointer, not a second gate, so the two surfaces cannot drift. (8) **`floor.md` is untouched**: a substantive write to the floor triggers the ainglish discipline's whole-card-on-touch conversion of the entire floor's normative prose (`guidelines/ainglish-writing-discipline.md`, "Adoption rules"), and the channel decision is card-level content under the skill-creator card's always-loaded-surface discipline. (9) **PR comments follow the issue-comment gate; PR bodies do not**: the pre-rip deck exempted the PR body (a merge artifact) and held PR comments to the same rule as issue comments, and the live deck states neither. (10) **The deliverable's reach is bounded to the rule and the contradiction it creates**: a substantive write to a card obligates that card's whole normative prose to be returned under the ainglish discipline, so the deliverable's cost and review surface scale with the number of cards it touches; the rule needs two, and the contradiction fix needs none. (11) **The rule governs agent-generated working content, not the tracker's other surfaces**: the `issues` card's label clause and ticket-state hygiene remain the `issues` card's business, and the rule says so, so the two surfaces do not classify the same content differently. |
| 6 | **User Intent / Original Prompt** | The developer's directives, this session: review the deck — the agent has started posting useless comments to remote issue tickets ("escalations", "interview attempts", "chat dialog", "reasonings", "state tracking," and other commentary) which the developer deletes as nothing more than trash and noise; comments added to the local spec record are fine, while remote API issue tickets are considered wasteful, polluting, and confusing. Find the probable wording issues or rewrite loss in the skill cards, using the ainglish reference materials to identify problematic wording. Widen the `correspondence` description as much as seems allowable. No scripting: "scripting always results in trash decks that have to be trashed and replaced with new decks." On the residual risk of an agent that disregards the deck's rules: the reported agent is already rogue and will work tirelessly to bypass any scripting, so the fix is the rule text and the routing, not enforcement. Spec per the recommendations. On the loop this artifact was in: a spec or plan needing more than four revisions to address defects is re-evaluated for decomposition and recomposition, for a poorly worded or unreachable intent, and for a spec too fat to split into interdependent parts — this artifact passed that threshold, and the re-evaluation's record is at `.opencode/.issues/2662/audit/re-evaluation.yaml`. |

The floor's standing formula names the halt but no channel; the rule's class-coverage statement carries the route.

Each produces developer-directed content, which the rule routes to chat by class. Amending each site is a real improvement and is recorded as a follow-on; it is not this artifact's deliverable, because an artifact that asserts a complete inventory of a live deck's producers cannot be completed — successive review rounds kept falsifying the inventory. The `implement` card's deprecation clause ("files or appends to a `[BITROT]` ticket") inherits the protocol's route: the protocol defines what an append targets, and the card names the ticket.
- **`skills/spec/SKILL.md`** — §5 already states that spec content never lives in comments and that corrections edit the artifact in place.
- **`skills/plan/SKILL.md`**, **`skills/research/SKILL.md`**, **`skills/behavioral-testing/SKILL.md`** — no tracker-comment instruction; the research card already routes findings to a local research card, and the behavioural card's "ceremony escalation" is a verdict sense of the word.
- **`skills/gh-cli/SKILL.md` and `skills/gb-cli/SKILL.md`** — the CLI cards carry mechanics, not judgment. The `gb-cli` card's `gb issue comment` example is a file-passing pattern, and its §5 mandates a comment POST for GitBucket issue state mutation — a state-mutation route whose body is the platform's own system comment, not agent working content. The rule governs what the agent publishes, not which command carries it.
- **`skills/git-workflow-pr/SKILL.md`** — the PR *body* contract's rule is unchanged; the card carries no tracker-comment instruction.
- **The criteria sets' content** — the defect classes, verdict contracts, analysis families, and loop mechanics of the `spec` and `plan` validation standards are unchanged. The `skill-creator` admission gate and every other deck-governance rule are untouched.
- **`skills/issues/SKILL.md` §2's label clause and §6's ticket-state hygiene** — the live deck writes pipeline state to remote labels ("Title states the work; labels describe pipeline state," `skills/issues/SKILL.md` §2) and treats the remote tracker's state as the anchor for out-of-band changes. That is state tracking on the tracker by a different route, adjacent to the developer's reported "state tracking" class, and it is a separate question from the comment gate; the deck's recorded position on labels is `.opencode#1312` principle 2 (remote labels are advisory for stakeholders; local state is authoritative), and this spec does not re-litigate it. The channel rule states that these are the `issues` card's surfaces, outside its own scope, so the two rules classify the same content consistently. Recorded here so the adjacency is visible rather than silently ignored.
- **The `local-issues` tool** — no command added, changed, or deprecated. The rule names the existing `comment --type internal` and `update --status`/`--phase` commands as routes; the tool itself is not touched.
- **`tests-v2/`** — no new scenario script and no harness change, per the developer's no-scripting directive. The change's runtime effect is observed in the developer's review of the tracker, not asserted by a new script.
- **`.opencode#2661`'s spec** — its R-5 recomposition notice is a legitimate stakeholder notice under the new rule, and the rule's classification leaves it permitted. The change does not edit that spec.

### 2.3 Impact

- **Consumers.** Every agent session that touches a tracked issue — the deck's own issue pipeline, the repositories whose issues it works, and the developers who read those trackers. The change replaces the deck's only instruction on remote comments with a falsifiable predicate, a named internal class, a default, and routes.
- **Risk — over-suppression.** A legitimate stakeholder notice withheld. Bounded by the positive class (R-3), which names the qualifying kinds, and by the developer's own review of the tracker, which is where the notice would otherwise have been noise.
- **Risk — no enforcement.** A determined agent that disregards every card remains outside the deck's reach, by the developer's explicit direction. The change's effect rests on the rule being encountered — the widened router is what puts the agent in front of it — and on the default being the working surface.
- **Risk — a wider diff than the targeted deltas.** The ainglish whole-card-on-touch rule brings each amended card's entire normative prose into scope: the `issues` card's eight items and its operating contract, and the `correspondence` card's five. The conversion resolves ambiguity without changing substance (R-12); content defects the conversion surfaces are recorded rather than fixed (§5).
- **Blast radius.** Two cards' full normative prose and one guideline's. No tool, harness, hook, or script surface changes; no data migration; nothing outside the deck is affected.

## 3. Requirements

- **R-1** — The `correspondence` card SHALL name the channel set: the stakeholder channels (an issue comment, a pull-request body, a pull-request comment, a wiki page, a release note, correspondence) and the working surfaces (chat, the local issue store, the artifacts under an issue's folder); SHALL state that the card owns the channel decision while the card owning a surface owns that surface's mechanics; and SHALL state that the issue tracker's labels and closure state are the `issues` card's surfaces, outside this rule's scope.
- **R-2** — The `correspondence` skill description SHALL name each of the six stakeholder channels enumerated in R-1 and chat, and SHALL state the decision the card owns; so that the card is loaded at the moment the agent chooses between a working surface and a stakeholder surface.
- **R-3** — The rule SHALL state the positive remote class with a falsifier: a remote issue comment is a stakeholder notice — content whose reader must take a specific action before the work can continue; and SHALL name the qualifying kinds (a decision, a scope change, a finding, a status the reader must act on) — those kinds being the ones outside the internal class named in R-4, so that no content is qualified by R-3 and forbidden by R-4.
- **R-4** — The rule SHALL name the content that never reaches a remote issue comment or a pull-request comment, and the named set SHALL include every observed failure class: escalation reports, clarification requests, the agent's reasoning, chat and session-transcript excerpts, and pipeline state — together with progress narration and audit and verification verdicts.
- **R-5** — The rule SHALL state that the default under uncertainty is the working surface, and SHALL state the asymmetry that decides the tie: a stakeholder notice can be added later, and published narration cannot be withdrawn.
- **R-6** — The rule SHALL name the route for each class: chat for a live exchange (an escalation, a clarification request, a report to the developer), the local issue store for the record — naming both the `local-issues comment --number repo#N --type internal` command and the `local-issues update --number repo#N --status`/`--phase` state fields — the artifacts for the durable trace, and the artifact edited in place for a correction.
- **R-7** — The rule SHALL state that a tracker comment is never an answer, an authorization, or a record the agent reads back.
- **R-8** — The rule SHALL state the class coverage: developer-directed content — an escalation, a clarification request, a report to the developer, a consultation — reaches the developer in chat, whichever card produces it; and a card's own escalation or halt rule names no channel of its own and takes this one.
- **R-9** — The `issues` card's comment gate SHALL defer to the channel rule through the deck's canonical link form, SHALL state that the gate is evaluated before the agent commits to posting and that posting is not the default outcome, and the card's description SHALL no longer summarize the gate as a bar on progress narration only.
- **R-10** — The deprecation protocol's two encounter-evidence append sites — the "Found → append the encounter evidence as a comment" clause and the duplicates bullet's "appending its encounter evidence to the first ticket" — SHALL be routed to the ticket's store record rather than to a tracker comment, so that the deck carries no live instruction to publish working content on the tracker.
- **R-11** — The `issues` card's one non-canonical cross-reference SHALL convert to the canonical `Read [Text](path)` form, per the skill-creator card's forwards-only rule ("existing content converts when touched").
- **R-12** — Each amended card's full normative prose SHALL be returned under the ainglish writing discipline (`guidelines/ainglish-writing-discipline.md`), per that discipline's whole-card-on-touch rule — the card's entire normative prose written so the reader cannot misbind it, with the misbindings the conversion surfaces resolved — and the guideline's normative prose SHALL be returned under the discipline on touch. The conversion SHALL preserve the prose's substance, changing nothing beyond this spec's rules.

### 6.1 The live gate and the retired procedure

**The retired procedure.** `attic/skills/issue-operations-comments/tasks/comment.md` (preserved, tag `pre-rip`) carried the caller-side gate ("Callers must not assume posting is the default outcome"), the classification table ("HOW it was figured out → internal"; "Audit findings, verdicts → internal"; "Discussion responses → internal"; "Decision log entries → internal"), and the default ("Default to `internal` (conservative) when classification is uncertain… Internal content posted publicly cannot be retracted"). ### 6.2 The channel vacuum, quoted

`skills/implement/references/implementation-workflow.md`: *"Escalation: any step that cannot complete honestly stops the cycle — report the state, the blocker, and what is needed; never fabricate a pass."* `skills/verify/SKILL.md` §4: *"Escalation to the developer fires when spin persists after genuine higher-level fixing attempts…"* `skills/git-workflow-pr/SKILL.md` §2(c): *"Any failure → halt and report the gap — never create the PR anyway."* `floor.md`: *"when unsure, halt with an open-ended clarification request — never a constrained-choice prompt."* None names a route. The rule's class-coverage statement routes every one of them by class.

### 6.3 The ainglish reading of the live gate

Against `guidelines/ainglish-writing-discipline.md`: the gate is passive with no named decision-maker (family 1, actor binding); "needs special attention" and "must see" are neither facts nor an assigned decision, and the deck never owns them (family 3, missing evidence vs unmade decision); the predicate carries no falsifier, and the pre-rip wording "needs to **act on**" was weakened to "must see," which a curiosity satisfies (family 4, claim confidence and falsifier anchoring); "chat or the local store" names two channels with no default, and "the local store" binds to neither of the deck's two stores (family 5, referent binding). The skill description compounds it by summarizing the gate as "non-substantive progress updates," so an agent that never loads the card believes the rule bans progress narration only.

### 6.4 The cross-reference the touch converts

One non-canonical cross-reference sits in the amended cards as of 2026-10-23: `skills/issues/SKILL.md` (the remote-body-format reference). The skill-creator card's "Agent-facing cross-references" section requires the canonical `Read [Text](path)` form and states "Forwards-only: existing content converts when touched." The `reference-integrity` tool matches `Read\s+\[([^\]]+)\]\(([^)]+)\)` — it validates that canonical links resolve and cannot see a non-canonical form, so the conversion is checked by reading (SC-11).

### 6.5 The developer's own store records the same principle

`.opencode#2610`, filed from the deck-debt ledger the agent had created in the stakeholder-facing tracker: *"A ledger is a tracking tool, not tracked work; it does not belong in the issues system; the mechanism was never asked for."* `.opencode#1312`'s spec, "Eliminate GitHub Issue comment spam from pipeline skills," states the principles this deck's live cards no longer carry: comments are for stakeholder communication only; remote labels are advisory for stakeholders and state tracking is local; comments are never an authorization source; status, progress, phase-complete, and verification results go to the state file and chat.

### 6.6 The rogue-agent limit, stated

The developer reports that the agent in question is already rogue and would work tirelessly to bypass any scripting. This spec therefore assumes no enforcement: there is no interlock, no wrapper, and no classifier, and the deliverable is the rule text and the routing that makes the correct channel the path of least resistance. A determined agent that disregards every card is outside the deck's reach, and the developer's directive in this session is explicit: no scripting.
