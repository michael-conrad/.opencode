# Spec: A vendored, pull-only deck checkout is not a repository the session manages

## 1. Problem

Consumers of this deck vendor it at `.opencode/` as a sub-repository the workspace root does not track, over a pull-only `https` origin. In that state the session's own tooling treats the vendored checkout as a repository it manages, and the agent tries to manage it.

### 1.1 The store mounts inside a checkout the session cannot write to

`local-issues init` — which the `issues` card mandates at session start — created an `issues-data` branch inside the vendored checkout and mounted the deck's whole issue store at `.opencode/.issues`. Reproduced on 2026-10-24 in a workspace whose `.gitmodules` names `.opencode` and whose `.opencode` is an unregistered `https` clone: after `init`, `git -C .opencode branch` lists `issues-data`, `git -C .opencode worktree list` lists `.opencode/.issues` at the upstream's tip, and the tool's own report reads `issues_count: 1255`. The deck's `issues-data` branch is published on the upstream — `git ls-remote --heads https://github.com/michael-conrad/.opencode.git issues-data` returned a ref on 2026-10-24 — so the fetch succeeds and the store mounts rather than failing.

The mutations this store accepts auto-commit and auto-push. The tool skips a push only when the remote is `https` **and** no credential helper is configured; with a credential helper configured — the ordinary state on a developer machine — the tool attempts a push into the pull-only remote, and the upstream's `issues-data` branch is public, so that push targets a repository the consumer does not own. The remote the tool reads is the *effective* one — `git remote get-url origin`, which applies git's URL rewrites — so the classification that decides this is the classification the transport would use.

### 1.2 The tool's repository set and the session's set disagree

`session-init` enumerates repositories through git's registered-submodule mechanism (`.opencode#2544`); `local-issues` parses `.gitmodules` text and accepts any child directory that exists. In the same reproduced workspace, `session-init` reports no `.opencode` entry and one store path, while `local-issues` reports a second repository holding a store. The two tools answer the question "which repositories does this workspace manage?" differently, and the tool is the one that writes.

### 1.3 A registered-but-uninitialized submodule is treated as a store host

`init` ran `git worktree add` inside a directory that is not a repository, and the bootstrap aborted: `error: failed to establish issues-data worktree for .../.opencode: worktree setup failed`, preceded by `fatal: 'issues-data' is already used by worktree at .../.issues`. The session's store bootstrap failed on a checkout that has no checkout.

### 1.4 No card states a writability precondition

`git-workflow-branch` (rules 1–6), `git-workflow-commit` (rules 1–5), and `git-workflow-pr` (rules 1–6) mandate branch creation, commits, pushes, and pull requests "in any repo" with no check that the session can write there. No card states that a repository the workspace root does not track is outside the managed set. `.opencode/AGENTS.md` states that it "must stay a pointer and carry no rules", so it is not a home for the rule either.

### 1.5 The agent routes around a non-delivery target

A checkout that is not a delivery target does not end the work: the agent looks for another copy of the same repository elsewhere on disk and attempts delivery there. The workspace holds such copies by construction — sibling repository folders each carry their own vendored `.opencode` checkout of the same upstream, untracked by their own roots (Section 8). Seeking a writable copy of a checkout in order to deliver into it is the same defect as treating the pull-only checkout as a delivery target: it moves delivery outside the workspace the developer scoped, into a repository the request never named, and it delivers work the developer did not ask that repository to receive. No card states the prohibition.

### 1.6 Root cause

The deck's tooling infers "the repositories this session manages" from the *declared* submodule configuration (`.gitmodules` text) and from filesystem shape, never from git's *registered* submodule state and never from the remote's writability. The deck's cards carry the same assumption: any repository present in the workspace is a work surface, and a checkout that refuses delivery is a checkout to route around rather than to report. The tool and the session therefore hold two different repository sets, and the set that writes is the wrong one.

## 2. Scope

The change touches six existing surfaces in the `.opencode` repository and adds one file.

The six surfaces:

- `tools/local-issues` — the set of repositories eligible to hold an issue store, and the pull-only rule that governs store creation, mutation, and pushing.
- `tools/session-init` — the writability fact it reports per repository, and the store path it advertises.
- `skills/git-workflow-branch/SKILL.md` — the delivery-target rule.
- `skills/issues/SKILL.md` — the store rule, and the operating-contract line it qualifies.
- `skills/issues/references/local-issues-cli.md` — the `init` row, which today describes the store's repository set as `.gitmodules` children.
- `skills/issues/references/sync-mirroring.md` — the `init` bullet, which carries the same description.

The one added file: a behavioral scenario script under `tests-v2/behaviors/`, the artifact generator for the delivery-target rule, paired with a clean-room evaluation of its recorded tool calls at verification time.

Untouched: `floor.md`; `.opencode/AGENTS.md`; the `git-workflow-commit` and `git-workflow-pr` cards' own mechanics; the deck's own issue store contents; `attic/`; the `skill-creator` admission gate.

## 3. Requirements

- **R-1** — `tools/local-issues` SHALL determine the repositories eligible to hold an issue store from git's registered-submodule mechanism: the workspace root, plus the repositories the workspace's registered-submodule mechanism reports — the set `git submodule status` reports for the workspace root, restricted to the paths the workspace's `.gitmodules` names. The tool SHALL NOT derive eligibility from `.gitmodules` text parsing or from the presence of a directory. A path `git submodule status` reports as uninitialized (a leading `-`) SHALL NOT receive a store.
- **R-2** — `tools/local-issues` SHALL treat a child repository as pull-only when its effective `origin` URL — as `git remote get-url origin` reports it, after git's URL rewrites — carries the scheme `http` or `https`. For such a repository the tool SHALL NOT create an `issues-data` branch, SHALL NOT mount an `.issues` worktree, SHALL NOT push to it, and SHALL NOT accept an issue mutation naming it. The workspace root SHALL be exempt from this rule: the scheme of the root's own origin is not evidence about the developer's push rights on their own repository, and an `https` root is a common state for a repository cloned over the web.
- **R-3** — `tools/session-init` SHALL report each enumerated repository's pull-only classification in the `## Repo Information` block, and SHALL NOT report an issue-store path for a repository that R-2 classifies as pull-only. The classification SHALL be reported as a `pull_only` field carrying `true` when the repository's effective `origin` URL carries the scheme `http` or `https` and `false` otherwise; the field's value SHALL be derived from the scheme alone, and the remote URL itself SHALL NOT be reported, because a remote URL can carry credentials. The workspace root is exempt and carries no such field. `tools/session-init` and `tools/local-issues` SHALL derive their repository sets from the same mechanism — git's registered-submodule mechanism — so that a checkout the workspace root does not track is in neither set. The two sets need not be identical: `session-init` additionally filters a repository without a checkout, without an `origin`, or with a wiki origin, and walks nested submodules; those differences are outside this change's scope.
- **R-4** — `skills/git-workflow-branch/SKILL.md` SHALL state the delivery-target rule. Two facts each independently make a checkout a non-delivery target: (a) the workspace root does not track it — it is a vendored copy, not a registered submodule; (b) its effective `origin` URL carries the scheme `http` or `https`. The workspace root is not a non-delivery target on account of its origin's scheme. In a non-delivery-target checkout the agent SHALL NOT create a branch, SHALL NOT commit, SHALL NOT push, and SHALL NOT open a pull request against it, and SHALL report the limitation instead of attempting delivery. The rule binds delivery, not editing: it does not prohibit an edit the developer asked for in such a checkout, the branch-and-commit rules do not apply there, and the agent reports such an edit as undeliverable. The rule carries two further clauses. **Pointer scope:** a checkout the workspace root does not track is not a submodule; the deck's submodule rules — the submodule-pointer sync (rule 2) and the pointer-capture commit (rule 3) — apply to registered submodules only, and the agent SHALL NOT move a non-tracked checkout's HEAD to a remote trunk tip. **No routing around:** the agent SHALL NOT seek another copy of the same repository elsewhere on disk — a sibling repository folder's copy included — in order to deliver into it; the limitation is reported, not routed around.
- **R-5** — `skills/issues/SKILL.md` SHALL state that a pull-only repository holds no issue store, that the local store's operations SHALL NOT target it, and that issue tracking for it goes through the platform API against its own tracker. The card's operating-contract line stating that a first mutation auto-initializes the `.issues/` orphan-branch worktree SHALL be qualified so that it does not claim a store for a pull-only repository.
- **R-6** — The two operating references that describe `init`'s repository set — `skills/issues/references/local-issues-cli.md` and `skills/issues/references/sync-mirroring.md` — SHALL describe that set as the workspace root plus its registered submodules, and SHALL NOT describe it as `.gitmodules` children.
- **R-7** — The change SHALL touch only the six surfaces named in Section 2, SHALL add exactly the one file named in Section 2, and SHALL add no tool command, no wrapper, and no enforcement hook.

## 5. Not included

- The `work` card's path selection, the `plan` card, and the `implement` card's own work-cycle rules.
- The pointer discipline for registered submodules (`.opencode#2563`) — the pointer sync, the capture commit, the ride-along, and the pointer-only prohibition — is unchanged for a registered submodule. This spec scopes that discipline to registered submodules; it does not retire it.
- The `skill-creator` admission gate and every other deck-governance rule.
- Any behavior change for a repository whose effective origin is `ssh`, a local path, or another non-`http(s)` scheme: the tool continues to treat it as a store host, and the agent continues to treat it as a delivery target.
- Detection of read-only credentials on a non-`http(s)` origin (a read-only SSH deploy key). The `http(s)` scheme is the detection rule; a read-only `ssh` origin is not detected.
- The workspace root's own writability. The root keeps its store under an `https` origin, and the root's push behavior is unchanged.
- Nested submodules at depth two or deeper. The tool's store scope stays the workspace root plus its direct registered submodules, as it is today, so the two tools' sets may differ where `session-init`'s nested walk reaches further.
- The eligibility of a wiki-origin submodule and of a submodule with no `origin` remote. The tool's existing handling of both is unchanged, and the two tools' sets may differ on them.
- Any new tool command, wrapper, hook, or scenario harness beyond the one scenario script named in Section 2.
- Routing an issue about a vendored deck file to the deck's upstream tracker. The `issues` card's path-prefix routing is unchanged; a consumer's agent that files an issue about a vendored file is a separate design question.

## 6. Approach

Fix the mechanism where the defect is decidable, and state the boundary where it is not.

1. **`tools/local-issues`** — replace the `.gitmodules` text parsing in the store-eligible repository set with the registered-submodule mechanism `session-init` already uses (R-1); add the pull-only rule that keeps a pull-only child repository out of the store set, off the push path, and out of the mutation path (R-2).
2. **`tools/session-init`** — report each child repository's `pull_only` classification and withhold the store path for a pull-only repository (R-3).
3. **`skills/git-workflow-branch/SKILL.md`** — state the delivery-target rule with its pointer-scope clause and its no-routing-around clause (R-4).
4. **`skills/issues/SKILL.md`** — state the store rule, name the platform API as the route for a pull-only repository's issue tracking, and qualify the operating-contract line (R-5).
5. **The two operating references** — bring the `init` descriptions into line with the new repository set (R-6).
6. **`tests-v2/behaviors/`** — add the scenario that runs an agent against a pull-only deck checkout and asks for delivery, and pair it with one clean-room evaluation dispatch per behavioral criterion (R-7).

No new mechanism, no tool command, no threshold (R-7): the defect is a wrong repository set, and the fix is the right repository set.

### Alternatives considered and discarded

- **`.opencode/AGENTS.md`** — the file states that it "must stay a pointer and carry no rules", and it sits outside the `skill-creator` admission gate's scope, so a rule placed there would bypass the deck's governance. Discarded.
- **`floor.md`** — the always-injected surface costs every session, in every repository, for a rule that binds one decision the `git-workflow-branch` card is loaded to make. Discarded in favor of the card.
- **A pre-push hook in the vendored checkout that refuses the push** — the deck's hooks are installed by `session-init` into the workspace root's git directory, and a vendored checkout is not the workspace root, so the session has no installation path for a hook in the checkout where the rule binds; placing one would require the repository management the rule forbids. The floor permits mechanical enforcement of fact-decidable rules, and this rule is fact-decidable, so the ground here is the installation path and the change's minimality — not a prohibition on scripting. Discarded.
- **Probing push access to decide whether a checkout is writable** — a probe mutates or prompts, and the `http(s)` scheme is the detection the developer stated. Discarded.
- **Keeping the `.gitmodules` parsing and instead checking whether a child directory is a git repository** — an unregistered plain clone *is* a git repository, so the check does not distinguish the consumer's vendored deck from a registered submodule. Discarded.
- **Making the tool's repository set transitive, matching `session-init`'s nested walk** — out of scope: the tool's store scope is the workspace root plus its direct registered submodules today, and nothing in the stated defect reaches deeper. Recorded in Section 5 rather than attempted here.

## 7. Impact

- **Consumers:** every session in a repository that vendors the deck. The store no longer mounts inside a read-only checkout, the session's inventory and the tool's inventory agree on the vendored checkout, the agent stops attempting delivery into a checkout it cannot write to, it stops treating a non-tracked checkout as a submodule whose pointer it manages, and it stops hunting sibling folders for a copy it can write to.
- **Consequence — a requested change to a vendored checkout becomes reported work, not delivered work.** Under R-4 the agent performs the edit the developer asked for in a non-delivery-target checkout and reports the delivery limitation; the change reaches the deck through the deck's own upstream tracker and the developer's direction, not through the consumer's session. That is the intended outcome: the consumer's session does not deliver into a repository the consumer does not own.
- **Risk — a false pull-only classification.** A child repository over an `https` origin that the session *can* push to loses its store. The workspace root is exempt (R-2), which covers the common case of a consumer's own repository cloned over the web; a child repository over `https` that the developer owns and pushes to is the residual case.
- **Risk — the developer's own deck checkout.** The deck's own development family (the `opencode-config` parent with the deck registered over an `ssh` origin) keeps the deck's store and stays a delivery target; SC-8 and SC-9 exercise both halves of that.
- **Blast radius:** `tools/local-issues`, `tools/session-init`, `skills/git-workflow-branch/SKILL.md`, `skills/issues/SKILL.md`, `skills/issues/references/local-issues-cli.md`, `skills/issues/references/sync-mirroring.md`, and one added behavioral scenario under `tests-v2/behaviors/`. No other card, tool, hook, or plugin changes.
- **Harness compatibility — the classification is tier-dependent.** The behavioral harness injects the rewrite `url.https://github.com/.insteadOf=git@github.com:` into the Docker tier as env-level config that applies to every git invocation in the container (`tests-v2/docker/docker-harness.sh`), and into the host tier as a clone-time `-c` option that git does not persist. Under the effective-URL read the rule uses, the deck submodule's origin therefore resolves differently by tier: as `https://github.com/michael-conrad/.opencode.git` in a Docker-tier run, and as its `ssh` form in a host-tier run (both verified 2026-10-24 — see Section 8). A Docker-tier run consequently classifies the deck as pull-only: the deck receives no issue store, and the deck is a non-delivery target. Two consequences follow, both checked: no harness scenario depends on the deck's issue store (the fixture issues are injected into the root store, and no scenario names the `.opencode#N` qualifier as a store target); and the two scenarios that edit a deck card in the harness test project (`.opencode#2554` SC-9 and `.opencode#2584` SC-4) judge the *edit* — their criteria are the whole-card conversion and the edit completing without a ceremony halt, and neither requires a branch, a commit, or a push in the deck checkout — so R-4's editing clause leaves both intact. The harness's own root reads as `https` in both tiers, which R-2's and R-4's root exemptions cover: the root keeps its store and stays a delivery target.
- **Recovery:** the change is text and tool behavior; reverting the six surfaces and removing the scenario script restores the previous behavior.

## 9. Edge cases

- The classification reads the *effective* origin: a checkout whose stored origin is `ssh` but whose URL rewrite resolves it to `https` is pull-only. The Docker tier of the behavioral harness is exactly such a case for the deck submodule.
- The workspace root is never a non-delivery target on account of its origin's scheme, and always keeps its store.
- A registered submodule whose `git submodule status` line carries a leading `+` (a checked-out commit other than the recorded gitlink) is registered and initialized: it remains a store host, exactly as the deck's own development family requires.
- A repository with no `origin` remote at all is neither pull-only nor pushable; the tool's existing no-remote handling is unchanged.
- A child repository whose effective origin is `git://` or another non-`http(s)` scheme is treated as writable, because the stated detection rule names `http` and `https` only.
- The deck's own `issues-data` worktree in the developer's checkout is a linked worktree of a registered submodule over an `ssh` origin; R-1 and R-2 leave it in place.
- An issue mutation naming a pull-only repository fails at the tool rather than silently succeeding; the tool's error names the repository and its pull-only classification.
