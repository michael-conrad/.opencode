# Spec: A vendored, pull-only deck checkout is not a repository the session manages

## 1. Problem

Consumers of this deck vendor it at `.opencode/` as a sub-repository the workspace root does not track, over a pull-only `https` origin. In that state the session's own tooling treats the vendored checkout as a repository it manages, and the agent tries to manage it.

### 1.1 The store mounts inside a checkout the session cannot write to

`local-issues init` — which the `issues` card mandates at session start — created an `issues-data` branch inside the vendored checkout and mounted the deck's whole issue store at `.opencode/.issues`. Reproduced on 2026-10-24 in a workspace whose `.gitmodules` names `.opencode` and whose `.opencode` is an unregistered `https` clone: after `init`, `git -C .opencode branch` lists `issues-data`, `git -C .opencode worktree list` lists `.opencode/.issues` at the upstream's tip, and the tool's own report reads `issues_count: 1255`. The deck's `issues-data` branch is published on the upstream — `git ls-remote --heads https://github.com/michael-conrad/.opencode.git issues-data` returned a ref on 2026-10-24 — so the fetch succeeds and the store mounts rather than failing.

The mutations this store accepts auto-commit and auto-push. The tool skips a push only when the remote is `https` **and** no credential helper is configured; with a credential helper configured — the ordinary state on a developer machine — the tool attempts a push into the pull-only remote, and the upstream's `issues-data` branch is public, so that push targets a repository the consumer does not own. The remote the tool reads is the *effective* one — `git remote get-url origin`, which applies git's URL rewrites — so the classification that decides this is the classification the transport would use.

### 1.2 The tool's repository set and the session's set disagree

`session-init` enumerates repositories through git's registered-submodule mechanism (`.opencode#2544`); `local-issues` parses `.gitmodules` text and accepts any child directory that exists. In the same reproduced workspace, `session-init` reports no `.opencode` entry and one store path, while `local-issues` reports a second repository holding a store. The two tools answer the question "which repositories does this workspace manage?" differently, and the tool is the one that writes.

### 1.3 A registered-but-uninitialized submodule is treated as a store host

`init` ran `git worktree add` inside a directory that is not a repository, and the bootstrap aborted: `error: failed to establish issues-data worktree for .../.opencode: worktree setup failed`, preceded by `fatal: 'issues-data' is already used by worktree at .../.issues`. The session's store bootstrap failed on a checkout that has no checkout.

### 1.4 The deck's own unit tests pin the mechanism being replaced

`tests/test_local_issues/test_cwd_independence.py` asserts that discovery yields the `.gitmodules` child, and `tests/test_local_issues/test_doctor_branch_health.py` asserts that `doctor` attributes a marker to the `.opencode` child. The first fixture makes the child a plain git repository with no gitlink; the second creates only the root as a repository and leaves `.opencode` as plain directories whose `.gitmodules` entry is inert text. Neither fixture presents a registered submodule, so neither expectation survives R-1 unchanged, and the second fixture's per-repository attribution assertion needs a child repository the new mechanism reports. The deck's precedent is that a discovery-mechanism change ships with its unit tests — commit `805d975c` ("#2544: strict registered-submodule discovery") changed `tools/session-init` and `tests/test_session_init/test_repo_discovery.py` together.

### 1.5 The cards' mandates reach a checkout the session may not touch

`git-workflow-branch` (rules 1–6), `git-workflow-commit` (rules 1–5), and `git-workflow-pr` (rules 1–6) mandate branch creation, commits, pushes, and pull requests "in any repo" with no check that the session can write there. Three specific mandates land on the vendored checkout:

- `git-workflow-branch` rule 2 tells the agent to sync each submodule's pointer to that submodule's remote trunk tip. A vendored checkout the workspace root does not track has no pointer to sync — and moving its HEAD to the upstream's trunk tip would rewrite the consumer's vendored deck.
- The same rule's rule 3 mandates an immediate pointer-capture commit; a non-tracked checkout has no pointer to capture.
- The delivery mandates themselves — branch, commit, push, pull request — have no writability precondition, so an agent asked to deliver a change into the deck attempts the whole sequence in a checkout it cannot write to.

Two further facts of the consumer's topology make the delivery attempt persistent rather than incidental. The deck exists in more than one checkout on the same machine: the vendored copy inside the consumer's workspace and the deck's own development checkout elsewhere on disk, so an agent that cannot deliver into the vendored copy can find a writable one. And `.opencode/AGENTS.md` states that it "must stay a pointer and carry no rules", so it is not a home for the rule either.

### 1.6 Root cause

The deck's tooling infers "the repositories this session manages" from the *declared* submodule configuration (`.gitmodules` text) and from filesystem shape, never from git's *registered* submodule state and never from the remote's writability. The deck's cards carry the same assumption: any repository present in the workspace is a work surface. The tool and the session therefore hold two different repository sets, and the set that writes is the wrong one.

## 2. Scope

The change touches seven existing surfaces in the `.opencode` repository and adds one file.

The seven surfaces:

- `tools/local-issues` — the set of repositories eligible to hold an issue store, and the pull-only rule that governs store creation, mutation, fetching, and pushing.
- `tools/session-init` — the writability fact it reports per repository, and the store path it advertises.
- `skills/git-workflow-branch/SKILL.md` — the delivery-target rule, the pointer-scope clause, and the no-routing-around clause.
- `skills/issues/SKILL.md` — the store rule, and the operating-contract line it qualifies.
- `skills/issues/references/local-issues-cli.md` — the `init` row, which today describes the store's repository set as `.gitmodules` children.
- `skills/issues/references/sync-mirroring.md` — the `init` bullet, which carries the same description.
- `tests/test_local_issues/` — the tool's unit tests, three test functions across two files whose expectations pin the discovery mechanism R-1 replaces. Their expectations move onto R-1's mechanism; the mechanism is not reverted to keep them green, and each test keeps the property it was written for.

The one added file: a behavioral scenario script under `tests-v2/behaviors/`, the artifact generator for the delivery-target rule, paired with clean-room evaluations of its recorded tool calls at verification time.

Untouched: `floor.md`; `.opencode/AGENTS.md`; the `git-workflow-commit` and `git-workflow-pr` cards' own mechanics; the deck's own issue store contents; `attic/`; the `skill-creator` admission gate.

## 3. Requirements

- **R-1** — `tools/local-issues` SHALL determine the repositories eligible to hold an issue store from git's registered-submodule mechanism: the workspace root, plus the repositories the workspace's registered-submodule mechanism reports — the set `git submodule status` reports for the workspace root, restricted to the paths the workspace's `.gitmodules` names. The tool SHALL NOT derive eligibility from `.gitmodules` text parsing or from the presence of a directory. A path `git submodule status` reports as uninitialized (a leading `-`) SHALL NOT receive a store.
- **R-2** — `tools/local-issues` SHALL treat a child repository as pull-only when its effective `origin` URL — as `git remote get-url origin` reports it, after git's URL rewrites — carries the scheme `http` or `https`. For such a repository the tool SHALL NOT create an `issues-data` branch, SHALL NOT mount an `.issues` worktree, SHALL NOT fetch from it, SHALL NOT push to it, and SHALL NOT accept an issue mutation naming it. Every mutation command the tool offers — `create`, `update`, `comment`, `close`, `delete`, `link`, `renumber` — that names such a repository SHALL be refused, and the refusal's diagnostic SHALL name the repository and its pull-only classification. The tool SHALL still resolve such a repository by name, so that the refusal can name it, and SHALL report it in its per-repository report with `status: pull-only`, reporting no operation against it. The workspace root SHALL be exempt from this rule: the scheme of the root's own origin is not evidence about the developer's push rights on their own repository, and an `https` root is a common state for a repository cloned over the web.
- **R-3** — `tools/session-init` SHALL report, for each enumerated repository, a `writability:` field in the `## Repo Information` block, valued `pull-only` or `not-pull-only`. A child repository whose effective `origin` URL carries the scheme `http` or `https` is reported `pull-only`; every other enumerated repository — the workspace root included — is reported `not-pull-only`. The tool SHALL NOT report an issue-store path for a repository reported `pull-only`, in either the `## Repo Information` block or the `## Local Issue Folders` section. `tools/session-init` and `tools/local-issues` SHALL derive their repository sets from the same mechanism — git's registered-submodule mechanism — so that a checkout the workspace root does not track is in neither set. The two sets need not be identical: `session-init` additionally filters a repository without a checkout, without an `origin`, or with a wiki origin, and walks nested submodules; those differences are outside this change's scope.
- **R-4** — `skills/git-workflow-branch/SKILL.md` SHALL state the delivery-target rule. Two facts each independently make a checkout a non-delivery target: (a) the workspace root does not track it — it is a vendored copy, not a registered submodule; (b) its effective `origin` URL carries the scheme `http` or `https`. The workspace root is not a non-delivery target on account of its origin's scheme. In a non-delivery-target checkout the agent SHALL NOT create a branch, SHALL NOT commit, SHALL NOT push, and SHALL NOT open a pull request against it, and SHALL report the limitation instead of attempting delivery. The rule binds delivery, not editing: it does not prohibit an edit the developer asked for in such a checkout, the branch-and-commit rules do not apply there, and the agent reports such an edit as undeliverable. The rule carries two further clauses. **Pointer scope:** a checkout the workspace root does not track is not a submodule; the deck's submodule rules — the submodule-pointer sync (rule 2) and the pointer-capture commit (rule 3) — apply to registered submodules only, and the agent SHALL NOT move a non-tracked checkout's HEAD to a remote trunk tip. **No routing around:** the agent SHALL NOT seek another copy of the same repository elsewhere on disk — a sibling repository folder's copy included — in order to deliver into it; the limitation is reported, not routed around.
- **R-5** — `skills/issues/SKILL.md` SHALL state that a pull-only repository holds no issue store and that the local store's operations SHALL NOT target it. The card's operating-contract line stating that a first mutation auto-initializes the `.issues/` orphan-branch worktree SHALL be qualified so that it does not claim a store for a pull-only repository.
- **R-6** — The two operating references that describe `init`'s repository set — `skills/issues/references/local-issues-cli.md` and `skills/issues/references/sync-mirroring.md` — SHALL describe that set as the workspace root plus its registered submodules, and SHALL NOT describe it as `.gitmodules` children. Both descriptions SHALL carry the pull-only carve-out R-2 establishes, so that neither claims a store for a pull-only repository.
- **R-7** — The change SHALL touch only the seven surfaces named in Section 2, SHALL add exactly the one file named in Section 2, and SHALL add no tool command, no wrapper, and no enforcement hook. The deck's unit-test suite SHALL pass after the change, with the tests that pin the old discovery mechanism carrying their expectations onto R-1's mechanism and keeping the properties they were written for.

## 5. Not included

- The `work` card's path selection, the `plan` card, and the `implement` card's own work-cycle rules.
- The `skill-creator` admission gate and every other deck-governance rule.
- Any behavior change for a **registered** submodule whose effective origin is `ssh`, a local path, or another non-`http(s)` scheme: the tool continues to treat it as a store host, and the agent continues to treat it as a delivery target. A child repository the workspace root does not track is excluded whatever its scheme — R-1 removes it from the store set and R-4's first trigger removes it from the delivery set.
- Detection of read-only credentials on a non-`http(s)` origin (a read-only SSH deploy key). The `http(s)` scheme is the detection rule; a read-only `ssh` origin is not detected.
- Determining the workspace root's actual push rights. The root is reported `not-pull-only` and keeps its store, because the scheme of its own origin is not evidence about the developer's push rights on their own repository; the root's push behavior is unchanged.
- Nested submodules at depth two or deeper. The *shape* of the tool's store scope is unchanged — the workspace root plus its direct children, never nested — while the *membership rule* changes from `.gitmodules` text to the registered-submodule mechanism; the two tools' sets may therefore differ where `session-init`'s nested walk reaches further.
- The eligibility of a wiki-origin submodule and of a submodule with no `origin` remote. The tool's existing handling of both is unchanged, and the two tools' sets may differ on them.
- Any new tool command, wrapper, hook, or scenario harness beyond the one scenario script named in Section 2.
- Which tracker receives an issue about a file in a vendored checkout — the deck's upstream tracker, the consumer's own tracker, or none. R-5 decides only that a pull-only repository holds no local store and that no local-store operation targets it; the `issues` card's path-prefix routing is unchanged, and a consumer's agent that files an issue about a vendored file is a separate design question.

## 6. Approach

Fix the mechanism where the defect is decidable, and state the boundary where it is not.

1. **`tools/local-issues`** — replace the `.gitmodules` text parsing in the store-eligible repository set with the registered-submodule mechanism `session-init` already uses (R-1); add the pull-only rule that keeps a pull-only child repository out of the store set, off the fetch and push paths, and out of the mutation path (R-2).
2. **`tools/session-init`** — report each repository's writability and withhold the store path for a pull-only repository (R-3).
3. **`skills/git-workflow-branch/SKILL.md`** — state the delivery-target rule, the pointer-scope clause, and the no-routing-around clause (R-4).
4. **`skills/issues/SKILL.md`** — state the store rule and qualify the operating-contract line (R-5).
5. **The two operating references** — bring the `init` descriptions into line with the new repository set (R-6).
6. **`tests/test_local_issues/`** — move the discovery tests' expectations onto R-1's mechanism, keeping the properties they were written for (R-7).
7. **`tests-v2/behaviors/`** — add the scenario that runs an agent against a pull-only deck checkout and asks for delivery, and pair it with clean-room evaluations of the recorded tool calls (R-7).

No new mechanism, no tool command, no threshold (R-7): the defect is a wrong repository set, and the fix is the right repository set.

### Alternatives considered and discarded

- **`.opencode/AGENTS.md`** — the file states that it "must stay a pointer and carry no rules", and it sits outside the `skill-creator` admission gate's scope, so a rule placed there would bypass the deck's governance. Discarded.
- **`floor.md`** — the always-injected surface costs every session, in every repository, for a rule that binds one decision the `git-workflow-branch` card is loaded to make. Discarded in favor of the card.
- **A pre-push hook in the vendored checkout that refuses the push** — the deck's hooks are installed by `session-init` into the workspace root's git directory, and a vendored checkout is not the workspace root, so the session has no installation path for a hook in the checkout where the rule binds; placing one would require the repository management the rule forbids. The floor permits mechanical enforcement of fact-decidable rules, and this rule is fact-decidable, so the ground here is the installation path and the change's minimality — not a prohibition on scripting. Discarded.
- **Probing push access to decide whether a checkout is writable** — a probe mutates or prompts, and the `http(s)` scheme is the detection the developer stated. Discarded.
- **Keeping the `.gitmodules` parsing and instead checking whether a child directory is a git repository** — an unregistered plain clone *is* a git repository, so the check does not distinguish the consumer's vendored deck from a registered submodule. Discarded.
- **Making the tool's repository set transitive, matching `session-init`'s nested walk** — out of scope: the tool's store scope keeps its shape (the workspace root plus its direct children) and nothing in the stated defect reaches deeper. Recorded in Section 5 rather than attempted here.

## 7. Impact

- **Consumers:** every session in a repository that vendors the deck. The store no longer mounts inside a read-only checkout, the session's inventory and the tool's inventory agree on the vendored checkout, and the agent stops attempting delivery into a checkout it cannot write to.
- **Risk — a false pull-only classification.** A child repository over an `https` origin that the session *can* push to loses its store. The workspace root is exempt (R-2), which covers the common case of a consumer's own repository cloned over the web; a child repository over `https` that the developer owns and pushes to is the residual case.
- **Risk — the developer's own deck checkout.** The deck's own development family (the `opencode-config` parent with the deck registered over an `ssh` origin) keeps the deck's store and stays a delivery target; SC-9 exercises the store half for a registered submodule over a writable origin and SC-8 the workspace root's own store, while the delivery half is exercised by SC-11's card-text check and by the SC-17–SC-20 scenario.
- **Blast radius:** `tools/local-issues`, `tools/session-init`, `skills/git-workflow-branch/SKILL.md`, `skills/issues/SKILL.md`, `skills/issues/references/local-issues-cli.md`, `skills/issues/references/sync-mirroring.md`, the tool's unit tests under `tests/test_local_issues/`, and one added behavioral scenario under `tests-v2/behaviors/`. No other card, tool, hook, or plugin changes.
- **Harness compatibility — the classification is tier-dependent.** The behavioral harness injects the rewrite `url.https://github.com/.insteadOf=git@github.com:` into the Docker tier as env-level config that applies to every git invocation in the container (`tests-v2/docker/docker-harness.sh`), and into the host tier as a clone-time `-c` option that git does not persist. Under the effective-URL read the rule uses, the deck submodule's origin therefore resolves differently by tier: as `https://github.com/michael-conrad/.opencode.git` in a Docker-tier run, and as its `ssh` form in a host-tier run (both verified 2026-10-24 — see Section 8). A Docker-tier run consequently classifies the deck as pull-only: the deck receives no issue store, and the deck is a non-delivery target. Three consequences follow, all checked. No harness scenario depends on the deck's issue store: the fixture issues are injected into the root store, and no scenario names the `.opencode#N` qualifier as a store target. The four scenarios that edit a deck card in the harness test project judge the *edit* and the absence of a self-chosen direction, not a delivery: `.opencode#2554` SC-8 (a mechanical fix leaves the card otherwise unconverted), `.opencode#2554` SC-9 (a substantive edit converts the whole card), `.opencode#2584` SC-4 (the edit completes without admission archaeology or a direction-seeking halt), and `.opencode#2657` SC-10 (the run asks one open-ended question and chooses nothing). None of those four criteria requires a branch, a commit, or a push in the deck checkout, so R-4's editing clause leaves the edits intact, and R-4's reporting clause is not a direction-seeking halt. And `git-workflow-branch` rule 2's pointer sync is not a delivery: the harness's deck is a *registered* submodule, so rule 2 still applies to it, and the sync moves that checkout's HEAD and records the pointer in the parent — the parent is where the push lands, so no delivery is attempted into the deck. One fixture assumption is affected: `.opencode#2657` SC-10's per-scenario fixture (`tests-v2/behaviors/fixtures/setup/2657-sc5-directed-deck-edit-open-choice.sh`) configures the deck checkout's git identity "so the agent can commit the card edit it is directed to make" — a delivery action the rule forbids in a tier where the deck reads as pull-only, and one that scenario's criterion does not require. The harness's own root reads as `https` in both tiers, which R-2's and R-4's root exemptions cover: the root keeps its store and stays a delivery target.
- **Recovery:** the change is text and tool behavior; reverting the seven surfaces and removing the scenario script restores the previous behavior.

## 9. Edge cases

- The classification reads the *effective* origin: a checkout whose stored origin is `ssh` but whose URL rewrite resolves it to `https` is pull-only. The Docker tier of the behavioral harness is exactly such a case for the deck submodule.
- The workspace root is never a non-delivery target on account of its origin's scheme, is reported `not-pull-only`, and always keeps its store.
- A registered submodule's pointer sync under `git-workflow-branch` rule 2 is not a delivery attempt: it moves that checkout's HEAD and records the pointer in the parent repository, and the parent's push lands in the parent. R-4's pointer-scope clause reaches a checkout the workspace root does not track, which has no pointer to sync in the first place.
- A registered submodule whose `git submodule status` line carries a leading `+` (a checked-out commit other than the recorded gitlink) is registered and initialized: it remains a store host, exactly as the deck's own development family requires.
- A repository with no `origin` remote at all is neither pull-only nor pushable; the tool's existing no-remote handling is unchanged.
- A child repository whose effective origin is `git://` or another non-`http(s)` scheme is treated as writable, because the stated detection rule names `http` and `https` only.
- The deck's own `issues-data` worktree in the developer's checkout is a linked worktree of a registered submodule over an `ssh` origin; R-1 and R-2 leave it in place.
- An issue mutation naming a pull-only repository fails at the tool rather than silently succeeding; the tool's error names the repository and its pull-only classification.
