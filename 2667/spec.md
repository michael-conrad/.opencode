# Spec: Detect a pull-only registered deck, and let the agent handle it with judgment

## 1. Problem

A consumer repository can hold this deck as a **registered** submodule whose origin is an `http`/`https` URL. Such a deck is **pull-only**: the session cannot push to it, so nothing can be written to it — including its `issues-data` branch. The deck's tooling and cards have no detection for that state, so the session walks into it.

**The store mounts inside a repository the session cannot write to.** `local-issues init` — which the `issues` card mandates at session start — created the deck's `issues-data` branch inside the checkout and mounted the deck's whole issue store at `.opencode/.issues`. Reproduced on 2026-10-24 in a consumer whose `.opencode` is a registered submodule with the effective origin `https://github.com/michael-conrad/.opencode.git`: after `init`, `git -C .opencode branch` listed `issues-data`, `git -C .opencode worktree list` listed `.opencode/.issues` at the upstream's tip, and the tool's own report read `issues_count: 1256`. The deck's `issues-data` branch is published on the upstream, so the fetch succeeds and the store mounts rather than failing.

**The push path is unguarded there.** The mutations that store accepts auto-commit and auto-push. The tool skips a push only on its worktree-establishment and auto-commit paths, and only when the remote is `https` **and** no credential helper is configured; with a credential helper configured — the ordinary state on a developer machine — the tool attempts a push into a repository the consumer does not own, whose `issues-data` branch is public. Two further push paths carry no guard at all: the `init`/`sync` path pushes the store branch whenever the store-holding repository has a remote, and `sync-file` resolves its target repository from the file path it is given and pushes that repository's store branch.

**The tool's store-host set is wider than "registered submodule".** `local-issues._discover_all_repos` parses `.gitmodules` text and accepts any child directory that exists, so a path named in `.gitmodules` that is not a registered submodule — a deinitialized one, a removed gitlink — is treated as a store host. A registered-but-uninitialized submodule makes the bootstrap abort outright: `git worktree add` runs inside a directory that is not a repository, and the session's store bootstrap dies with `fatal: 'issues-data' is already used by worktree at .../.issues`. `session-init` already draws the line the tool should draw: it enumerates repositories through git's registered-submodule mechanism (`.opencode#2544`).

**The session's inventory does not say what the agent cannot do.** `session-init`'s `## Repo Information` block reports each repository's owner, repo, platform, and url. Nothing marks a repository the session cannot write to, so the agent has no signal that a push there cannot succeed.

**No card tells the agent how to handle it.** `git-workflow-branch` (rules 1–6), `git-workflow-commit` (rules 1–5), and `git-workflow-pr` (rules 1–6) mandate branch creation, commits, pushes, and pull requests "in any repo" with no check that the session can write there, and the `issues` card's operating contract claims that a first mutation auto-initializes the `.issues/` worktree. An agent that meets a pull-only deck runs the whole delivery sequence and fails at the push.

### 1.1 Root cause

The deck detects nothing about writability. Detection is fact-decidable and belongs in the tooling; the handling that follows is intent-decidable and belongs to the agent. The deck currently has neither half: the tooling treats every discovered repository as writable, and the cards state no rule that would let the agent recognize the state it is in.

### 1.2 What this change does not claim

The consumer case that is **not** a defect: a vendored deck that the workspace root does not track — a gitignored sub-repository with no `.gitmodules` entry — is never discovered by the tool. Measured on 2026-10-24: `local-issues init` in such a workspace leaves the vendored checkout untouched — no `issues-data` branch, no `.issues` worktree, no store. A gitignored sub-repository has no reason to be named in `.gitmodules`, so this state is not the defect, and the change does not rest on it.

## 2. Scope

The change touches seven existing surfaces in the `.opencode` repository and adds one file.

The seven surfaces:

- `tools/local-issues` — the set of repositories eligible to hold an issue store, the pull-only detection, the per-repository report the agent reads, and the `doctor` health marker.
- `tools/session-init` — the writability fact it reports per repository.
- `skills/git-workflow-branch/SKILL.md` — the pull-only delivery clause.
- `skills/issues/SKILL.md` — the store rule, the operating-contract line it qualifies, and the pull-only handling clause.
- `skills/issues/references/local-issues-cli.md` — the `init` row, which today describes the store's repository set as `.gitmodules` children.
- `skills/issues/references/sync-mirroring.md` — the `init` bullet, which carries the same description.
- `tests/test_local_issues/` — the tool's unit tests, four test functions across two files: three pin the discovery and per-repository-attribution behavior R-1 changes, and the fourth (`test_doctor_is_read_only`) shares the doctor file's module fixture and keeps its read-only property. Their expectations move onto R-1's mechanism; the mechanism is not reverted to keep them green, and each function keeps the property it was written for.

The one added file: a behavioral scenario script under `tests-v2/behaviors/`, the artifact generator for the pull-only handling clause, paired with a clean-room evaluation of its recorded tool calls.

Untouched: `floor.md`; `.opencode/AGENTS.md`; the `git-workflow-commit` and `git-workflow-pr` cards' own mechanics; the deck's own issue store contents; `attic/`; the `skill-creator` admission gate.

## 3. Requirements

- **R-1** — `tools/local-issues` SHALL determine the repositories eligible to hold an issue store from git's registered-submodule mechanism: the workspace root, plus the set `git submodule status` reports for the workspace root, restricted to the paths the workspace's `.gitmodules` names. The tool SHALL NOT derive eligibility from `.gitmodules` text parsing or from the presence of a directory. A path `git submodule status` reports as uninitialized (a leading `-`) SHALL NOT receive a store, and the bootstrap SHALL NOT fail on it.
- **R-2** — `tools/local-issues` SHALL detect a pull-only repository: one whose effective `origin` URL — as `git remote get-url origin` reports it, after git's URL rewrites — carries the scheme `http` or `https`. Detection SHALL cover the workspace root's children only; the workspace root SHALL be exempt, because the scheme of the root's own origin is not evidence about the developer's push rights on their own repository, and an `https` root is a common state for a repository cloned over the web.
- **R-3** — For a repository the tool detects as pull-only, the tool SHALL NOT create an `issues-data` branch in it, SHALL NOT mount an `.issues` worktree in it, SHALL NOT fetch from it, and SHALL NOT push to it. Every mutation command the tool offers — `create`, `update`, `comment`, `close`, `delete`, `link`, `renumber` — that names it SHALL be refused with a diagnostic naming the repository and its pull-only classification, and `sync-file`, which resolves its target repository from the file path it is given and pushes that repository's store, SHALL refuse a path inside such a repository's store on the same terms.
- **R-4** — `tools/local-issues` SHALL report a pull-only repository in its per-repository report, marked with the classification `pull-only`, and SHALL report no operation against it. The tool SHALL still resolve such a repository by name, so that a refusal can name it. A repository outside the tool's repository set is not known to the tool at all: a command naming it is refused as an unknown repository. The tool's `doctor` health report SHALL mark the pull-only repository's store state with the same classification and SHALL NOT emit the `UNHEALTHY` branch marker for it, because R-3 makes the absent store intentional — the absent-branch health failure is a false alarm there.
- **R-5** — `tools/session-init` SHALL report, for each enumerated repository, a `writability:` field in the `## Repo Information` block, valued `pull-only` or `not-pull-only`, using the same detection and the same root exemption as R-2. A repository reported `pull-only` SHALL carry no issue-store path, in either the `## Repo Information` block or the `## Local Issue Folders` section. The two tools SHALL derive their repository sets from the same mechanism, so a checkout the workspace root does not track is in neither set.
- **R-6** — `skills/git-workflow-branch/SKILL.md` SHALL state the pull-only delivery clause. The clause SHALL name the state — a registered submodule whose origin is pull-only, so that a push to it cannot succeed — and SHALL leave the handling to the agent's judgment: the agent does not attempt a push it knows cannot succeed, and it decides how the change is to be delivered instead (from a repository it can push to, such as a fork or clone of that repository, or by reporting to the developer that the change cannot be delivered from this workspace). The clause SHALL NOT prescribe the handling itself, and SHALL NOT forbid the agent from delivering the change from a repository it can push to.
- **R-7** — `skills/git-workflow-branch/SKILL.md` SHALL scope its submodule rules — the pointer sync (rule 2) and the pointer-capture commit (rule 3) — to registered submodules, and SHALL state that a checkout the workspace root does not track is not a submodule: it has no pointer to sync or to capture, and the agent does not move its HEAD to a remote trunk tip.
- **R-8** — `skills/issues/SKILL.md` SHALL state that a pull-only repository holds no local issue store, that the local store's operations do not target it, and that its issues are read and written through the platform CLI against its own tracker. The card's operating-contract line stating that a first mutation auto-initializes the `.issues/` orphan-branch worktree SHALL be qualified so that it does not claim a store for a pull-only repository.
- **R-9** — The two operating references that describe `init`'s repository set — `skills/issues/references/local-issues-cli.md` and `skills/issues/references/sync-mirroring.md` — SHALL describe that set as the workspace root plus its registered submodules, SHALL NOT describe it as `.gitmodules` children, and SHALL carry the pull-only carve-out R-3 establishes.
- **R-10** — The change SHALL touch only the seven surfaces named in Section 2, SHALL add exactly the one file named in Section 2, and SHALL add no tool command, no wrapper, and no enforcement hook. The deck's unit-test suite SHALL pass after the change, with the tests that pin the old discovery mechanism carrying their expectations onto R-1's mechanism and keeping the properties they were written for.

## 5. Not included

- The `work` card's path selection, the `plan` card, and the `implement` card's own work-cycle rules.
- The `skill-creator` admission gate and every other deck-governance rule.
- A vendored deck that the workspace root does not track — a gitignored sub-repository with no `.gitmodules` entry. The tool does not discover it today and does not after this change; it receives no store and appears in no report, and a command naming it is refused as an unknown repository. Section 1.2 records the measurement.
- Any behavior change for a **registered** submodule whose effective origin is `ssh`, a local path, or another non-`http(s)` scheme: it keeps its store and stays a delivery target.
- Read-only credentials on a non-`http(s)` origin (a read-only SSH deploy key). The `http(s)` scheme is the detection rule; a read-only `ssh` origin is not detected.
- The workspace root's own push rights. The root is reported `not-pull-only` and keeps its store, because the scheme of its own origin is not evidence about the developer's push rights on their own repository; the root's push behavior is unchanged.
- Nested submodules at depth two or deeper. The *shape* of the tool's store scope is unchanged — the workspace root plus its direct children, never nested — while the *membership rule* changes from `.gitmodules` text to the registered-submodule mechanism; the two tools' sets may therefore differ where `session-init`'s nested walk reaches further.
- A wiki-origin submodule is affected to the extent its origin carries `http` or `https` — a wiki remote is an `https` URL — and then receives no store; `session-init` keeps its own wiki exclusion, so the two tools' sets may differ on a wiki-origin child.
- Any new tool command, wrapper, hook, or scenario harness beyond the one scenario script named in Section 2.
- A script that decides the handling for the agent. The handling is intent-decidable, and the deck's discipline forbids scripting it; the tooling detects and reports the state, and the card leaves the choice to the agent.

## 6. Approach

Split the problem at the line the deck already draws: a fact-decidable rule may be enforced mechanically, an intent-decidable one may not be scripted.

1. **`tools/local-issues`** — draw the store-host set with git's registered-submodule mechanism (R-1); detect a pull-only child repository (R-2); perform no store, fetch, push, or mutation operation against it, and refuse a mutation by name (R-3); report it as pull-only so the agent can see the state — in the per-repository report and, in `doctor`, as the classification instead of the absent-branch health marker (R-4).
2. **`tools/session-init`** — report the same fact in the same vocabulary, and withhold the store path for a pull-only repository (R-5), so the session's picture and the tool's behavior agree.
3. **`skills/git-workflow-branch/SKILL.md`** — state the pull-only delivery clause (R-6) and scope the pointer rules to registered submodules (R-7). The clause names the state and leaves the handling to the agent's judgment.
4. **`skills/issues/SKILL.md`** — state the store rule and the handling for a pull-only repository's issues (R-8).
5. **The two operating references** — bring the `init` descriptions into line with the new repository set and the pull-only carve-out (R-9).
6. **`tests/test_local_issues/`** — carry the discovery tests' expectations onto R-1's mechanism, keeping the properties they were written for (R-10).
7. **`tests-v2/behaviors/`** — add the scenario that runs an agent against a pull-only deck and asks for delivery, and pair it with a clean-room evaluation of the recorded tool calls (R-10).

No new mechanism, no tool command, no threshold (R-10): the defect is a missing detection and a missing rule about what the agent does with it.

### Alternatives considered and discarded

- **`.opencode/AGENTS.md`** — the file states that it "must stay a pointer and carry no rules", and it sits outside the `skill-creator` admission gate's scope, so a rule placed there would bypass the deck's governance. Discarded.
- **`floor.md`** — the always-injected surface costs every session, in every repository, for a rule that binds one decision the `git-workflow-branch` card is loaded to make. Discarded in favor of the card.
- **A pre-push hook in the deck checkout that refuses the push** — the deck's hooks are installed by `session-init` into the workspace root's git directory, and the deck checkout is a submodule with its own git directory, so the session has no installation path for a hook where the rule binds. The floor permits mechanical enforcement of fact-decidable rules, and the tool's own refusal is the mechanical enforcement point. Discarded.
- **Probing push access to decide whether a repository is writable** — a probe mutates or prompts, and the `http(s)` scheme is the detection the developer stated. Discarded.
- **Keeping the `.gitmodules` parsing and instead checking whether a child directory is a git repository** — an unregistered plain clone *is* a git repository, so the check does not distinguish a registered submodule from anything else. Discarded.
- **A rigid prohibition on delivering into a pull-only repository** — that would forbid the agent from delivering the change from a repository it can push to, which is the handling a competent engineer chooses. Discarded in favor of the judgment clause.
- **Making the tool's repository set transitive, matching `session-init`'s nested walk** — out of scope: the tool's store scope keeps its shape (the workspace root plus its direct children) and nothing in the stated defect reaches deeper. Recorded in Section 5 rather than attempted here.

## 7. Impact

- **Consumers:** every session in a repository that holds the deck as a pull-only submodule. The store no longer mounts inside a repository the session cannot write to, the session's inventory says which repository that is, `doctor` no longer reports that repository's missing store as a branch-health failure, and the agent gets to decide how to handle it.
- **Risk — a false pull-only classification.** A child repository over an `https` origin that the session *can* push to loses its store. The workspace root is exempt (R-2), which covers the common case of a consumer's own repository cloned over the web; a child over `https` that the developer owns and pushes to is the residual case.
- **Risk — the developer's own deck checkout.** The deck's own development family (the `opencode-config` parent with the deck registered over an `ssh` origin) keeps the deck's store and stays a delivery target; SC-6 exercises the store half for a registered submodule over a writable origin and SC-5 the workspace root's own store.
- **Blast radius:** `tools/local-issues` (its discovery set, its pull-only classification and per-repository reporting, its `doctor` marker, the mutation refusals, and the `sync-file` refusal), `tools/session-init`, `skills/git-workflow-branch/SKILL.md`, `skills/issues/SKILL.md`, `skills/issues/references/local-issues-cli.md`, `skills/issues/references/sync-mirroring.md`, the tool's unit tests under `tests/test_local_issues/`, and one added behavioral scenario under `tests-v2/behaviors/`. No other card, tool, hook, or plugin changes.
- **Harness compatibility — the classification is tier-dependent.** The behavioral harness injects the rewrite `url.https://github.com/.insteadOf=git@github.com:` into the Docker tier as env-level config that applies to every git invocation in the container, and into the host tier as a clone-time `-c` option, which git persists in the superproject's own `.git/config` — so it reaches the superproject's git invocations but not the submodule's. The deck submodule's effective origin therefore resolves as `https://…` in a Docker-tier run and as its `ssh` form in a host-tier run (both verified 2026-10-24 — see Section 8). A Docker-tier run consequently presents the agent with a pull-only deck: no issue store in the deck, and the deck reported pull-only. No harness scenario depends on the deck's issue store: the fixture issues are injected into the root store, and no scenario names the `.opencode#N` qualifier as a store target. The four scenarios that edit a deck card in the harness test project judge the *edit* and the absence of a self-chosen direction, not a delivery: `.opencode#2554` SC-8 (a mechanical fix leaves the card otherwise unconverted), `.opencode#2554` SC-9 (a substantive edit converts the whole card), `.opencode#2584` SC-4 (the edit completes without admission archaeology or a direction-seeking halt), and `.opencode#2657` SC-10 (the run asks one open-ended question and chooses nothing) — none of which requires a push to the deck.
- **Recovery:** the change is text and tool behavior; reverting the seven surfaces and removing the scenario script restores the previous behavior.

## 9. Edge cases

- The classification reads the *effective* origin: a checkout whose stored origin is `ssh` but whose URL rewrite resolves it to `https` is pull-only. The Docker tier of the behavioral harness is exactly such a case for the deck submodule.
- The workspace root is never classified pull-only on account of its origin's scheme, is reported `not-pull-only`, and always keeps its store.
- A registered submodule's pointer sync under `git-workflow-branch` rule 2 is not a delivery: it moves that checkout's HEAD and records the pointer in the parent repository, and the parent's push lands in the parent. R-7 reaches a checkout the workspace root does not track, which has no pointer to sync in the first place.
- A registered submodule whose `git submodule status` line carries a leading `+` (a checked-out commit other than the recorded gitlink) is registered and initialized: it remains a store host, exactly as the deck's own development family requires.
- A repository with no `origin` remote at all is neither pull-only nor pushable; the tool's existing no-remote handling is unchanged.
- A child repository whose effective origin is `git://` or another non-`http(s)` scheme is treated as writable, because the stated detection rule names `http` and `https` only.
- The deck's own `issues-data` worktree in the developer's checkout is a linked worktree of a registered submodule over an `ssh` origin; R-1 through R-4 leave it in place.
- A mutation naming a pull-only repository fails at the tool rather than silently succeeding; the tool's error names the repository and its pull-only classification.
- The `doctor` marker line for a pull-only repository names its classification instead of the absent-branch failure; the marker for a repository that merely misses its branch, with no classification, stays `UNHEALTHY`.
