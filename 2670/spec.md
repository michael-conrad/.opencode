# [SPEC] Docs-currentness duty and rule-compliance counterweight — sequence over gates

Resolves `.opencode#2670`.

## 1. Intent and Executive Summary

This spec repairs two measured regressions with one mechanism: prose and sequence, with zero mechanized in-path gates. The two regressions share one root cause shape — the deck's directive surface was gutted by #2501's consolidation, and even surviving directive text demonstrably does not gate behavior — so one change answers both: the producer-side duty re-enters as a step in an already-fidelity-bound workflow sequence, and the rule-compliance counterweight re-enters the floor's decision-loop region. Enforcement is ex-post only (the existing fresh-context `verify` pass) plus real-time in-chat visibility.

## 3. Requirements

**R-1 — docs-currentness step (implementation-workflow.md, pre-implementation table).** A new row SHALL state the duty with these elements:

- (a) **Scope.** Every surface the change implements against that is documented outside this repository — library APIs, language features, configuration formats, wire formats, dependency versions. Which surfaces a change touches is the agent's judgment at cycle time; the class is concrete, not a vague duty.
- (b) **Consultation before code.** The agent consults the surface's current authoritative documentation — official documentation at the current version, the live package registry, or the consumed source and type hints — before the first code-write of that surface. The duty is per-surface and per-cycle: a mid-cycle change implementing a new externally-documented surface re-triggers it (the reference is re-read before every mid-cycle change per `implement` item 4).
- (c) **In-chat statement.** The agent states in chat what the current documentation established for the surface — brief, discriminating (what the docs say that the code now relies on), not a fetched-URL recital.
- (d) **What does not count.** Memory, training data, prior sessions' knowledge, similar-library analogy, stale posts and tutorials. None of these is verification.
- (e) **Composition pointers.** A witnessed deprecation follows the deprecation encounter protocol (pointer, no duplication); implement item 6's consumed-framework docs pass and recorded version remain the special case it already is.

**R-2 — pointer clause (implement SKILL.md, item 2).** Item 2 SHALL name the docs-currentness step as part of the pre-implementation work — one clause pointing at the reference's step, restating none of R-1's content.

**R-3 — clarify-first (floor.md, decision-loop region).** A terse developer message that could plausibly authorize or touch a prohibited or authorization-gated surface SHALL be clarified first — never acted on under its most convenient reading.

**R-4 — compliance-is-action (floor.md, decision-loop region).** Knowledge of a rule — including citing it — SHALL NOT stand as satisfaction of the rule; compliance is the action, never the citation.

**R-5 — option listings name no prohibited surface (floor.md, decision-loop region).** An option listing SHALL NOT name a prohibited surface; raising a prohibited surface as an option is the defect the owning rule already states. Tests-v2 R-20's model-instance (line 681) is the particular case; this generalizes it. The floor clause owns the general statement — per-card rules state their own instances.

**R-6 — ex-post examination (verify SKILL.md).** The reviewer's diff examination SHALL include the change's externally-documented-surface usage, judged for adequacy against current documentation; usage the current documentation contradicts is a correctness finding, flagged under the existing churn rule (it affects correctness — the anti-churn binding is unchanged).

## 5. Edge Cases

- **Unreachable documentation.** When the live source cannot be reached, the reference's standing escalation rule governs — the step cannot complete honestly, so the cycle stops with a reported blocker; silently falling back to memory substitutes the unverified for the unavailable and is the exact failure class this spec repairs.
- **Short-path work.** The pre-implementation checklist binds all work cycles; a change touching no externally-documented surface vacuously satisfies the step — the scope element (a) limits the duty to surfaces actually implemented against, and invents no ceremony for one-line fixes that touch none.
- **Earlier research.** A research pass with sourced findings (the `research` card demands live-source verification) does not exempt the implementation-time step: the step verifies against the surface's documentation as of the cycle, not as of when research happened. No conflict exists — both demand live sources; the step adds the before-code timing.
- **The floor's size discipline.** The three clauses are the measured remediation target (the LL-1 record names the floor's standing formula as the counterweight's home); they add three sentences to one region and nothing else — no restructure, no new section.

## 6. Out of Scope

- Mechanized enforcement of any kind — hooks, scripts, lint, tests-v2 scenarios, record artifacts (recorded bypass history and the 2026-10-26 rulings).
- Attic restorations — evidence sources only (retired tooling and structure would be cargo culted).
- Changes to the session-init banner, the `research` card, `deprecation-encounter-protocol`, or tests-v2 R-20's text.
- Any new card or guideline file; any floor restructuring beyond the three clauses.
- Re-review loops or multi-pass verification — the single-verify-pass design of #2501 stands unchanged.
