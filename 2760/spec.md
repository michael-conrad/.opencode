# [SPEC] git-workflow-pr: decision-time stacked-PR term anchor, per-layer precedent stance, same-scope create-time enumeration, companion-PR disposition

## Intent and Executive Summary

**Problem Statement.** Under one `approved for stacked PR` authorization (NewsRx/hermes, 2026-11-20), the agent filed two pull requests — one per-layer PR whose base was the middle layer's *branch* (the exact shape `git-workflow-pr` rule 3 names as "never") and one companion PR for the spec-mandated promotion — leaving the middle layer with no PR and the session asking the developer for a third. The same per-layer shape, filed by an earlier session (hermes PR #455), stood open beside the new ones as if it were house style. The card's rule 3 already mandates the opposite — one PR against the trunk carrying one squashed commit per issue, with "N branches / N PRs for one authorization scope is the violation" — and the scope-boundary amendment .opencode#2639 delivered was on trunk at the time. The violation therefore repeated against delivered provisions, and the card leaves four surfaces at the decision point undefended: (1) the token "stacked PR" collides with the wider ecosystem's term — GitHub's own documented and, since 2026-07-30, natively supported stacked pull requests are the per-layer chain — and the card states its opposite definition once, with no contrast where the token is read; (2) no card text classifies an already-open per-layer PR as a violation rather than precedent; (3) the rule-2 pre-create checklist verifies commits, tests, verify, and pointer state but never enumerates PRs of the same scope, so the one-scope-one-PR rule bites only in the developer's review, after creation; (4) whether a spec-mandated companion PR (a dev→main topology promotion) counts inside the authorization scope or stands apart is undefined deck-side.

**Root Cause / Motivation.** The shape mandate rests on three unstated loads, and each one broke in the incident. First, term binding: rule 3 defines "stacked PR" once; an agent carrying ecosystem priors binds the developer's token to the ecosystem definition at token-read time, and nothing in the card points back to rule 3 when the token arrives (contribution 1 of the incident record). Second, precedent: rule 3 says nothing about how to treat an existing open per-layer PR, so a prior session's violation survived as apparent sanction and shaped the next session's filing (contribution 2). Third, create-time contrast: rule 2's checklist has no same-scope PR enumeration, so "one authorization scope → one PR" had no enforcement surface at the moment of creation (contribution 3). And the scope boundary's split condition ("splitting requires the developer to have named the split") does not say whether a spec-mandated second PR shape is that naming — the incident left that question to the agent's improvisation (contribution 4). Recurrence is the motivation for timing: this behavior class has now violated three times (.opencode#2509, the .opencode#2639 incident, this incident), and the third violation happened while #2639's provisions were live on trunk, which isolates the four surfaces above as the uncovered remainder.

**Approach Chosen.** Amend `git-workflow-pr` at the rules where the decisions are actually made. Rule 1's token-arrival step (the not-done-default state determination) gains a short pointer naming card-scoped tokens that read "stacked PR" as bound to rule 3's definition, never the ecosystem's per-layer pattern. Rule 3 gains, beside its definition: the decision-time term contrast (the deck's one-trunk-PR definition versus the ecosystem's per-layer chain, named as the prohibited shape), the precedent stance (an existing open per-layer PR is a violation, not precedent; the creating agent halts for developer direction on its disposition), and the companion-PR disposition in the scope provision (an approved spec that explicitly names a second PR-shaped deliverable — its head, base, and sequencing — is the developer's named split: a distinct deliverable, not a stacked-PR layer). Rule 2's checklist gains one item: the create-time same-scope enumeration, resolved against rule 3 before creation.

**Alternatives Considered & Why Discarded.**

- *Route the requirements into .opencode#2639's spec in place (search-before-filing match check).* Discarded: that spec's requirement set — scope definition, extension rule, no-issue rule, one-PR default, bounded freshness verification — is delivered and verified on trunk, its completion gate is closed (`completed`, 2026-10-21), and none of the four uncovered surfaces above is in it. Amending it would mix delivered and pending work under one completed gate; the search-before-filing mandate routes when an existing spec covers the same requirement, and #2639 does not cover these.
- *Write the term contrast into `floor.md`'s authorization-vocabulary entry ("approved for pr"-class tokens).* Discarded: the floor is the always-injected surface, and deck governance keeps card-scoped directives out of it (the skill-creator admission gate; recorded in #2639's approach). The card is load-triggered exactly when PR-boundary authorization arrives, so the anchor lands in context at the decision moment without widening always-loaded scope.
- *A mechanical gate — a hook or script blocking a second same-scope PR.* Discarded: the shape disposition is intent-decidable (which PRs are the "same scope," which file is a named split); judgment decides, and mechanisms verify facts only. The enumeration the checklist gains is the fact work feeding that judgment; the disposition stays with the agent's reading of rule 3.
- *Definition in the card's description field instead.* Discarded: descriptions state routing triggers; the existing trigger already fires at the decision point ("whenever PR-boundary authorization arrives"), so a description-side definition adds no earlier moment and buries a rule where the agent is not yet executing shape work.

**Key Design Decisions.**

- *The contrast lives at both the token-arrival step and the definition.* The misread forms at token read (rule 1's step) and materializes at shape selection (rule 3); a one-clause pointer at rule 1 catches the bind early while the full contrast at rule 3 stays where the definition it interprets lives. Tradeoff: two touched rules instead of one, for anchoring at both moments the incident separated.
- *The precedent stance routes discovery to a halt for developer direction, never agent-side closure.* Closing or removing another session's PR is outside the card rule 6's permitted update triggers and is hard to reverse; the developer — who merges and approves — directions the disposition. Tradeoff: one developer round per discovered violation, versus the agent unilaterally disposing of another session's work.
- *The companion bar is explicit spec naming: head, base, and sequencing stated in the approved spec.* The approved spec is the developer's authorization artifact, so its explicit naming satisfies "the developer named the split" in the only form the pipeline carries. The explicit-triple bar excludes PR-shape-adjacent phrasing ("a promotion follows") that does not actually design a second PR, keeping the default one-PR rule as the default. Tradeoff: some legitimately designed companions must re-file their spec to qualify — the bar errs toward fewest surprises.
- *The enumeration is fact-decidable; its resolution is not.* The checklist item states what to enumerate (open PRs intersecting the scope, by head, base, closing reference, or stacked chain membership) and uses the platform CLI (`gh pr list` / `gb` equivalent) — verifiable facts — and routes each finding to rule 3's provisions and the halt posture, where judgment governs. This keeps the floor's fact/intent split intact: no script decides scope.

## Requirements

- R-1. `git-workflow-pr` SHALL anchor the stacked-PR term at decision time: (a) rule 1's token-arrival step SHALL state that a card-scoped token reading "stacked PR" ("approved for stacked PR", `pr_strategy: stacked`, equivalents) carries the definition rule 3 defines — one PR against the trunk carrying one squashed commit per issue in the scope — and that the wider ecosystem's per-layer reading does not govern the token; (b) rule 3's definition SHALL state the contrast explicitly: the ecosystem's "stacked pull requests" pattern — a series of PRs where each PR targets the branch of the PR below it, forming a chain that lands on the trunk, per GitHub's own documentation — is the per-layer shape this rule names as the violation.
- R-2. `git-workflow-pr` rule 3 SHALL state the precedent stance: an existing open per-layer PR in a repository — including one filed by an earlier agent session of the same repo — is a shape violation under this rule, not precedent or house style; when the creating agent discovers one, the agent halts for developer direction on that PR's disposition rather than imitating its shape or closing it agent-side.
- R-3. `git-workflow-pr` rule 2's pre-create checklist SHALL include the same-scope enumeration: before creating any PR, the agent enumerates the repository's open pull requests intersecting the authorization scope — by head or base branch, by closing-keyword reference to a scope issue, or by stacked-chain membership with the scope's branches — using the platform CLI (`gh pr list` / `gb` equivalent); each intersecting PR is resolved against rule 3's provisions before creation, and PR creation is blocked until every intersecting PR is dispositioned.
- R-4. `git-workflow-pr` rule 3's scope provision SHALL define the companion disposition: a second PR-shaped deliverable that the approved spec explicitly names as its own deliverable — stating its head, base, and sequencing — is the developer's named split: permitted as a distinct deliverable, not a stacked-PR layer, and filed per the sequencing the spec states; a spec requirement that does not explicitly name the second PR's head, base, and sequencing, and any PR-shaped work outside a spec mandate, defaults to the one-PR rule.
- R-5. The amendments SHALL be confined to `git-workflow-pr`: one checklist item added to rule 2, and rule 1's and rule 3's stated additions; every other clause of the card survives unchanged; the card's provenance line gains exactly one entry citing this issue; the amended text stays root-agnostic — no repository names, no absolute paths.

## Cost Frame

- SC-1 … SC-6 (structural): acting — reading the amended card and running one diff against trunk: minutes. Skipping — the term anchor, stance, and gate exist only as text intent; the next stacked authorization can repeat the violation class, and each recurrence costs a developer-correction round plus the unwind of misshaped open PR surfaces on the affected repo's tracker.
- SC-7 (behavioral): acting — one harness scenario: container provisioning plus a live run, minutes of compute. Skipping — the decision-point behavior the amendments prescribe is never observed under the token that triggered the incident, so a conforming-text/non-conforming-behavior gap can persist invisibly; the text-only criteria cannot fail on it.

## Edge Cases

| Condition | Expected behavior | Resolution |
|---|---|---|
| Enumeration finds no open PR intersecting the scope | The gate passes on empty; the agent creates the scope's one trunk PR — no halt, no report overhead | Covered by SC-4's resolution element (normal path) |
| Enumeration finds an open per-layer PR filed earlier in the same scope, by the same session | Violation finding: the agent halts for developer direction before creating anything | Covered by SC-3, SC-7 |
| Enumeration finds a prior per-layer PR created by another party (a human, or a session outside this authorization) | Same stance: halt for developer direction; the agent never closes, retargets, or edits that PR agent-side | Covered by SC-3; rule 6's permitted-update triggers are unchanged |
| The approved spec explicitly names a companion PR (head, base, sequencing) alongside the scope's stacked work | The companion is permitted as its own deliverable per stated sequencing; the scope's own deliverable still lands as exactly one trunk PR | Covered by SC-5 |
| The spec carries PR-adjacent phrasing without naming head, base, and sequencing (e.g. "a promotion follows") | The naming bar is not met: the one-PR default holds, and the agent raises the ambiguity for developer direction rather than filing a second PR | Covered by SC-5's default branch |
| The scope spans a parent/submodule family (the promotion PR is a parent-repo artifact) | The same-scope enumeration runs per repository at each PR creation; parent/submodule ordering stays under rule 2's existing ordering gate, unchanged | Covered by SC-4 (enumeration subject is the repository's own open PRs); SC-6 preserves rule 2's existing clauses |
