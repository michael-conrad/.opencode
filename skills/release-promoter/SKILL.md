# release-promoter

0. **Release-candidate composition — before any analysis, branching, or gate.** For every release PR: pull the parent repository's trunk to its remote tip; then, for every registered submodule per `.gitmodules` (per-path and non-recursive), sync that submodule's pointer to the submodule's remote trunk tip — the tracked-branch tip fetched from the remote, never the recorded pointer — using `git-workflow-branch` rule 2's executed per-submodule remote-tip comparison as the evidence instrument. The trunk tip resolves through the `submodule.<name>.branch` field of the parent repository's `.gitmodules`; when no branch field exists, through the submodule remote's default branch (`refs/remotes/origin/HEAD`, ref existence guarded before use) — the release path never resolves the trunk tip from the submodule checkout's current checked-out branch. Composition is done when the executed comparison returns `at-tip` for every registered submodule; that outcome is the composition's success evidence. A registered submodule whose remote trunk tip cannot be resolved or fetched halts composition for developer direction — no `no-remote-tip` recorded-and-continue outcome exists on the release path, and no release branch, gate, or PR is entered past the halt. Unresolvable is exact — no `.gitmodules` branch field AND no resolvable `refs/remotes/origin/HEAD` after fetch (absent or pointing at a nonexistent ref), or an unfetchable tip; there is no fallback (enumerated remote refs, `ls-remote` listings, and the checkout's own HEAD are never the trunk tip). The order is fixed: compose (promote pointers at trunk tips), record the release branch, run the clean-room gate on the composed tree, file the release PR — a release PR is never filed from pointers that were not promoted at composition time. The promoted pointer bumps are the release's real content and are recorded in the release branch as pointer-capture commits under `git-workflow-branch` rule 3's tagged-SHA pointer discipline (the release exemption `git-workflow-pr` §2(e) already states); recording never passes through `git add <submodule-path>` when the submodule checkout's HEAD differs from the promoted SHA — index plumbing or a checkout of the promoted SHA is the mechanism, and the mandatory post-capture assertion (`git ls-tree HEAD <path>` == promoted SHA per promoted submodule) gates the capture commit before push (the full capture procedure is Phase C-0 step 8). The full procedure is the detail card: [the operating protocol](references/operating-protocol.md).
1. **Clean-room verification gate — after the parent repository's release branch is pushed, before the release PR is filed.** Verify the release candidate from a clean, shallow temp-copy checkout of the **parent repository** — the repository the project family is consumed from — cloned from the parent repository's remote URL, remote transport only. The parent's submodule resolution (`git submodule update --init --depth 1`) brings the release candidate and its sibling submodules along at the parent's recorded pointers; assert no drift; run the build and test commands through the parent's build framework and require zero failures. Assertion failures (`DRIFT_FAIL`, `BUILD_FAIL`) and the terminal no-source failure (`NO_SOURCE_FAIL` — no sanctioned source yields build/test commands) block the release PR — no retries within the release run; manifest absence is not a blocking failure (commands resolve from the fixed order: declared manifest → session-init per-root facts → the repository's documented build framework); environment/transport setup failures are diagnosed and the gate re-run, never treated as release-blockers. The gate never modifies the source working tree. A submodule repository never hosts its own release PR or tag — its content ships via the parent's pointer capture (two-way carve-out, .opencode#2683: that prohibition targets release artifacts; hash-permanence discipline tags on submodule commits per `git-workflow-branch` rule 3 are agent duty, not release artifacts). The full mechanism is the detail card: [the operating protocol](references/operating-protocol.md). **Release PR body:** the changelog plus the Submodule-bump section (`git-workflow-pr` §4), with `Closes` lines only when a release issue exists.
2. **Post-merge pre-tag re-check — after the release PR merges, before tag creation.** From a shallow temp-copy of the parent's merged trunk commit, assert submodule drift against the parent's recorded pointers and that the composed tree is content-identical to the tree the clean-room gate verified. A `TREE_MISMATCH` blocks promotion — no tag — the release stops for developer direction.
3. **Tag.** Annotated tag, `v`-prefixed, pointing at the merged release commit on the parent repository's trunk; tag message names the release.
4. **GitHub Release.** Create from the tag with the changelog as body
   (`gh release create`) — the Release body stays changelog-only; the tag
   and release exist together or neither does.
5. **Verify live.** Confirm tag and release via the API after creation — `gh release view` output is the evidence.
6. **No retries on partial state.** If a step half-succeeded, inspect actual state first; blind retries create duplicates.
